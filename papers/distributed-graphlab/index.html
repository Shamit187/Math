Distributed GraphLab: A Framework for Machine Learning and Data Mining in the Cloud

Yucheng Low, Joseph Gonzalez, Aapo Kyrola, Danny Bickson, Carlos Guestrin, Joseph M. Hellerstein Proceedings of the VLDB Endowment, Vol. 5, No. 8 · 2012
Abstract High-level data parallel frameworks such as MapReduce simplify large-scale data processing, but they do not naturally or efficiently support the graph-structured, asynchronous, iterative computation patterns common in machine learning and data mining (MLDM) algorithms. GraphLab, introduced in 2010 for the shared-memory setting, provides an abstraction that naturally expresses these patterns while enforcing serializability. This paper extends GraphLab to the substantially more challenging distributed setting. Key contributions include: a two-phase atom-based distributed graph representation for efficient load balancing, a pipelined distributed locking engine that hides network latency, a chromatic engine using graph coloring for synchronous-like execution, asynchronous fault tolerance via a variant of the Chandy-Lamport snapshot algorithm expressed using GraphLab primitives, and comprehensive evaluation on Amazon EC2 showing 20–60x speedup over Hadoop and performance competitive with hand-tuned MPI implementations on Netflix recommendation, video co-segmentation, and named entity recognition tasks.

1. Why MapReduce Is Not Enough for ML

MapReduce is a magnificent tool for a particular class of problems: embarrassingly parallel transformations and aggregations over large collections of independent records. Given a billion web pages, you can count word frequencies, build inverted indexes, or extract named entities — each page independently, results combined at the end. The framework handles parallelism, fault tolerance, and data movement automatically.

Machine learning algorithms, however, have a fundamentally different structure. They are not embarrassingly parallel. They are iterative: each step depends on the results of the previous step. They have graph-structured dependencies: updating a parameter for one vertex requires reading the current values of neighboring vertices. And they benefit enormously from asynchronous execution: if we update parameters in parallel using the most recent available values rather than waiting for a global synchronization barrier, many algorithms converge much faster.

Example — PageRank as a graph algorithm

PageRank is defined recursively. The rank of a webpage $v$ is: $$\mathbf{R}(v) = \frac{\alpha}{n} + (1-\alpha) \sum_{u \text{ links to } v} w_{u,v} \times \mathbf{R}(u)$$ where $\alpha$ is the random-jump probability and $w_{u,v}$ is the link weight. Computing PageRank requires iterating this equation until convergence. Each iteration requires reading the current ranks of all linking pages — which are being simultaneously updated by other iterations. In a synchronous (Pregel-style) system, all vertices update at the same time using values from the previous step. In an asynchronous (GraphLab-style) system, each vertex uses the most recent available values. Experiments show asynchronous PageRank converges in roughly half the wall-clock time.

The paper lists four properties of MLDM algorithms that existing distributed frameworks fail to support simultaneously: (1) graph-structured computation with sparse dependencies; (2) asynchronous iterative computation with parameter updates using the most recent values; (3) dynamic computation where some parameters converge quickly and computation should focus on the remainder; (4) serializability, the guarantee that the parallel execution is equivalent to some sequential execution, which many algorithms require for correctness (e.g., Gibbs sampling) or improved convergence (e.g., ALS for collaborative filtering).

2. The GraphLab Abstraction

GraphLab addresses all four properties through a clean three-part abstraction: the data graph, the update function, and the sync operation. These correspond roughly to data, computation, and global aggregation.

The GraphLab Abstraction

Data Graph: $G = (V, E, D)$ — a directed graph where each vertex $v \in V$ stores user data $D_v$ and each edge $uv \in E$ stores data $D_{u \to v}$. The graph structure is static (it does not change during execution), but vertex and edge data are mutable.
Update Function: $f(v, \mathcal{S}_v) \to (\mathcal{S}_v', \mathcal{T})$ — a user-defined stateless procedure that reads all data in the scope $\mathcal{S}_v$ of vertex $v$ (vertex data plus adjacent edge and vertex data), writes the updated scope $\mathcal{S}_v'$, and returns a set $\mathcal{T}$ of vertices to schedule for future updates.
Sync Operation: Maintains global aggregates (e.g., convergence estimators) by applying a commutative, associative Map-Reduce across all vertices' scopes.

The execution model is a simple loop: while there are scheduled vertices, pick one, apply its update function, add the returned vertices to the schedule. This single-loop semantics makes the abstraction easy to reason about sequentially, even though the actual execution may be highly parallel.

3. The Data Graph and Update Functions

The scope $\mathcal{S}_v$ of vertex $v$ is the set of data that an update function can read and write: the data on $v$ itself, the data on all edges incident to $v$, and the data on all neighboring vertices. This is deliberately local: an update function cannot directly access the data of a vertex two hops away, or global aggregates (those require the sync operation). This locality is the key property that makes the framework amenable to distributed execution.

An update function that returns neighboring vertices in $\mathcal{T}$ is scheduling those neighbors for future updates. This expresses adaptive computation: a vertex that changed significantly can trigger its neighbors to recompute, while a vertex that has converged need not schedule anyone. This is fundamentally more expressive than Pregel's BSP model, where all vertices communicate via messages in synchronized super-steps. In Pregel, you cannot decide to skip a vertex or prioritize one over another based on the current state of the computation. In GraphLab, you can.

Push vs pull for data access

Pregel is a push model for data: a vertex sends messages to its neighbors, and those neighbors receive the messages and update themselves. GraphLab is a pull model: a vertex directly reads the data of its neighbors when it executes. The difference matters for dynamic computation. In Pregel, if vertex $u$ has changed, it must explicitly send a message to all its neighbors to trigger their update. In GraphLab, if vertex $v$ is scheduled for an update, it simply reads the current values of its neighbors — whether or not they explicitly sent messages. This makes it natural for an update function to read the latest neighbor values and decide whether to reschedule based on what it finds.

4. Consistency Models

The power of the GraphLab abstraction comes from its consistency guarantees. The runtime guarantees a serializable execution: the parallel execution produces the same result as some sequential execution of update functions. This is achieved through three consistency models that trade off consistency strength against parallelism.

The Three Consistency Models

Full Consistency: An executing update function has exclusive read-write access to its entire scope (vertex + all adjacent edges + all adjacent vertices). No two update functions can run simultaneously unless their scopes are disjoint. This provides the strongest guarantee but limits parallelism: concurrently executing updates must be at least two hops apart in the graph.
Edge Consistency: An executing update function has exclusive read-write access to its central vertex and all incident edges, but only read access to adjacent vertices. Two update functions can overlap on adjacent vertices (both reading a vertex), but neither can be writing it. This is sufficient for many ML algorithms (e.g., PageRank only writes to the central vertex's data) and allows much more parallelism.
Vertex Consistency: An executing update function has exclusive write access only to the central vertex's data. Adjacent vertex and edge data can be read and written by other concurrent updates. Maximum parallelism but weakest consistency.

Most ML algorithms in practice require only edge consistency. The ALS (Alternating Least Squares) collaborative filtering algorithm requires full consistency for correctness. Gibbs sampling requires full consistency for statistical correctness. The framework lets the algorithm designer choose the appropriate level.

5. Distributed Design: The Atom Graph

Extending the shared-memory GraphLab to a distributed cluster requires solving graph partitioning at scale. The naive approach — partition the graph across machines, then acquire locks for cross-machine scope access — suffers from high network latency on every lock acquisition.

The distributed GraphLab uses a two-phase partitioning scheme. In the first phase, the graph is partitioned into many small pieces called atoms — far more atoms than machines (typically $k$ is much larger than the number of machines). Each atom is stored as a compressed journal file (a log of graph construction commands like AddVertex and AddEdge) on a distributed file system such as HDFS or Amazon S3. Each atom also records its ghosts: vertices adjacent to the partition boundary that actually belong to other atoms. In the second phase, a fast balanced partition of the atom meta-graph (a graph where atoms are nodes and edges represent cross-atom adjacency) is computed and assigned to machines. Each machine loads only the atoms assigned to it.

This two-phase approach allows the expensive graph partitioning to be done once and reused across different cluster sizes. To add more machines, only the atom-to-machine assignment changes; the atom files stay the same. Ghosts (shadow copies of boundary vertices) act as caches: when a machine needs to access a neighboring vertex on another machine, it first checks its local ghost cache, avoiding a network round trip unless the value has changed.

6. Two Execution Engines

Distributed GraphLab implements two execution engines to support different application profiles.

Chromatic Engine. This engine uses graph coloring: vertices are assigned colors such that no two adjacent vertices share the same color. The engine executes all vertices of one color simultaneously, then moves to the next color. Because no two simultaneously executing vertices are adjacent, there are no scope conflicts — no locking is needed within a color-step. This gives synchronous-like execution semantics (all color steps complete before the next begins) with good cache locality and low communication overhead. It is optimal for algorithms on bipartite graphs (two-colorable) such as collaborative filtering (users vs. movies) and topic models.

Locking Engine. This engine supports fully asynchronous, dynamic computation with vertex prioritization. It acquires distributed locks for each update function's scope using a non-blocking, callback-based protocol. To hide network latency, it uses pipelined locking: each machine maintains a pipeline of vertices for which locks have been requested. Lock acquisition requests are chained in a continuation-passing style across machines. The machine does not wait idle for a lock to arrive; instead, it processes other pipeline entries while waiting, and executes the update function as soon as all required locks have been granted. A pipeline length of 1,000 (processing 1,000 lock requests in flight simultaneously) achieves a factor-of-three reduction in runtime compared to a naive sequential locking implementation.

Pause: why pipelining works here

The key insight is that lock acquisition latency (a network round trip) and lock-holding computation (running the update function) can be overlapped for different vertices. While vertex A's lock request is in flight over the network, the machine can be executing the update for vertex B (whose locks have already arrived). This is the same pipelining principle used in CPU instruction pipelines and in high-throughput network protocols. The "pipeline" is simply a queue of in-progress lock requests at different stages of completion. The longer the pipeline, the more latency is hidden, but with diminishing returns as the pipeline becomes long enough to saturate the local compute capacity.

7. Fault Tolerance via Snapshots

A 64-machine EC2 cluster can experience machine failures during a multi-hour computation. Distributed GraphLab implements fault tolerance via distributed snapshots — checkpoints of the complete graph state from which computation can restart.

Two snapshot strategies are provided. A synchronous snapshot suspends all computation, flushes all communication channels, saves all modified data to a distributed file system, and resumes. This is correct but expensive: the pause can last tens of seconds on a large cluster.

The more elegant solution is an asynchronous snapshot, implemented as a variant of the Chandy-Lamport algorithm expressed using GraphLab's own update function mechanism. The snapshot algorithm is itself a GraphLab update function (Algorithm 5 in the paper): when a vertex is visited for snapshot, it saves its data, marks itself as snapshotted, and schedules its neighbors for snapshotting if they have not been visited yet. By prioritizing snapshot updates over algorithm updates, the snapshot propagates through the graph while computation continues. The resulting snapshot is consistent (it reflects some valid sequential execution state) without ever stopping the computation. In multi-tenant cloud experiments where a machine was artificially delayed by 15 seconds, the asynchronous snapshot incurred only a 3-second runtime penalty versus a 16-second penalty for the synchronous snapshot.

8. Applications and Evaluation

The paper evaluates Distributed GraphLab on three real MLDM applications.

Netflix Movie Recommendation (ALS). Collaborative filtering via ALS on a bipartite graph of $0.5M$ users and $99M$ rating edges. The ALS algorithm factorizes the sparse user-movie matrix $R$ as the product of two low-rank matrices: $$R \approx U \times V^T$$ where $U$ and $V$ are rank- $d$ matrices. Each vertex update solves a local least-squares problem using its neighbors' current values. GraphLab outperforms Hadoop by 40–60x and is competitive with a carefully hand-tuned MPI implementation. The chromatic engine is used (the bipartite graph is two-colorable, so no locking conflicts arise).

Video Co-Segmentation (CoSeg). A graph of 10.5 million super-pixels extracted from 1,740 high-resolution video frames, with edges connecting spatially and temporally adjacent super-pixels. The algorithm uses Loopy Belief Propagation with a Gaussian Mixture Model to label each super-pixel. GraphLab's locking engine with dynamic scheduling is the only distributed abstraction supporting the required dynamic asynchronous computation. GraphLab achieves excellent weak scaling (the runtime increases by only 11% as the problem size grows 16x from 16 to 64 machines).

Named Entity Recognition (NER). A bipartite graph of 2 million noun-phrase tokens and 200 million edges to their contexts in a large web crawl. The CoEM algorithm alternates between estimating entity types given contexts and context types given entities. GraphLab achieves a 20–30x speedup over Hadoop. An optimized MPI implementation outperforms GraphLab here due to the extremely high communication-to-computation ratio, which stresses GraphLab's current communication layer — an area the authors identify for future improvement.

On the EC2 cost dimension, GraphLab is approximately two orders of magnitude more cost-effective than Hadoop for the Netflix application — achieving the same result quality in far less time and therefore billing far fewer instance-hours.

9. Lasting Impact

Distributed GraphLab was one of the founding contributions to what became the graph-parallel paradigm for large-scale machine learning. The abstraction of update functions operating on local scopes, combined with principled consistency models and dynamic scheduling, directly influenced systems that followed.

GraphLab itself evolved into GraphX in Apache Spark (a graph processing layer built on Spark's RDD abstraction), and into PowerGraph (a successor paper by the same group addressing power-law graphs). The GraphLab company was spun off as Turi (later acquired by Apple), which developed into a suite of machine learning tools. The core ideas — data graph, update functions, consistency models — appeared in Google's TensorFlow computation graphs, in PyTorch Geometric and Deep Graph Library for graph neural networks, and in distributed training frameworks generally.

The paper's demonstration that a clean graph abstraction could match hand-tuned MPI performance on real machine learning tasks was a landmark result. It showed that the right level of abstraction for MLDM was not the flat key-value pairs of MapReduce but the graph-structured, scope-local computation model of GraphLab — a lesson that shaped an entire generation of ML infrastructure.
