WebTables: Exploring the Power of Tables on the Web

Michael J. Cafarella, Alon Halevy, Daisy Zhe Wang, Eugene Wu, Yang Zhang Proceedings of the VLDB Endowment, Vol. 1, No. 1 · PVLDB 2008
Abstract The World-Wide Web contains not only unstructured documents but also an enormous and largely untapped reservoir of structured data embedded in HTML tables. The authors extracted 14.1 billion raw HTML tables from Google's general-purpose web crawl and used statistical classification to recover an estimated 154 million tables that contain high-quality relational data. From this corpus they built the WebTables system, which supports keyword search over millions of individual databases. More importantly, they introduce a new database object — the attribute correlation statistics database (ACSDb) — that records corpus-wide co-occurrence statistics for schema elements. The ACSDb powers three novel applications: schema auto-complete (suggest likely column names given a partial schema), attribute synonym finding (automatically discover synonymous column labels across schemas), and join-graph traversal (navigate between related schemas via auto-generated join links). SchemaRank, the ranking algorithm that incorporates ACSDb coherence scores, delivers 85–98% improvement in search quality over a naive baseline.

1. Introduction: A Hidden Relational Web

When most people think of "the web," they think of free-flowing prose and hyperlinks. But embedded throughout the web's billions of pages are structured datasets masquerading as ordinary HTML. A page about the US Presidents contains a four-column table with a schema of Name, Party, Term, Vice-President. A sports site publishes a table with columns goals, assists, points, player, team. Each such table, taken alone, is a small relational database — complete with typed columns, labeled attributes, and rows of coherent tuples — and there are hundreds of millions of them.

The WebTables project asks two fundamental questions: First, can we support effective search over this enormous collection of databases? Second, what additional analytical power emerges when we study the corpus statistically, treating the collection of schemas as a dataset in its own right? The answers to both questions turn out to be surprising and rich.

Intuition — Why the Web is a Database

When a user clicks on a search-engine result that contains a table about city populations, they are effectively querying a database. The table has a schema, typed columns, and rows of facts. What the web lacks is the metadata layer that traditional databases use: no CREATE TABLE statement, no declared primary keys, no join information. WebTables reconstructs this metadata layer statistically from the raw corpus, enabling database-style operations over the entire web.

A scan of a single day's log of Google queries revealed that close to 30 million queries resulted in users clicking on pages that contained tables from the filtered relational corpus — a striking signal of demand for structured-data search, even though such search was never explicitly offered.

2. The Scale Problem: 14 Billion Tables, 154 Million Databases

The web contains roughly 14.1 billion raw HTML tables. The vast majority are not relational at all: they are used for page layout, navigation bars, advertisement grids, and other non-tabular formatting. Only about 1.1% of raw HTML tables are genuine relational tables. The challenge is identifying and extracting this small fraction accurately enough that downstream applications can trust the data.

Definition — Relational Table

A table is deemed relational if it contains high-quality relational data: consistent column types, relatively few empty cells, and a labeled header row. The WebTables system trained a statistical classifier on hand-labeled examples, achieving precision 0.41 and recall 0.81 on relational tables. The low precision is deliberate: downstream ranking algorithms can handle some non-relational tables, and losing true relations (low recall) is more costly than admitting false positives.

After applying the relational filter, a separate metadata-detection module attempts to recover the header row — the row that contains column labels. This module achieves precision 0.89 and recall 0.85. The combined pipeline produces roughly 125 million high-quality relations from the original 14.1-billion-table crawl. The automatically-chosen WebTables corpus consists of 41% true relations and contains 81% of all true relations present in the raw HTML crawl.

This corpus is five orders of magnitude larger than any previously studied HTML-table corpus. That gap in scale is not merely quantitative — it is the key that unlocks statistical analysis of schemas. For the first time, attribute names appear frequently enough that their co-occurrence patterns become statistically meaningful.

3. The Data Model and the ACSDb

Each extracted relation $R \in \mathcal{R}$ is characterized by three components: a URL and page offset $R_u$ and $R_i$ that uniquely identify it within the crawl, a schema $R_S$ which is an ordered list of attribute labels, and a set of tuples $R_T$ where each tuple is a list of data strings aligned to the schema. Empty strings appear when a cell is missing a value.

The Attribute Correlation Statistics Database (ACSDb) is derived from this corpus. It stores, for every schema $R_S$, the count $c$ of how many distinct-domain relations in $\mathcal{R}$ express that schema. (Duplicate schemas from the same domain are counted only once, to prevent a single site with many similar pages from swamping the statistics.) The ACSDb contains 5.4 million unique attribute names and 2.6 million unique schemas.

Definition — ACSDb Probability

The probability of seeing attribute $a$ in a schema is written $p(a)$ — simply the sum of all counts $c$ for schemas that contain $a$, divided by the total count across all schemas. Similarly, the conditional probability $p(a \mid b)$ counts schemas containing both $a$ and $b$ normalized by those containing $b$. These simple probabilities are the raw material for all three ACSDb applications.

The schema distribution follows a heavy-tailed power law (see Figure 3 in the paper): a small number of schemas appear extremely frequently, while the vast majority appear only once or twice. This means the corpus captures both the most common relational patterns on the web (product listings, event schedules, sports statistics) and a long tail of domain-specific schemas.

4. Relation Search and Ranking

Even the best corpus is useless without a way to query it. WebTables provides keyword search over all extracted relations — you type a query like "city population" and get back a ranked list of tables containing relevant data, not just pages that mention those words.

Three ranking algorithms of increasing sophistication are described. The simplest, naiveRank, just returns the top search-engine results for the query and extracts whatever relations those pages contain. It is fast but unreliable, because pages rank highly for reasons unrelated to their relational content. filterRank improves on this by crawling deeper into the search results until it finds $k$ actual relations, rather than stopping at the first $k$ result pages. featureRank breaks free of search-engine ordering entirely by scoring relations using a combination of per-relation features: the number of rows, the number of columns, whether the query terms hit the header row or the body, and what document-level rank the source page has.

Example — SchemaRank Coherence Score

The key insight behind the best algorithm, schemaRank, is that a good relational table should have attributes that belong together. A schema like [make, model, year, price, mileage] is coherent: all attributes co-occur frequently across many car-listing databases. A schema like [make, zipcode, gpa] is incoherent: its attributes come from different domains. The coherence score of a schema $s$ is the average of all pairwise Pointwise Mutual Information scores across its attributes:

$$\text{PMI}(a,b) = \log\!\left(\frac{p(a,b)}{p(a)\,p(b)}\right)$$

PMI is large and positive when two attributes co-occur more than chance predicts, zero when they are independent, and negative when they repel each other. SchemaRank incorporates these coherence scores into a linear regression model trained on 1,000 human-judged (query, relation) pairs. The result is an 85–98% improvement in relevance over the naive baseline.

WebTables also requires specialized index support. The standard inverted index cannot efficiently retrieve the table-specific features needed for ranking — such as whether a query term appears in the leftmost column of a relation. WebTables extends the posting list to store two-dimensional (x, y) offsets for each term occurrence, allowing the ranking function to determine whether a hit is in the header row, the leftmost column, or elsewhere.

5. Schema Auto-Complete

The first ACSDb application assists database designers. Imagine you are designing a schema for a product database and you have decided on one attribute: stock-symbol. What other columns should your table have? The schema auto-complete tool answers this by using the ACSDb to suggest the most likely co-occurring attributes.

The formal problem: given an initial set of attributes $I$, find the schema $S$ of a given size that maximizes $p(S \mid I)$ — the probability that a schema contains exactly these attributes together. The SchemaSuggest greedy algorithm (Figure 10 in the paper) iteratively adds the attribute $a$ from the universe $\mathcal{A}$ that maximizes $p(S \setminus I \mid I)$, stopping when the overall schema probability falls below a threshold $t$ (set to 0.01 in experiments).

Example — Auto-Complete in Action

When a designer enters the attribute stock-symbol, the auto-completer suggests: company, pct-of-portfolio, num-of-shares, mkt-value-of-securities, ratings. When they enter goals, it suggests: assists, points, player, team, gp. These outputs, derived purely from co-occurrence statistics over millions of web tables, are remarkably domain-appropriate. The tool gives the designer three "tries" at each input — each attempt removes the suggested schema from the ACSDb and re-runs, exposing different plausible schemas for the same topic.

Evaluation against ten expert-generated test schemas showed that by the third try, WebTables reproduced most of the correct attributes for nine of ten schemas, with an average attribute recall of 0.62 at three tries.

6. Attribute Synonym Finding

Schema matching — aligning attributes from two different databases that mean the same thing — is a pervasive challenge in data integration. Traditionally, matchers use manually constructed synonym thesauri, which are expensive to build, incomplete, and fail for domain-specific abbreviations (like hr for home run, or tel-# for telephone). The ACSDb provides a purely data-driven alternative.

The core idea is elegant: two attributes are synonymous if they (a) appear in schemas with the same context attributes, and (b) never appear together in the same schema (since duplicate columns are useless). The syn score formalizes this intuition:

$$\text{syn}(a,b) = \frac{p(a)\,p(b)}{\epsilon + \sum_{z \in \mathcal{A}} \bigl(p(z \mid a, C) - p(z \mid b, C)\bigr)^2}$$

The numerator rewards pairs whose marginal probabilities are large (common attributes that never co-occur are more surprising and thus more likely synonymous). The denominator penalizes pairs whose context distributions differ — if $a$ and $b$ appear with completely different neighbors, they probably mean different things even if they never share a schema.

Example — Synonyms Found by WebTables

Given context album, artist, the synonym finder outputs song / track. Given context sqft, it finds bath / baths, list-price / price, bed / beds. These are exactly the synonyms a human schema-matcher would use, but they are discovered automatically from co-occurrence patterns in millions of web tables. The synonym finder achieves 80% accuracy in its top-5 results, compared with 57.5% or lower for the linguistic DIRT system tested on the same inputs.

7. Join-Graph Traversal

The WebTables corpus contains 2.6 million unique schemas. A designer who finds an interesting schema — say, [last-modified, name, size] — might want to discover related schemas: schemas that deal with similar data and could plausibly be joined. But without explicit foreign-key declarations, join information must be inferred.

The basic join graph connects any two schemas that share an attribute label. Unfortunately, the raw join graph is impractically dense: a schema with a common attribute like name links to thousands of unrelated schemas (filesystem listings, address books, sports rosters, etc.). To make the graph navigable, WebTables clusters neighbors using a neighbor similarity metric:

$$\text{neighborSim}(X, Y, D) = \frac{1}{|X||Y|}\sum_{a \in X,\, b \in Y} \log\!\left(\frac{p(a,b \mid D)}{p(a \mid D)\,p(b \mid D)}\right)$$

Here $D$ is the shared attribute that connects schemas $X$ and $Y$. This measures whether $D$ plays the same role in both schemas. If it does, the schemas belong to the same cluster. The user sees a small set of coherent clusters instead of thousands of raw links, making the join graph browsable by a human designer.

Pause — Why This Is Hard

Consider the attribute size. It appears in schemas about filesystem listings ([description, name, size]), clothing ([l, m, s, xl]), and personal health ([height, size, weight]). These three domains are completely unrelated, yet a naive join graph would link them all together. NeighborSim separates them by conditioning PMI on the shared attribute, asking: given that both schemas contain size, do their other attributes co-occur? They do not, so these clusters are separated.

8. Experimental Results

The WebTables authors evaluated all components on carefully constructed benchmarks. For relation ranking, they collected 1,000 human-judged (query, relation) pairs across 30 queries, each scored 1–5 for relevance. Table 5 in the paper shows the fraction of high-scoring relevant relations in the top-$k$ results as a fraction of the optimal human-judged ordering.

At $k=10$, naiveRank achieves 0.26, filterRank achieves 0.35, featureRank achieves 0.43, and schemaRank (with ACSDb coherence) achieves 0.47. The gap widens with larger $k$: at $k=30$, schemaRank reaches 0.68 versus naiveRank's 0.34. The ACSDb-derived coherence score is the single most valuable feature.

For schema auto-complete, the tool was given three tries to reproduce ten expert-generated test schemas. By the third try, WebTables reproduced all attributes for nine of the ten schemas. For synonym finding, the system achieved an average accuracy of 80% on the top-5 results — substantially better than the linguistic DIRT baseline of 57.5%.

Caveat — Precision vs. Recall Trade-off

The relational filter was deliberately tuned for high recall (0.81) at the cost of low precision (0.41). This means the corpus includes many non-relational tables. For downstream applications that depend on the ACSDb statistics (auto-complete, synonym finding), incorrectly-admitted tables contribute incoherent schemas that should not bias the statistics — and in practice they do not, because non-relational tables lack organized attribute structure. But application designers should be aware that the raw corpus is noisy.

9. Impact and Legacy

WebTables was the first large-scale attempt to treat the web as a corpus of relational databases rather than a corpus of documents. Its intellectual legacy is substantial. The ACSDb concept — that co-occurrence statistics over a massive schema corpus can drive novel database applications — anticipated the modern wave of data-driven schema integration tools. The work directly influenced Google's "Knowledge Graph" efforts, Google Fusion Tables, and later work on table understanding in search.

The statistical approach to schema synonymy, attribute auto-completion, and join discovery are now recognized as core problems in the broader field of data lake management: the challenge of organizing and querying enormous collections of heterogeneous relational data that arrive without shared metadata. WebTables showed that the web itself, if treated statistically, can supply the missing metadata.

Perhaps most importantly, the paper established that keyword search over structured data is qualitatively different from document search, and that ranking functions for databases must incorporate schema-level signals — not just textual match quality — to deliver useful results. This insight has shaped the design of every subsequent table search system.
