HadoopDB: An Architectural Hybrid of MapReduce and DBMS Technologies for Analytical Workloads

Azza Abouzeid, Kamil Bajda-Pawlikowski, Daniel Abadi, Avi Silberschatz, Alexander Rasin Proceedings of the VLDB Endowment, Vol. 2, No. 1 · PVLDB 2009
Abstract The production environment for analytical data management is shifting: enterprises are moving from expensive proprietary high-end machines toward cheaper commodity hardware in shared-nothing clusters, often virtualized as private or public clouds. Two technologies compete for this space: MapReduce-based systems (especially Hadoop) and parallel database management systems. Parallel DBMSs are fast but do not scale gracefully to thousands of nodes, assume hardware homogeneity, and fail expensively. Hadoop is fault-tolerant and scales to thousands of nodes, but is orders of magnitude slower than parallel DBMSs on structured data workloads. HadoopDB proposes a hybrid: use Hadoop as the fault-tolerant task scheduler and network communication layer, while running single-node PostgreSQL instances inside each worker node to process data with full SQL optimization. Queries are expressed in standard SQL, translated into MapReduce jobs by an extended version of Hive, and as much processing as possible is pushed inside the per-node database engines. Benchmarks show HadoopDB approaches parallel DBMS performance while retaining Hadoop's scalability and fault tolerance.

1. The Analytical Data Management Problem

The market for analytical database software was worth $3.98 billion in 2008 and growing at over 10% annually. Enterprises increasingly make decisions from data — not instinct — and the volumes of data requiring analysis are exploding. Facebook's data warehouse was 2.5 petabytes at the time of writing. Google processes roughly 1.2 node failures per analysis job on average. It is no longer unusual for a company to load more than a terabyte of structured data per day into its analytical database system.

This scale creates a problem: the right tool for the job depends on which of three properties you care about most.

Definition — The Three Desired Properties

Performance: Analytical queries (aggregations, joins, scans over hundreds of millions of rows) should complete quickly. A factor-of-ten performance difference directly affects the cost of operating the system and the volume of analysis that can be performed per day.

Fault Tolerance: At petabyte scale with hundreds of nodes, some node will fail during almost every long query. The system must recover without restarting the entire query from scratch.

Heterogeneous Environment Tolerance: In large commodity clusters (especially on cloud infrastructure like Amazon EC2), individual nodes perform differently due to hardware variation, OS scheduling, concurrent background processes, and disk fragmentation. A system that assumes all nodes are equally fast will be bottlenecked by the slowest node — the "straggler" problem.

Parallel DBMSs excel at performance but score poorly on fault tolerance and heterogeneity. Hadoop excels at fault tolerance and heterogeneity but is dramatically slower than parallel DBMSs for structured analytical workloads. HadoopDB asks: can we build a hybrid that scores well on all three?

2. Why Not Just Use Hadoop?

Hadoop is an open-source MapReduce implementation designed for processing unstructured data at massive scale. A MapReduce job consists of three phases: Map (each node processes its local data chunk independently), Shuffle (the framework redistributes key-value pairs across nodes by key), and Reduce (each node processes the key-value pairs assigned to it). The JobTracker schedules tasks and monitors heartbeats from TaskTrackers; if a TaskTracker fails or becomes slow, the JobTracker reassigns its tasks to other nodes.

This design is excellent for fault tolerance and heterogeneity. But it was designed for unstructured text processing, and it pays a large performance tax when applied to structured relational data:

Hadoop's Performance Weaknesses on Structured Data

First, Hadoop requires data to be modeled and loaded before processing, but does not benefit from pre-loading optimizations like indexing, compression, or column-oriented storage. Second, MapReduce's one-time-query model is poorly suited to traditional business intelligence workloads with many repeated queries, since it cannot reuse partially computed results. Third, Hadoop's runtime does not use a cost-based query optimizer — each job's execution plan is fixed, and decisions like whether to use hash aggregation or sort-based aggregation must be made by hand. The net result is that on structured data benchmarks, Hadoop is typically one to two orders of magnitude slower than parallel DBMSs.

3. Why Not Just Use a Parallel DBMS?

Parallel database systems (Vertica, DBMS-X/Greenplum, Teradata) have been developed since the late 1980s and implement decades of performance research: compression, columnar storage, clustered indexes, cost-based query optimization, pipelining, and efficient join algorithms. On structured data workloads, they are dramatically faster than Hadoop.

But parallel DBMSs have three weaknesses at very large scale. First, fault intolerance: most parallel DBMSs abort and restart the entire query when a node fails, because they do not checkpoint intermediate results. At 1,000-node scale, with Google's observed failure rate of 1.2 failures per job, every long query will fail. Second, homogeneity assumption: parallel DBMSs assume all nodes run at the same speed and divide work equally. In heterogeneous environments (especially on cloud VMs), one slow node delays the entire query — Vertica saw a 170% increase in query time with a single slow node in the authors' experiments, versus less than 30% for HadoopDB and Hadoop. Third, cost: commercial parallel databases have seven-figure price tags for large installations. Hadoop and its ecosystem are open source.

Intuition — The Central Idea of HadoopDB

What if we kept Hadoop as the "outer layer" — responsible for scheduling, fault tolerance, load balancing, and inter-node data movement — but replaced Hadoop's brute-force file processing inside each node with a proper relational database engine? The database engine can use indexes, compression, and SQL optimization for the per-node work. Hadoop handles everything that crosses node boundaries. The result is a system where the fast part (intra-node SQL query processing) is done by a DBMS, and the resilient part (scheduling, recovery, data shuffling) is done by Hadoop.

4. The HadoopDB Architecture

HadoopDB sits on top of the standard Hadoop framework. Hadoop consists of two layers: the Hadoop Distributed File System (HDFS), a block-structured distributed filesystem managed by a central NameNode, and the MapReduce Framework, a master-slave architecture where the JobTracker assigns Map and Reduce tasks to TaskTrackers on worker nodes.

In a standard Hadoop deployment, each TaskTracker processes data by reading raw files from HDFS and parsing them with an InputFormat implementation. HadoopDB replaces this file-based InputFormat with a Database Connector that connects to a single-node PostgreSQL instance running on the same machine as the TaskTracker. Instead of parsing files, the TaskTracker issues a SQL query to its local PostgreSQL instance. PostgreSQL returns results as key-value pairs to the Map task, which then participates in the normal Hadoop shuffle and reduce pipeline.

The key insight is that the data — rather than being stored as raw HDFS files — is pre-loaded into PostgreSQL databases on each node. Each node holds a partition of the data. The Hadoop job still performs the inter-node coordination (shuffling keys, aggregating results), but the expensive per-node computation is done inside PostgreSQL with full access to indexes and the query optimizer.

5. The Four Components

HadoopDB extends Hadoop with four new components:

Component 1 — Database Connector

The Database Connector is a Hadoop InputFormat implementation that connects to a single-node DBMS (PostgreSQL or MySQL in the prototype) via JDBC. The MapReduce job passes it an SQL query and connection parameters. The Connector executes the SQL query against the local database and returns results as key-value pairs to the Map task. Because it extends Hadoop's InputFormat, the database looks to Hadoop like just another data source — the same as an HDFS file. The Connector was implemented for both PostgreSQL and MySQL; PostgreSQL was preferred because MySQL's join algorithms and aggregation optimizers were inadequate for the benchmark queries.

Component 2 — Catalog

The Catalog maintains metadata about the databases on each node: connection parameters (JDBC driver, host, credentials), data partitioning information (which partition of which table is on which node), replica locations, and partitioning properties. In the current implementation, the Catalog is an XML file stored in HDFS and accessed by the JobTracker and TaskTrackers. The authors plan to evolve it into a separate metadata service resembling Hadoop's NameNode.

Component 3 — Data Loader

The Data Loader handles the non-trivial task of getting data from HDFS into the per-node PostgreSQL instances. It has two sub-components. The Global Hasher executes a MapReduce job that reads raw data from HDFS and repartitions it into as many parts as there are nodes, using a consistent hash function. This ensures that all records with the same partition key end up on the same node — enabling co-located joins. The Local Hasher then takes each global partition, breaks it into smaller chunks (up to the maximum chunk size, e.g., 1 GB), and bulk-loads each chunk into a separate PostgreSQL database on the node using the COPY command. Clustered indexes on join/partition keys are created for each chunk.

Component 4 — SQL-to-MapReduce-to-SQL (SMS) Planner

The SMS Planner is the query translation layer. It extends Hive — Facebook's open-source SQL-to-MapReduce translator — to push as much SQL processing as possible inside the per-node databases. Standard Hive translates SQL into a DAG of relational operators, then wraps the entire DAG in a MapReduce job where data processing happens in the Map and Reduce phases by iterating over raw files. The SMS Planner modifies this process in two passes: it first identifies which operators can be executed inside the database (filters, projections, partial aggregations, co-located joins) and constructs SQL queries for them; then it wraps the remaining operators (final aggregations, cross-node joins) in the Hadoop Map and Reduce phases. The per-database SQL is regenerated from the relational operator tree and passed to the Database Connector.

6. The SMS Query Planner in Detail

Consider a simple analytical query:

Example — GroupBy Query Translation

The query SELECT YEAR(saleDate), SUM(revenue) FROM sales GROUP BY YEAR(saleDate) is processed as follows. Hive parses it into an Abstract Syntax Tree, constructs a logical query plan (a DAG of operators: TableScan → Select → GroupBy → ReduceSink → GroupBy → FileSink), and optimizes it. The SMS Planner then inspects this DAG.

If the sales table is partitioned by YEAR(saleDate), then the entire GroupBy can be pushed inside each PostgreSQL instance: each node computes its local aggregate, and a single Reduce task merges the partial results. The Map phase just passes each local aggregate through. If the table is not partitioned by saleDate, the local database still computes partial aggregates (SELECT YEAR(saleDate), SUM(revenue) FROM sales GROUP BY YEAR(saleDate)), and the Reduce phase performs the final merge. In either case, PostgreSQL's optimizer handles the local computation efficiently, using indexes if available.

For join queries, if both tables are partitioned on the join key, the entire join can be pushed into each PostgreSQL instance — zero inter-node data movement is required. If they are not co-partitioned, the SMS Planner falls back to Hive's standard approach (a Reduce-side join with a full data shuffle). This co-location optimization is one of the most important performance advantages of HadoopDB over standard Hive: when data is partitioned appropriately, joins that would require shuffling gigabytes across the network are replaced by local index-join operations inside PostgreSQL.

7. Data Loading

Loading data into HadoopDB is more expensive than loading into Hadoop, because data must be partitioned, chunked, and indexed before analysis can begin. For the UserVisits dataset (20 GB per node, partitioned by destinationURL), the loading process broke down as follows: global repartitioning by the Global Hasher took about 14,000 seconds — by far the dominant step. Local partitioning into 1 GB chunks took 2,500 seconds. Bulk loading via COPY took 5,200 seconds. Creating clustered indexes took 7,100 seconds. Vacuuming (PostgreSQL maintenance) took 1,200 seconds. Total load time was approximately 30,000 seconds.

This upfront cost is amortized across all queries run against the dataset. Because HadoopDB's query performance is typically 5–10x better than Hadoop's on structured data, the load time is recovered after a relatively small number of queries. The authors calculated that for the Join task (where HadoopDB outperforms Hadoop by a factor of 10), just one query run recovers the load time cost.

Caution — Load Time Is a Real Cost

HadoopDB's load time is approximately 10 times longer than Hadoop's (which loads data simply by storing files in HDFS). For workloads with many different datasets, each queried only once or twice, HadoopDB's load overhead may not be recoverable. HadoopDB is best suited for workloads where data is loaded once and queried many times — the traditional data warehouse scenario.

8. Benchmark Results

The authors evaluated HadoopDB against Hadoop (hand-coded and Hive-coded), Vertica (a column-store), and DBMS-X (a commercial row-store parallel database) using a five-task benchmark run on Amazon EC2 "large" instances (7.5 GB memory, 2 virtual CPUs, 850 GB disk) at cluster sizes of 10, 50, and 100 nodes.

Grep task: A full scan to find all records matching a three-character pattern. Since no system has an index on the pattern field, all systems are I/O-limited. HadoopDB slightly outperforms Hadoop because PostgreSQL handles I/O more efficiently than Hadoop's raw file parsing. Both are outperformed by Vertica and DBMS-X, which compress their data and thus have much less to scan.

Selection task: A simple predicate on an indexed column (pageRank > 10 from a Rankings table). HadoopDB outperforms Hadoop significantly because it can use PostgreSQL's clustered index on pageRank to avoid scanning the entire table. Vertica and DBMS-X also beat Hadoop for the same reason.

Aggregation tasks: Computing total ad revenue grouped by a prefix of the source IP address (many groups) or the full source IP (very many groups). For the small-group query, HadoopDB outperforms Hadoop by a factor of roughly 2–3x because PostgreSQL uses hash aggregation optimally (the hash table fits in memory). For the large-group query, HadoopDB outperforms Hadoop by a larger factor. Both lag behind Vertica, which benefits from column-oriented storage (only 2 of 20 UserVisits attributes need to be read for this query).

Join task: Finding the average pageRank of pages visited from the top-revenue source IPs, requiring a join between UserVisits (partitioned by destinationURL) and Rankings (partitioned by pageURL). Since both tables are co-partitioned on the join key, HadoopDB pushes the entire join into PostgreSQL on each node. The result is remarkable: HadoopDB's query time is comparable to DBMS-X and Vertica at all cluster sizes, and both dramatically outperform Hadoop (which must perform a full cross-network shuffle to join the tables). This is HadoopDB's strongest result and best illustrates the architectural advantage of co-located in-database joins.

Intuition — Why Co-located Joins Are the Key Result

Hadoop's join is slow because joining two tables at different nodes requires sending one table's data across the network to the other. At 20 GB per node and 100 nodes, this means shuffling up to 2 TB of data over the network — which takes thousands of seconds. HadoopDB, by pre-partitioning both tables on the join key, ensures that matching rows from both tables always reside on the same node. The join never touches the network. PostgreSQL's clustered index on the join key makes the local join fast. This is the architectural principle: push data movement costs into the load phase, where they are paid once, rather than into every query.

UDF Aggregation task: Counting inward links for each URL in an HTML document corpus, requiring arbitrary text parsing. Here Hadoop outperforms HadoopDB because the Documents table contains full HTML documents, which are naturally stored as merged files in HDFS — Hadoop processes them efficiently as blobs, while HadoopDB's TextDataType and external-call approach adds overhead. This result illustrates HadoopDB's one area of relative weakness: workloads that mix structured and unstructured data at the storage level favor pure Hadoop's flexible file processing.

9. Fault Tolerance and Heterogeneous Environments

The authors tested fault tolerance by terminating a TaskTracker at the 50% completion point of a 10-node aggregation query. Hadoop and HadoopDB both recovered gracefully: the JobTracker detected the failure, reassigned the failed node's tasks to other TaskTrackers, and completed the query with less than 40% slowdown. Vertica experienced a 135% increase in query time because it had to abort and restart the query from scratch.

For heterogeneity testing, a background I/O-intensive job was run on one node to simulate a consistently slow "straggler." Hadoop and HadoopDB again performed similarly: both handled the straggler by speculatively re-executing its tasks on other nodes, resulting in less than 30% slowdown. Vertica experienced a 170% increase in query time because it waited for the straggler to complete its assigned work.

One subtlety: HadoopDB's speculative re-execution is slightly less effective than Hadoop's in heterogeneous environments. When a TaskTracker is assigned a task previously assigned to a straggler, standard Hadoop can copy the data block from a replica. HadoopDB's TaskTracker must instead connect to the straggler's or replica's PostgreSQL database, which may involve an extra round-trip to process a straggler's unprocessed chunks. The authors plan to address this by modifying the task scheduler to prefer connecting to replica databases rather than straggler databases.

10. Impact and Legacy

HadoopDB appeared at a moment of intense debate in the database community. DeWitt and Stonebraker had published a provocative blog post arguing that MapReduce was "a major step backwards" from relational databases, and the MapReduce community had responded that parallel databases were too expensive and brittle. HadoopDB offered an empirical answer: both sides were partly right, and a hybrid could take the best of both.

The paper's direct descendants include Amazon Redshift (which uses a parallel DBMS architecture on cloud hardware), Google BigQuery (which separates storage from compute to get cloud elasticity with DBMS-style SQL optimization), Spark SQL (which adds SQL optimization layers on top of the Spark distributed computation framework, analogously to HadoopDB's SMS planner on Hadoop), and Apache Hive itself, which has been dramatically improved since 2009 to include cost-based optimization, vectorized execution, and better SQL support.

The architectural principle that HadoopDB articulated — push as much processing as possible into the storage layer, use a resilient distributed framework only for inter-node coordination — is now the standard design for analytical systems. The modern "lakehouse" architecture (Databricks Delta Lake, Apache Iceberg, AWS Lake Formation) is in many ways an evolution of this principle: SQL-optimized query engines running over distributed object storage, with columnar formats providing the index-like benefits that HadoopDB got from PostgreSQL.

HadoopDB also made a methodological contribution: it was one of the first papers to benchmark analytical systems on public cloud infrastructure (Amazon EC2), acknowledging that cloud elasticity and commodity hardware costs are first-class concerns for system designers — not just performance on dedicated server clusters.
