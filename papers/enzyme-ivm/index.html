Enzyme: Incremental View Maintenance for Data Engineering

Ritwik Yadav, Supun Abeysinghe, Min Yang, Jeffrey Helt, Manuel Ung, Yuhong Chen, Melody Hu, William Wei, Yiming Yang, Tom van Bussel, Sourav Chatterji, Indrajit Roy, Paul Lappas, Yannis Papakonstantinou, Tahir Fayyaz, Bilal Aslam, Ross Bunker, Michael Armbrust, Shrikanth Shankar Databricks, Inc. & Google, Inc. — SIGMOD Companion 2026, Bengaluru, India
Abstract. Materialized views (MVs) are physically stored query results used to accelerate analytical queries and power ETL pipelines. Keeping a materialized view consistent as its source tables change is the incremental view maintenance (IVM) problem — studied for decades but rarely solved end-to-end in industrial systems. This paper describes Enzyme, Databricks's production IVM engine. Enzyme automatically selects between incremental refresh and full recomputation for each view in a pipeline, using a cost model grounded in historical execution data. Deployed across thousands of production pipelines, it has cut daily CPU consumption by billions of seconds. Built on Apache Spark primitives (Delta Lake, Catalyst), Enzyme handles arbitrary compositions of SQL operators — including joins, aggregations, and window functions — without requiring any manual tuning from users.

1. Introduction

A materialized view is a database object that caches the result of a query in physical storage. Unlike a standard (virtual) view — which re-runs its defining query on every access — a materialized view is computed once and stored. Subsequent queries read the stored result, making them dramatically faster. The trade-off is staleness: the stored result must be refreshed as the underlying source data changes.

Definition: Materialized View

A materialized view (MV) is a named, persistently stored query result. It is defined by a query $Q(T_1, \ldots, T_n)$ over base tables $T_1, \ldots, T_n$. The MV must be periodically or continuously refreshed to reflect changes to those base tables. A full refresh re-executes $Q$ from scratch; an incremental refresh computes only the delta.

Modern data architectures make MVs indispensable. The medallion architecture — used widely in data lakehouses like Databricks — organizes data into three layers:

  • Bronze — raw, as-landed data with metadata.
  • Silver — cleaned, merged, and conformed records ready for analytics.
  • Gold — denormalized, read-optimized aggregates for reporting and ML.

MVs appear primarily in the Silver and Gold layers, transforming data as it flows downstream. As the AI era has driven exponential data growth, the cost of full recomputation on every pipeline run has become prohibitive. Incremental refresh — processing only what changed — is now a necessity, not a nice-to-have.

Intuition: Why IVM Is Hard

For a simple filter or projection, IVM is trivial: just apply the same filter to the incoming changes. But once you introduce joins, aggregations, or window functions, correctness becomes subtle. A single new row in an Orders table can change aggregate values for hundreds of customer groups; a deletion can turn an outer-join row from matching to null-padded. Non-deterministic functions like rand() or current_timestamp() break the assumption that you can re-evaluate an expression on old data and get the same answer. These challenges compound when views depend on other views in a pipeline DAG.

Most existing IVM systems fall short in at least one of four ways: (1) limited SQL operator coverage (no window functions, no outer joins); (2) reliance on secondary indexes that lakehouses do not provide; (3) no automated cost-based strategy selection; or (4) per-view tuning that burdens engineers. Enzyme addresses all four.

2. Background: Materialized Views at Databricks

On Databricks, MVs are backed by Unity Catalog-managed Delta tables. Users define MVs either inside a Spark Declarative Pipeline (refreshed when the pipeline runs) or as standalone DBSQL objects (refreshed on a schedule or when source tables change). Delta Lake's ACID transactions guarantee readers always see a consistent, fully committed MV state — partial refreshes are never visible.

Internally each MV has two parts: a backing table (which stores user data plus Enzyme's internal metadata columns) and a top-level view (which hides the metadata and exposes only user-facing columns). This split is critical: it lets Enzyme add auxiliary columns — for example, storing both SUM(x) and COUNT(*) when the user requested only AVG(x) — without changing the schema the user sees.

2.1 Running Example

The paper uses the following MV as a running example throughout. It computes the average order amount per region, filtered to three regions, refreshing every hour: 

CREATE MATERIALIZED VIEW region_avg_sales
SCHEDULE EVERY 1 HOUR
AS
SELECT
  c.region,
  AVG(o.amount) AS avg_order_amount
FROM
  Customers c
  JOIN Orders o ON c.customer_id = o.customer_id
GROUP BY c.region
HAVING c.region IN ('us-east', 'us-west', 'asia');
Example: Reading This Query

This query joins Customers and Orders on customer_id, groups by region, computes the average amount per group, and keeps only the three named regions. The result is one row per region with the average order size. Every hour, Enzyme must update this result in response to new orders, modified customer records, or both.

2.2 Spark Primitives Enzyme Uses

Enzyme applies computed changes to an MV's backing table using two Spark/Delta Lake operations:

  • MERGE INTO — a conditional upsert. Given a source table of changes, it matches source rows to target rows on a key and applies insert, update, or delete actions. Enzyme uses this to update aggregate rows in place (e.g., bumping a running sum without rewriting unaffected groups).
  • REPLACE WHERE — atomically deletes all rows matching a predicate and inserts a new set of rows. Simpler than MERGE INTO, it works well for partition-level overwrites.

2.3 Delta Lake Features Enzyme Relies On

Four Delta Lake capabilities are central to Enzyme's design:

Row Tracking

Each row in a Delta table receives a stable, unique identifier at insertion time, preserved across updates. Enzyme uses these IDs as fine-grained row-level lineage handles: it can pinpoint exactly which output rows must be deleted or updated when a specific input row changes, without scanning unrelated data.

Change Data Feed (CDF)

Delta's CDF tracks row-level changes between two table versions. It returns one row per insertion or deletion, augmented with a _change_type metadata column encoded as $+1$ (insert) or $-1$ (delete). An effectivized changeset is the most compact form: redundant insert-then-delete pairs for the same row cancel out, leaving only the net change.

Deletion Vectors

Instead of rewriting entire Parquet files on every delete or update (copy-on-write), deletion vectors mark rows as logically removed without rewriting. This reduces write amplification — the extra I/O caused by rewriting large files to change a few rows — at the cost of slightly more work during reads (a merge step filters out deleted rows).

Time Travel

Every DML operation on a Delta table creates a new version. Time travel lets Enzyme read the table as it existed at any past version number or timestamp. This is essential for IVM: Enzyme needs the before state of a table to compute what changed.

3. Formalizing Incremental View Maintenance

This section unpacks the math that underlies Enzyme's approach. The core idea is elegant: instead of re-running the whole query, derive a delta query $\Delta Q$ that computes only what changed.

3.1 The Basic Problem Statement

Suppose an MV stores the result of a query $Q(T_1, \ldots, T_n)$ over base tables $T_1, \ldots, T_n$. After changes arrive, the updated tables become $T_1', \ldots, T_n'$. We want the refreshed MV to equal $Q(T_1', \ldots, T_n')$.

The incremental approach says: compute a change $\Delta Q$ and apply it to the existing MV:

$$Q(T_1', \ldots, T_n') \;=\; Q(T_1, \ldots, T_n) \;\oplus\; \Delta Q$$

Here $\oplus$ means "apply the incremental update" — a combination of row insertions and deletions. The per-table change is $\Delta T_i = T_i' - T_i$, where the subtraction is bag (multiset) difference. Each row in $\Delta T_i$ carries a $+1$ or $-1$ tag indicating whether it was inserted or deleted.

Intuition: Why Not Just Diff the Outputs?

A naive approach: run $Q$ on both old and new inputs, then diff the outputs to get $\Delta Q = Q(T') - Q(T)$. This is always correct for deterministic queries, but it evaluates $Q$ twice, which is at least as expensive as a full recompute and often worse (you need both the old and new states of the data simultaneously). Enzyme's key insight is to push the delta inside the query plan, operator by operator, so that most of the work touches only the changed rows rather than the full tables.

3a. Operator-Level Delta Plan Construction

Enzyme works by traversing the logical query plan — a tree of relational operators — from the leaves (base tables) upward. At each operator node, it applies a specific delta rule that expresses how the change to that operator's output relates to changes in its inputs. The delta fragments compose bottom-up into a complete incremental plan for the whole query.

Formally, for any operator node $\phi$ with child $\psi$, we want $\Delta\phi$ such that:

$$\phi(\psi') \;=\; \phi(\psi \oplus \Delta\psi) \;=\; \phi(\psi) \oplus \Delta\phi$$

Computing $\Delta\phi$ may require access to the old state $\psi$, the new state $\psi'$, and the change $\Delta\psi$. Enzyme propagates all three explicitly for efficiency. Let's go through each operator type.

Filter and Projection — the easy ones

For a filter $\sigma_\theta$ (which keeps rows satisfying predicate $\theta$) and a projection $\pi_{a_1,\ldots,a_k}$ (which selects columns), the delta passes straight through:

$$\Delta(\sigma_\theta(T)) \;=\; \sigma_\theta(\Delta T)$$

$$\Delta(\pi_{a_1,\ldots,a_k}(T)) \;=\; \pi_{a_1,\ldots,a_k}(\Delta T)$$

Intuitively: since filter and projection operate on each row independently and have no memory of other rows, you just apply the same operation to the incoming changes. A new row that satisfies the filter contributes a new output row; a deleted row that satisfied it removes an output row.

Aggregation — the group-by update

Aggregation is harder because each output row summarizes an entire group of input rows. Let $G_{k, agg}$ denote a group-by on key $k$ with aggregate function $agg$. Enzyme's delta rule is:

$$\Delta\!\left(G_{k,\,agg}(T)\right) \;=\; \pi^{-}\!\left(G_{k,\,agg}(T \ltimes_k \Delta T)\right) \;+\; \pi^{+}\!\left(G_{k,\,agg}(T' \ltimes_k \Delta T)\right)$$

Intuition: Reading the Aggregation Delta

The $\ltimes_k$ is a semijoin: it keeps only those groups (distinct values of $k$) that appear in the changeset $\Delta T$. This is the key efficiency win — instead of re-aggregating every group, we touch only the groups actually affected by the change.

  • $\pi^-$ extracts the old aggregate values for those groups (from $T$), marking them as deletions.
  • $\pi^+$ extracts the new aggregate values for those groups (from $T'$), marking them as insertions.
The net effect: old aggregate rows are removed, new ones inserted, for only the affected groups. Unaffected groups are untouched.

Joins — the most complex case

For an inner join $L \bowtie R$, the delta rule is:

$$\Delta(L \bowtie R) \;=\; (\Delta L \bowtie R) \;+\; (L' \bowtie \Delta R)$$

Intuition: Why Two Terms in the Join Delta?

Think about it concretely. If new orders arrive ($\Delta R$), each new order must be joined against all current customers ($L'$, i.e., customers after their own changes). That gives the second term. Conversely, if customers change ($\Delta L$), each changed customer must be joined against all original orders ($R$). That's the first term. The join delta is the union of both effects. This "double scan" is unavoidable for joins and is why joins are the costliest operator to maintain incrementally.

Outer joins are harder still. They can be decomposed into an inner join plus anti-joins (to handle the null-padded rows that appear when one side has no match). This is theoretically clean but can degrade badly when many outer joins are composed. Enzyme uses specialized rules for the most common patterns (equi-joins, primary-foreign key joins) to avoid this performance cliff.

Window Functions

Window functions with a PARTITION BY clause behave like aggregations: only the partitions touched by $\Delta T$ need recomputation. Window functions with an ORDER BY and no PARTITION BY are more expensive — a single change can shift the rank of many rows — and Enzyme falls back to partition overwrite or full recompute in those cases.

The Running Example: Delta Plan Expansion

For the region_avg_sales MV, the query is $\sigma\!\left(G_{\text{region},\,\text{AVG}(\text{amount})}(C \bowtie O)\right)$. Applying the delta rules bottom-up, writing $C$ for Customers and $O$ for Orders:

$$\Delta Q \;=\; \sigma\!\left(\pi^-\!\left(G(C \bowtie O) \ltimes \Delta(C \bowtie O)\right) \;+\; \pi^+\!\left(G(C' \bowtie O') \ltimes \Delta(C \bowtie O)\right)\right)$$

where $\Delta(C \bowtie O) = (C \bowtie \Delta O) + (\Delta C \bowtie O)$. In plain English: find the regions affected by any order or customer change; delete the old average for those regions; compute and insert the new average. All other regions are untouched.

3b. Applying Computed Changes Back to the MV

Once $\Delta Q$ is computed, Enzyme must apply the resulting insertions and deletions to the MV's backing table. To do this efficiently it needs to know which specific rows in the MV correspond to which output tuples.

Enzyme solves this by threading a unique row_id through every stage of the query plan:

  • At the base table level, Delta Lake's Row Tracking provides stable row IDs.
  • At a join, the output row ID is derived by combining the IDs of the left and right input rows (e.g., a hash-combine).
  • At an aggregation, the output row ID is the grouping key (since there is exactly one output row per distinct key value).

With these IDs, applying $\Delta Q$ reduces to: identify row IDs marked for deletion and remove them; then insert the new rows marked as additions. Delta Lake's ACID semantics ensure this happens atomically.

3c. Handling Non-Determinism

The delta rules above assume that re-evaluating an expression on old inputs gives the same result it gave when those rows were originally inserted. Most SQL expressions satisfy this — but not all.

The Non-Determinism Problem

Consider a query with rand(): 

SELECT a, rand() AS r FROM T WHERE r > 0.5

When a row is deleted from T, the naive delta rule would re-evaluate rand() for that row. But rand() is non-deterministic — it returns a different value each call. The newly computed random value might not satisfy r > 0.5, so the deletion would be skipped, leaving a stale row in the MV. Correctness breaks silently.

Non-determinism appears in many forms beyond explicit randomness:

  • collect_set / collect_list — output order not guaranteed.
  • Floating-point SUM / AVG — rounding differences between evaluation orders produce different results.
  • Window functions with ties in their ORDER BY — tie-breaking is arbitrary.
  • current_timestamp() — depends on wall-clock time.

Enzyme's strategy is layered: first try a semantic-preserving rewrite to eliminate the non-determinism (e.g., inject a deterministic local sort before collect_set); if that is not possible, apply a specialized incrementalization technique tailored to the pattern; as a last resort, fall back to full recomputation for that view.

3d. Optimizations and Special Cases

Temporal Filters

A very common pattern in production ETL is a rolling-window filter: WHERE date >= current_date() - INTERVAL 30 DAYS. This is non-deterministic because current_date() changes on every refresh. Enzyme handles it by capturing the previous and current refresh timestamps and computing three components of the delta:

$$\Delta(\sigma_{f(t)}(T)) \;=\; \pi^-\!\sigma_{\lnot f(\text{curr}) \land f(\text{prev})}(T) \;+\; \pi^+\!\sigma_{\lnot f(\text{prev}) \land f(\text{curr})}(T) \;+\; \sigma_{f(\text{curr})}(\Delta T)$$

Intuition: The Three Parts of the Temporal Delta

Think of a 30-day window sliding forward each hour. Three things happen:

  1. Rows exiting the window — they satisfied the filter last time ($f(\text{prev})$) but no longer do ($\lnot f(\text{curr})$). They must be deleted.
  2. Rows entering the window — they didn't satisfy the filter last time but now do. They must be inserted.
  3. New rows within the window — rows from $\Delta T$ that fall within the current window. They must be inserted too.

Leveraging Materialized Data

For MVs whose top-level operator is an aggregation or window function, the previous aggregate result is already stored in the MV. Enzyme exploits this to skip recomputing the "before" aggregate from scratch. Instead, it:

  1. Computes the join changeset to find which grouping keys are affected.
  2. Deletes all MV rows whose grouping key appears in the changeset (using the stored row to get the old value).
  3. Recomputes and inserts the new aggregate for only those keys.

For SUM and COUNT, Enzyme can go further: rather than delete-and-reinsert, it maintains incremental adjustments (a running sum of deltas) and uses MERGE INTO to update the aggregate row in place. Enzyme stores SUM(x) and COUNT(*) in the backing table to support AVG(x) incrementally.

Partition Overwrite

When both source tables and the MV are partitioned on the same columns (commonly a date column), and the query does not aggregate across partition boundaries, Enzyme can refresh at the partition level rather than the row level. This is simpler and often faster: instead of computing fine-grained row deltas, it just overwrites the affected partitions entirely. The cost model decides which granularity to use.

4. System Architecture

Enzyme's architecture processes each MV refresh through six sequential stages: Normalization → Fingerprinting → Decomposition → Incremental Plan Generation → Costing → Execution. Each stage is a separate, composable component that can be reasoned about independently.

4a. Normalization

Enzyme's entry point is a Spark Catalyst logical plan — a tree representation of the query. Catalyst is the query optimizer used by Spark SQL and DataFrame API. Because Enzyme intercepts at the logical plan level, it works with SQL queries, Python DataFrames, and PySpark programs equally.

The normalizer simplifies the logical plan before Enzyme's delta rules are applied. Key transformations include:

  • Inlining common table expressions (CTEs) so the plan is a tree rather than a DAG.
  • Merging and simplifying filter predicates.
  • Collapsing unnecessary projections.
  • Eliminating redundant operations.

Crucially, Enzyme normalizes before full Catalyst optimization. Some Catalyst optimizations — like timestamp substitution and empty-relation propagation — would destroy information Enzyme needs for correct incrementalization. The normalized plan is a "sweet spot" between raw and fully optimized.

4b. Query Fingerprinting

If the definition of an MV changes, Enzyme must discard the existing stored results and perform a full recomputation. A fingerprint is a stable hash of the normalized plan that identifies the MV's semantic content. When the fingerprint changes, Enzyme knows a full refresh is needed.

Why Not Just Compare Source Code?

Source code comparison fails in both directions. A Python refactor can change source without changing semantics — Enzyme should not trigger a full recompute. Conversely, a change to an external parameter or a referenced view can change semantics without touching source code. Operating on the normalized plan captures the true semantic content: semantics-preserving changes leave the plan identical; semantic changes alter it.

The fingerprinter applies additional canonicalization on top of normalization: standardizing the order of commutative operators (joins, unions) and the order of operands in commutative expressions. For Python UDFs, Enzyme fingerprints the Python bytecode of the function and its transitive dependencies (imported libraries, nested calls), ensuring that a library upgrade triggers recomputation.

Fingerprint stability is a practical challenge: when Enzyme itself is upgraded and its normalizer changes, fingerprints might change even though user queries did not. This would spuriously trigger full recomputes for every MV during a system upgrade. Enzyme solves this with multi-versioned fingerprints: before deploying normalizer changes, a new fingerprint version is registered that maps the new plan representation back to the existing stored fingerprint.

4c. Decomposition and Technique Enablers

Before the incremental plan generator runs, the decomposer transforms the normalized plan to make incremental computation possible or more efficient. These transformations, called technique enablers, exploit the backing-table / top-level view split of Databricks MVs.

The most important enabler is aggregate decomposition: an MV containing $\text{AVG}(x)$ is internally augmented with columns for $\text{SUM}(x)$ and $\text{COUNT}(*)$. These are incrementally computable; the top-level view then exposes only the derived $\text{AVG}$ to users.

Similarly, the decomposer rewrites FIRST(x) to MIN(x) when an ordering guarantee makes them equivalent, and it propagates grouping/partition keys explicitly to the top of the plan so the plan generator can identify them without pattern-matching deeper in the tree.

4d. Incremental Plan Generator

The plan generator implements the delta rules from Section 3 as a recursive visitor over the query plan tree. Traversing bottom-up, at each node it produces a delta plan: a triple of (pre-state, post-state, delta). These triples compose at each parent node according to the operator-specific delta rule until the root of the tree yields $\Delta Q$.

Effectivization — collapsing redundant insert/delete pairs for the same row — is applied selectively at intermediate nodes. It is optional but reduces downstream computation when change volume is large and contains many cancellations.

For MVs with top-level aggregations, the generator applies an extra optimization: it only needs the grouping keys (not full row images) to identify which aggregate rows to delete, and it only needs the after-image for insertions. This avoids materializing the entire pre-state of affected groups, which can be very expensive for complex aggregations.

4e. Cost Model

For every MV refresh, Enzyme generates multiple candidate plans (several incremental strategies plus a full-recompute baseline) and selects the cheapest one. This requires a cost model that accurately predicts execution time.

Standard database cost models often work poorly for this problem — they are tuned for query planning under stable statistics, not for estimating the cost of incremental plans with highly variable changeset sizes. Enzyme's cost model uses an empirical approach:

  • Model total refresh cost as the sum of CPU times across key physical operators (joins, aggregates, window functions, shuffles, file scans, file writes).
  • For each operator in a candidate plan, find structurally similar past executions via normalized physical plan matching.
  • Derive expected CPU time from observed metrics of those past executions, implicitly capturing data skew, spilling, and dynamic pruning.
  • When no historical data is available, fall back to default parameters from large-scale query logs.
Pipeline-Aware Cost Modeling

A crucial insight from production deployment: you cannot optimize each MV in isolation. Even if a single MV would be cheaper to fully recompute, performing an incremental refresh produces a smaller changeset that propagates downstream — making all dependent MVs cheaper too. Enzyme's cost model accounts for this by summing costs across the entire pipeline DAG, not just the current view. A locally suboptimal choice can be globally optimal.

4f. Refresh Execution

Enzyme submits incremental plans to Apache Spark for execution. It operates entirely on Spark logical plans, leaving physical planning and execution to Spark's own optimizer (Catalyst) and execution engine (Photon/Tungsten). This means Enzyme automatically benefits from all ongoing Spark performance improvements.

Before execution, Enzyme tunes Spark configuration parameters based on expected workload characteristics:

  • Hints the optimizer toward broadcast vs. shuffle joins based on historical changeset sizes.
  • Adjusts broadcast thresholds dynamically.
  • Caches intermediate results that are used multiple times within a single refresh (e.g., the input changeset consumed by both the delete and insert phases of an aggregation update).

Choosing the update mechanism: Enzyme picks between REPLACE WHERE and MERGE INTO based on plan structure. For aggregate MVs with in-place update support, MERGE INTO is used to update running totals without deleting and re-inserting rows. For other cases, REPLACE WHERE handles an atomic delete-then-insert (requiring effectivization first so a row does not appear in both sets).

Transactional provenance: Enzyme stores metadata about each refresh — query fingerprint, source table versions, timestamps — as part of the MV's Delta transaction. Because Delta's ACID semantics guarantee atomicity, the provenance and the data are always consistent: either both update or neither does.

5. Operational Experience & Lessons Learned

Ensuring Correctness at Scale

Enzyme uses two complementary correctness frameworks. A Random Query Generator (RQG) produces random schemas, synthetic data, and SQL queries covering complex operator combinations. For each generated query, Enzyme creates an MV, applies random changes, and verifies that the incremental result matches a full recomputation.

In production, an A/B correctness testing system continuously compares MV contents against their defining queries on live data. This dual approach catches bugs that only manifest under specific data distributions or timing conditions that synthetic tests cannot anticipate.

Reliability Through Fallback

Enzyme automatically falls back to full recomputation whenever the incremental planner raises an exception or produces a plan that fails a validation check. The system monitors these fallbacks as signals for underlying bugs. Integration with Databricks's Health Mediated Release framework enables automatic rollback to the previous Enzyme version when a refresh fails after an upgrade.

Enzyme as a Spark Stress Test

Incremental plans exercise execution paths that ordinary user queries never touch. As a result, Enzyme has become an effective stress test for uncovering optimizer and execution bugs in Spark itself — bugs that production user queries would not have revealed.

Performance Challenges in Practice

Several real-world issues arose that the theory did not anticipate:

  • Dynamic file pruning failures: Spark's dynamic file pruning optimization sometimes did not activate for incremental plans, causing full table scans instead of targeted reads. Enzyme worked around this by reformulating affected plans to use explicit semijoins, giving Spark more pruning hints.
  • Driver out-of-memory during optimization: Highly complex incremental plans caused Spark's driver to run out of memory while building its optimization search space. Enzyme addressed this by adding rules to the normalizer that simplify plan structure, and by reformulating certain delta formulas to reduce plan complexity.
  • Fingerprint stability: Upgrading Scala from version 2.12 to 2.13 changed how objects were hashed, potentially altering fingerprints for many MVs. The multi-versioned fingerprint system absorbed this without triggering unnecessary recomputes.

6. Experimental Evaluation

6.1 Benchmark and Setup

Enzyme is evaluated on the TPC-DI benchmark (Transaction Processing Council Data Integration), specifically designed for ETL and incremental processing systems. TPC-DI includes built-in incremental update batches, covers realistic operational domains (Customer, Account, Trade, Company, Security, Financial, Market), and mixes append-only and CDC-style changes.

The experimental pipeline mirrors a real medallion architecture:

  • Append-only streaming tables for event streams: TradeHistory, DailyMarket, Financial.
  • CDC streaming tables for entity records that mutate over time: Customer, Account, Company, Security.
  • Materialized views in the Silver/Gold layers performing multi-table joins, aggregations, and enrichment: DimCustomer, DimAccount, DimSecurity, FactHoldings, FactMarketHistory.

Tests were run at scale factors 1,000, 2,000, 5,000, and 10,000 using Databricks Serverless (AWS c7g.2xlarge instances, 8 CPU cores, 16 GiB RAM each, capped at 64 executors). The comparison system (referred to as CV-IVM, a leading cloud vendor's IVM offering) was also run at the 10,000 scale factor.

6.2 Key Results

Headline Numbers
  • Enzyme successfully incrementalizes 100% of TPC-DI workloads (full operator coverage).
  • 6 out of 8 datasets see substantial speedup over full recomputation when incremental refresh is applied.
  • The cost model makes the optimal decision in 7 of 8 cases (87.5% accuracy).
  • Speedups are consistent across scale factors — efficiency scales with data volume.
  • Against CV-IVM at scale factor 10,000: Enzyme incrementalizes more datasets (CV-IVM could not handle DimAccount and FactMarketHistory due to unsupported operators) and achieves better performance on datasets both support.

6.3 Notable Cases

FactMarketHistory computes 52-week highs and lows per stock symbol over roughly two years of historical data. Each refresh requires scanning a full year of records per symbol, causing high memory pressure. This is a hard case for IVM, and speedups dip at larger scale factors due to disk spilling.

Prospect is a case where incremental refresh loses: more than 95% of prospect rows are rewritten in each batch (the column SK_RecordDateID updates for every persisting record). When nearly all rows change, the overhead of computing and applying fine-grained row-level deltas exceeds the cost of a simple full rewrite. Enzyme's cost model correctly chooses full recompute for Prospect.

DimAccount is a small, fast workload. Its incremental refresh shows limited speedup on its own, but Enzyme still incrementalizes it because doing so produces a small downstream changeset, dramatically reducing costs for dependent downstream MVs. This demonstrates the importance of pipeline-aware cost modeling.

6.4 Autoscaling Benefits

Incremental runs exhibit smoother, lower Spark task curves — fewer tasks with smaller spikes compared to full recomputes. Because the cluster's autoscaler tracks task load, incremental pipelines require fewer executors on average, reducing compute cost beyond just the CPU-time savings. The autoscaler can scale down during the smoother incremental workload and scale up only when the periodic full-recompute peaks occur.

7. Related Work

IVM has a rich research history spanning four decades. Early work (Blakeley, Larson, and Tompa, 1986; Gupta, Mumick, and Subrahmanian, 1993; Griffin and Libkin, 1995) established the first-order delta rules for relational algebra that Enzyme builds on. These covered set and bag semantics but left nested and correlated subqueries only partially addressed.

DBToaster (Koch et al., 2014) pushed to higher-order deltas: it materializes not only the view but also deltas of deltas, reducing update costs for join-heavy queries at the cost of more state. Differential Dataflow (McSherry et al., 2013) generalizes incremental computation using partially ordered timestamps. DBSP (Budiu et al., 2023) recasts databases as streams over commutative groups with integration and differentiation operators — a powerful unifying formalism.

In production systems: Redshift, BigQuery, and PostgreSQL offer periodic-refresh MVs for query acceleration. Materialize and RisingWave are streaming MV systems that maintain views as long-running dataflows with row-level updates on every change. Snowflake Dynamic Tables pair CDC with scheduled or freshness-target-based maintenance. Databricks itself offers both streaming tables (continuously updated, append-oriented) and MVs (batch-refreshed with optional incrementalization via Enzyme).

Enzyme's position is unique: it is a fully automated, cost-aware, pipeline-level IVM engine that handles arbitrary SQL compositions in a lakehouse setting (no secondary indexes, ACID transactions via Delta Lake). Its cost model's empirical, history-driven approach contrasts with static cost models in most commercial systems.

8. Conclusion

Enzyme demonstrates that a production-grade IVM system can be built on top of an open lakehouse stack — Apache Spark plus Delta Lake — without sacrificing correctness, operator coverage, or automation. Its six-stage architecture cleanly separates concerns: normalization and fingerprinting handle query identity; decomposition sets up the backing store; the plan generator applies compositional delta rules; the cost model selects strategies; execution integrates tightly with Spark.

The key lessons are: (1) an adaptive, history-driven cost model beats static heuristics in a production setting; (2) pipeline-level optimization is essential — local decisions affect global cost; (3) fingerprint stability requires explicit versioning as a system evolves; (4) non-determinism and temporal functions are not edge cases — they are common in real ETL workloads; and (5) comprehensive, randomized correctness testing is indispensable because IVM bugs are subtle and data-distribution-dependent.

The Big Picture

Incremental view maintenance is fundamentally a question of reusing work. Full recomputation is always safe and always correct, but throws away everything the system already knows. IVM is the disciplined application of the chain rule of computation: if the inputs changed by a small amount, the output should change by a correspondingly small amount — and a smart system should be able to compute only that small change. Enzyme shows that this ideal can be realized end-to-end at production scale, across complex SQL, with no manual tuning required.
