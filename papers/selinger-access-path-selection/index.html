Scientific Paper · SIGMOD 1979

Access Path Selection in a Relational Database Management System

P. Griffiths Selinger, M. M. Astrahan, D. D. Chamberlin, R. A. Lorie, T. G. Price Proceedings of ACM SIGMOD 1979 · IBM Research Division, San Jose
Abstract In a high-level query language like SQL, requests are stated non-procedurally: the user says what data to retrieve, not how to retrieve it. The System R optimizer is responsible for choosing both the order in which tables are joined and the physical access path—segment scan or index—used for each table. From the many possible plans, it selects the one that minimizes total access cost. This paper describes how that optimizer works: the statistics it maintains, the cost formulas it applies to single-table and multi-table queries, the dynamic-programming algorithm it uses to explore join orderings, and how it handles nested subqueries. The result is a query optimizer whose ideas—selectivity factors, interesting orders, and bottom-up dynamic programming—became the blueprint for virtually every relational optimizer that followed.

1. The Problem: Choosing How to Execute a Query

When you write a SQL statement like SELECT NAME, SAL FROM EMP WHERE TITLE = 'CLERK' AND LOC = 'DENVER', you are describing a what, not a how. The database engine must figure out the how on its own. For a single table, that means deciding whether to read every row (a full segment scan), or to use an index. For a query that joins three tables, it must also decide which pair to join first, which pair second, and by what method to perform each join. The number of possible execution plans grows explosively with the number of tables, and choosing badly can cost orders of magnitude more than choosing well.

System R was an experimental relational database management system built by IBM's San Jose Research Laboratory starting in 1975. It was one of the first systems to take the promise of non-procedural SQL seriously—meaning the system, not the user, would pick the execution strategy. The paper by Selinger et al. is the definitive description of how System R's OPTIMIZER component makes those decisions. It remains one of the most-cited papers in database research because the architecture it describes—cost-based, statistics-driven, exhaustive-with-pruning dynamic programming—is still the dominant paradigm in modern query optimizers.

Intuition — Why access path choice matters so much

Imagine a table EMP with one million rows, indexed on SALARY. You issue the query WHERE SALARY = 50000. If exactly 10 employees earn $50,000, using the index costs roughly 10 disk reads. A full segment scan costs roughly 50,000 disk reads (one per page). That is a factor of 5,000 difference—in a real system, the difference between a sub-second response and a query that runs for several minutes.

2. System R and Its Storage Layer

System R processes each SQL statement in four phases: parsing, optimization, code generation, and execution. The OPTIMIZER runs during the second phase. It looks up the tables and columns in the System R catalog, checks for type compatibility, and then performs access path selection. The output of the optimizer is a plan expressed in the Access Specification Language (ASL), which the CODE GENERATOR translates into machine code.

The physical storage of data is managed by the Research Storage System (RSS), which presents a tuple-oriented interface to the rest of System R. Two types of scans are available. A segment scan reads every non-empty page of a segment and returns all tuples belonging to a given relation—it is essentially a full table scan. An index scan uses a B-tree index to locate only tuples matching a predicate. Index scans come in two flavors: clustered and non-clustered. A clustered index physically orders data pages to match the index order, so a range scan reads pages roughly once. A non-clustered index may require a separate disk I/O for each matching tuple, since the data pages are scattered in arbitrary order.

Definition — Clustered vs. Non-Clustered Index

An index on column C is clustered if the physical ordering of data pages in the segment corresponds to the ordering of C values in the index. For a clustered index, a range scan touches each data page at most once. For a non-clustered index, consecutive index entries may point to tuples on completely different pages, so in the worst case each tuple retrieval requires a separate page fetch.

The optimizer also uses the concept of a sargable predicate (Search ARGument able). A predicate is sargable if it can be evaluated inside the RSS—i.e., it can be expressed as a boolean combination of simple comparisons involving index key columns. Sargable predicates can be pushed into the index scan as "search arguments" (SARGS), filtering tuples without ever returning them to the optimizer layer. Non-sargable predicates (for example, those involving arithmetic on a column) must be evaluated after each tuple is returned.

3. The Cost Model

The optimizer's central objective is to minimize total access cost, which it estimates using a weighted formula that captures both disk I/O and CPU work. The cost formula for any access path is:

$$\text{COST} = \text{PAGE FETCHES} + W \times \text{RSI CALLS}$$

Here, PAGE FETCHES is the number of disk pages read, RSI CALLS is the number of tuples retrieved from the storage system (a proxy for CPU time), and $W$ is an adjustable weight between 0 and 1 that blends I/O cost and CPU cost into a single scalar. Because System R spends most of its CPU time inside the RSS, the RSI CALLS count is a good approximation of CPU utilization.

Intuition — Why a single cost number?

Combining I/O and CPU into one number lets the optimizer compare plans on a single dimension. In 1979, disk I/O dominated, so $W$ was set close to zero—essentially treating I/O as the only cost that mattered. Modern optimizers still use variants of this idea, though today the blending of CPU, memory, and I/O cost is far more sophisticated.

To compute a cost prediction, the optimizer needs statistics about the data. It maintains the following in the System R catalog. For each relation $T$:

  • $\text{NCARD}(T)$ — the cardinality (number of tuples) of relation $T$.
  • $\text{TCARD}(T)$ — the number of pages in the segment holding tuples of $T$.
  • $P(T)$ — the fraction of data pages that hold tuples of $T$, defined as $\text{TCARD}(T) / (\text{non-empty pages in segment})$.

For each index $I$ on relation $T$:

  • $\text{ICARD}(I)$ — the number of distinct key values in index $I$.
  • $\text{NINDX}(I)$ — the number of pages in index $I$.

These statistics are not updated on every INSERT or DELETE (that would create locking bottlenecks). Instead, they are refreshed periodically via an UPDATE STATISTICS command, so cost estimates may be stale. The optimizer is designed to be robust to moderate inaccuracy in these numbers.

4. Single-Table Access Paths and Their Costs

For a query that references only one table, the optimizer enumerates every available access path (each index, plus the segment scan) and computes a predicted cost for each. It also tracks the ordering of tuples that each path produces—this will matter later for joins and ORDER BY clauses. The cost formulas, taken from Table 2 of the paper, are:

Cost Formulas — Single Relation (Table 2 in the paper)
  • Unique index matching an equality predicate: $1 + 1 + W$ — one page to traverse the index, one page to fetch the data tuple, plus CPU cost for one RSI call.
  • Clustered index matching one or more boolean factors: $F(\text{preds}) \times (\text{NINDX}(I) + \text{TCARD}) + W \times \text{RSICARD}$
  • Non-clustered index matching one or more boolean factors: $F(\text{preds}) \times (\text{NINDX}(I) + \text{NCARD}) + W \times \text{RSICARD}$
  • Segment scan: $\text{TCARD}/P + W \times \text{RSICARD}$

Here $F(\text{preds})$ is the selectivity factor (fraction of tuples expected to satisfy the predicate), and RSICARD is the expected number of tuples returned by the RSS for this access path. For non-clustered indexes, the formula uses NCARD (total tuple count) rather than TCARD (page count) because scattered tuples may each require a separate page read.

The distinction between clustered and non-clustered indexes is crucial. A clustered index on a column where the query has a range predicate—say, SALARY BETWEEN 40000 AND 60000—will read a contiguous run of pages and is highly efficient. A non-clustered index on the same query must follow one pointer per matching tuple, and if many tuples match, it can be slower than a full segment scan.

5. Selectivity Factors: Estimating How Many Rows Match

The selectivity factor $F$ for a predicate is the optimizer's estimate of the fraction of tuples that will satisfy it. It is the key parameter that feeds into the cost formulas. Table 1 of the paper lists how $F$ is computed for different predicate types:

Selectivity Factor Rules (Table 1)
  • column = value: If an index exists on that column, $F = 1/\text{ICARD}(\text{column index})$ (assumes uniform distribution). Otherwise, $F = 1/10$ as a default.
  • column > value: If the column is arithmetic and the value is known, linear interpolation over the key range is used: $F = (\text{high key} - \text{value}) / (\text{high key} - \text{low key})$. Otherwise, $F = 1/3$.
  • column BETWEEN value1 AND value2: $F = (\text{value2} - \text{value1}) / (\text{high key} - \text{low key})$ if arithmetic; otherwise $F = 1/4$.
  • column IN (list): $F = (\text{list length}) \times F(\text{col} = \text{val})$, capped at $1/2$.
  • pred1 AND pred2: $F = F(\text{pred1}) \times F(\text{pred2})$ (independence assumed).
  • pred1 OR pred2: $F = F(\text{pred1}) + F(\text{pred2}) - F(\text{pred1}) \times F(\text{pred2})$.
  • NOT pred: $F = 1 - F(\text{pred})$.

These formulas make strong simplifying assumptions—most notably column-value independence and uniform value distribution—that are often violated in practice. The paper acknowledges this, and subsequent decades of database research have produced increasingly sophisticated cardinality estimators (histograms, sketches, machine learning models). But the 1979 formulas were a workable starting point, and the insight that the optimizer must estimate selectivity at all was itself a significant contribution.

Pause and Reflect

The independence assumption for AND predicates says: if 10% of rows have TITLE = 'CLERK' and 20% of rows have LOC = 'DENVER', then roughly 2% of rows satisfy both. This is wrong whenever columns are correlated—for example, if clerks are disproportionately located in Denver. The optimizer cannot know about such correlations without additional statistics. This tension between accurate cardinality estimation and the cost of collecting statistics remains one of the central unsolved problems in query optimization today.

6. Join Order Selection and Join Methods

For queries that join multiple tables, the optimizer must choose both the order in which tables are joined and the method used for each join. System R supports two join methods:

Definition — Nested Loop Join

The nested loop join picks one relation as the outer and another as the inner. For each tuple of the outer relation, a scan is opened on the inner relation to retrieve matching tuples. The outer tuple and each matching inner tuple together form a result tuple. The cost is roughly the cost of scanning the outer once, plus the cost of scanning the inner once per outer tuple.

Definition — Merging Scans (Sort-Merge Join)

The merging scans method requires both the outer and inner relations to be sorted (or scanned) in join-column order. By advancing pointers into each sorted stream, matching tuples can be found in a single pass. This method is highly efficient when both inputs are already ordered—for example, when each has a clustered index on the join column. If one or both inputs are not sorted, a sort step must be performed first, but that sort is amortized if subsequent operations also benefit from the ordering.

The cost of a nested loop join of two relations is:

$$C_{\text{NL}}(\text{path1}, \text{path2}) = C_{\text{outer}}(\text{path1}) + N \times C_{\text{inner}}(\text{path2})$$

where $N$ is the number of qualifying tuples from the outer relation, and $C_{\text{inner}}(\text{path2})$ is the cost of one scan of the inner relation. Similarly, the cost of a merge scan join is:

$$C_{\text{merge}}(\text{path1}, \text{path2}) = C_{\text{outer}}(\text{path1}) + N \times C_{\text{inner}}(\text{path2})$$

where for the merge join, the inner scan is the cost of scanning the contiguous group of matching rows in the (sorted) inner relation, rather than the entire inner table. The merging scans method exploits clustering in the join column, making the effective inner scan cost very small.

7. Interesting Orders and Dynamic Programming

For a query joining $n$ tables, there are $n!$ possible orderings in which to join them. Even for $n = 5$, that is 120 orderings. Evaluating every possible plan naively would be intractable. The optimizer uses a bottom-up dynamic programming approach that systematically builds optimal solutions for subsets of tables, reusing subproblem solutions as it grows to larger subsets.

The key insight that makes this tractable is the principle of optimality: the best plan for joining tables $T_1, \ldots, T_k$ can be found by taking the best plan for joining $T_1, \ldots, T_{k-1}$ and joining it to $T_k$ using the best available method. Because the cost of joining the composite relation to $T_k$ depends only on the ordering and cardinality of the composite—not on how the composite was built—the dynamic programming decomposition is valid.

Definition — Interesting Order

A tuple ordering is called an interesting order if it matches a column specified in the query's GROUP BY or ORDER BY clause, or a join column used in a merging-scan join. The optimizer must track not only the cheapest unordered access path for each relation, but also the cheapest access path that produces each interesting ordering—because a plan that is more expensive at one step may save cost later by avoiding a sort.

For example, suppose a query has ORDER BY DNO and EMP has an index on DNO. Scanning EMP via the DNO index costs more than a full segment scan (assume the index is non-clustered). But the DNO index produces tuples in DNO order, which is an interesting order. If the next step is a merge join on DNO, the sorted output can be used directly with no additional sort. So the optimizer must keep the DNO-order path alive even if it loses the raw-cost comparison against the segment scan.

The algorithm works as follows: first, find the cheapest access path for each single relation for each interesting ordering and for the unordered case. Then, for each pair of relations, find the cheapest way to join any one of the single-relation solutions to any access path on the other relation, considering both nested loop and merging scan methods, for each interesting ordering and the unordered case. Continue for triples, quadruples, and so on, pruning dominated solutions at each level. The final answer is the cheapest solution for all $n$ tables joined together.

Heuristic: Join Order Pruning

To further reduce the search space, System R applies a heuristic: when building join orderings for a relation $T_j$, it only considers orderings in which every relation to the left of $T_j$ has a join predicate connecting it to at least one other relation to its left. This prevents Cartesian products from being introduced too early—Cartesian products generate enormous intermediate results and are almost never the right choice. The paper calls such orderings those in which $T_j$ has a join predicate with $T_i$ for some $i < j$.

The number of solutions that must be stored is at most $2^n$ (the number of subsets of $n$ tables) times the number of interesting orderings. For typical queries with 2–8 tables, this is very manageable. The paper reports that 8-table joins have been optimized in a few seconds on a 370/158 mainframe using only a few thousand bytes of storage.

8. Nested Queries

SQL allows subqueries to appear inside predicates, as in WHERE SALARY > (SELECT AVG(SALARY) FROM EMPLOYEE). System R calls these nested queries or subqueries. The OPTIMIZER arranges for subqueries to be evaluated before the top-level query block whenever possible. If the subquery returns a single value (a scalar subquery), that value is substituted into the predicate as if it were a literal constant.

More complex are correlated subqueries, where the subquery references a column from the outer query block. For example:

Example — Correlated Subquery 
SELECT NAME
FROM EMPLOYEE X
WHERE SALARY > (SELECT SALARY FROM EMPLOYEE
                WHERE EMPLOYEE_NUMBER = X.MANAGER)

For each candidate tuple from EMPLOYEE X, the subquery must be re-evaluated using X.MANAGER as a parameter. This re-evaluation is expensive—ideally done once per unique value of X.MANAGER rather than once per outer tuple. If the referenced relation is ordered on the correlated column, the optimizer can make the re-evaluation conditional, reusing the previous result whenever the correlated value hasn't changed.

9. Why This Paper Mattered

The Selinger et al. paper made several contributions that proved durable. First, it demonstrated that a cost-based optimizer, driven by statistics gathered from the data, could reliably choose good execution plans without user guidance. Before System R, the conventional wisdom was that hand-tuned procedural access patterns were necessary for performance. The paper showed that non-procedural query languages and automatic optimization were not just theoretically appealing but practically viable.

Second, the concept of the selectivity factor gave the optimizer a principled way to estimate intermediate result sizes—the key quantity that determines which join order is cheapest. Even though the independence assumption is often violated, it was good enough that the optimizer selected the correct plan in the large majority of cases.

Third, the notion of interesting orders was a key insight: the optimizer should not just track cheapest cost, but cheapest cost for each possible output ordering. This allowed the optimizer to avoid unnecessary sorts by leveraging index-ordered scans and merge joins, and it is still the correct formulation of the multi-objective optimization problem in relational query execution.

Fourth, the bottom-up dynamic programming framework provided a sound algorithmic foundation for join order enumeration. The paper proved that the search space could be systematically pruned using the principle of optimality, and the resulting algorithm was efficient enough to run at compile time in a real system. Every major commercial relational database engine—IBM DB2, Oracle, SQL Server, PostgreSQL—implements a variant of this algorithm today.

Intuition — The lasting impact

It is hard to overstate how foundational this paper is. When you run a complex SQL query on any modern database and it completes in milliseconds, you are benefiting directly from the ideas here: the optimizer is silently enumerating access paths, estimating selectivities, tracking interesting orders, and applying dynamic programming to find the cheapest join order. The vocabulary of "access path", "selectivity", "interesting order", and "cardinality estimate" still structures how database engineers think about and discuss query optimization.
