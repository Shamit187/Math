Scientific Paper · VLDB 1987

The R+-Tree: A Dynamic Index for Multi-Dimensional Objects

Timos Sellis, Nick Roussopoulos, Christos Faloutsos Proceedings of the 13th VLDB Conference, Brighton, 1987
Abstract The problem of indexing multidimensional objects is considered. First, a classification of existing methods is given along with a discussion of the major issues involved in multidimensional data indexing. Second, a variation on Guttman's R-trees—called R+-trees—is introduced that avoids overlapping rectangles in the intermediate nodes of the tree. Algorithms for searching, updating, initial packing, and reorganization of the structure are discussed in detail. Finally, analytical results indicate that R+-trees achieve up to 50% savings in disk accesses compared to an R-tree when searching files of thousands of rectangles.

1. Why Index Multi-Dimensional Data?

Standard database indexes—B-trees and their variants—work beautifully for one-dimensional data like integers, strings, or dates. A B-tree organizes values on a total order, making range queries straightforward: given a query WHERE SALARY BETWEEN 40000 AND 60000, the tree finds the leftmost match and reads consecutive leaves. But what happens when data is inherently two-dimensional or higher?

Consider these applications, each of which the paper explicitly lists: cartographic databases (maps of roads, buildings, and boundaries), VLSI circuit design (thousands of rectangles representing electronic gates and wiring channels), computer vision (bounding boxes around detected objects), and rule indexing in expert systems (rules stored as geometric entities in an abstract space). All of these require spatial queries: given a query region, find all stored objects that overlap it, or given a point, find all objects that contain it.

A B-tree on latitude alone cannot answer "find all restaurants within this map rectangle." A spatial index must reason about two (or more) coordinates simultaneously. The challenge is to organize rectangles on disk pages—each page holding perhaps 50 entries—in a way that supports efficient search without reading most of the dataset.

Definition — Point Query and Region Query

A point query asks: given a point $P$ in space, find all stored objects that contain it. A region query (also called a window query) asks: given a query rectangle $W$, find all stored objects whose bounding rectangle overlaps $W$. Both are fundamental operations in geographic information systems and spatial databases.

The paper surveys the landscape of existing approaches—fixed-grid methods, k-d trees, space-filling curves, and the R-tree—before introducing the R+-tree. Understanding why the R-tree falls short is necessary before appreciating what the R+-tree fixes.

2. The R-Tree and Its Overlap Problem

Guttman's R-tree (SIGMOD 1984) extends the B-tree to multiple dimensions. Like a B-tree, it is a height-balanced tree where all leaves appear at the same level. Each leaf node stores pairs of the form $(oid, RECT)$, where $oid$ is an object identifier and $RECT$ is the object's minimum bounding rectangle (MBR). Each internal (intermediate) node stores pairs $(p, RECT)$ where $p$ is a pointer to a child node and $RECT$ is the MBR of all objects reachable through that child.

The structure is dynamic: insertions and deletions can be intermixed with queries. Whenever a node overflows (more than $M$ entries), it is split into two nodes. Guttman described several split algorithms (linear, quadratic, exponential) all aimed at minimizing the total area covered by the two resulting MBRs.

The fundamental problem with R-trees is overlap between sibling MBRs at intermediate nodes. Because data rectangles can be large and arbitrarily placed, the MBRs of two sibling nodes in the tree often overlap. When a query window $W$ falls in the overlapping region, the search algorithm must descend into both subtrees—even though only one of them may actually contain qualifying data.

Example — The Cost of Overlap

Suppose an R-tree has two child nodes $A$ and $B$ whose MBRs overlap in a large central region. A point query landing in that overlap must check both $A$ and $B$ and their descendants. In the worst case, if the tree has height $h$ and every level has $k$ overlapping nodes, the search fans out to $k^h$ leaf nodes—potentially degenerate into a linear scan of the entire tree.

Roussopoulos and Leifker (SIGMOD 1985) showed that for point data, the zero-overlap condition (no two sibling MBRs overlap) is only achievable with a packing algorithm applied to a static dataset. For region data (non-zero-area objects), zero overlap at intermediate nodes is generally unachievable without splitting data objects. It is this insight—that data rectangles can be split across multiple subtrees if necessary—that motivates the R+-tree.

3. The R+-Tree: The Core Idea

The R+-tree's central design decision is simple but consequential: intermediate node MBRs must not overlap. To enforce this when a data rectangle $R$ would otherwise span two sibling MBRs, the R+-tree clips $R$ into two or more sub-rectangles, each assigned to a different subtree. Each sub-rectangle is stored in the appropriate leaf node, tagged to indicate it belongs to the same original object.

Intuition — Trading space for search efficiency

Think of it like organizing a jigsaw puzzle by region. If a puzzle piece straddles the boundary between two boxes, the R-tree puts the piece in whichever box it fits best (keeping an overlapping MBR). The R+-tree cuts a copy of the piece and puts half in each box—so each box's region is perfectly disjoint. Searching a specific area of the puzzle only ever requires opening boxes whose regions contain that area, never boxes whose regions merely might overlap it.

The tradeoff is that a data rectangle that spans a partition boundary will appear in more than one leaf node. This increases the storage requirement and complicates insertion (since inserting a rectangle may require propagating splits downward through the tree). However, the paper argues—and demonstrates analytically—that this extra storage cost is more than recovered by the savings in search time, especially for workloads with many point queries and moderate data rectangle sizes.

4. Structure and Formal Properties

An R+-tree is formally defined as follows. A leaf node stores entries of the form $(oid, RECT)$, where $RECT$ is the bounding rectangle of the data object (or a sub-rectangle of it, if the object was clipped). An intermediate node stores entries of the form $(p, RECT)$ where $RECT$ is a rectangle enclosing all leaf entries reachable through pointer $p$. In two dimensions, a RECT entry is:

$$(x_{low}, x_{high}, y_{low}, y_{high})$$

The R+-tree satisfies four properties:

R+-Tree Properties
  1. Coverage: For each entry $(p, RECT)$ in an intermediate node, every rectangle $R$ in the subtree rooted at $p$ is covered by $RECT$ (or overlaps with $RECT$ if $R$ is in a leaf).
  2. Disjointness: For any two entries $(p_1, RECT_1)$ and $(p_2, RECT_2)$ in an intermediate node, the overlap between $RECT_1$ and $RECT_2$ is zero.
  3. Non-trivial root: The root has at least two children unless it is a leaf.
  4. Height balance: All leaves appear at the same level.

Property 2 (disjointness) is the key distinction from the R-tree. Note that the disjointness guarantee applies only to intermediate nodes. At the leaf level, two entries may correspond to overlapping data objects—that is fine, because the objects genuinely overlap in space. The prohibition on overlap is at the directory level, where it would cause unnecessary search fan-out.

One important difference from the R-tree: the R-tree guarantees that every leaf node contains between $M/2$ and $M$ entries (except the root). The R+-tree does not strictly guarantee this, because the clipping of rectangles can result in leaf nodes with fewer entries. However, in practice the fill factor remains acceptable.

5. Searching an R+-Tree

The search algorithm is elegant and benefits directly from the disjointness property. Given a query window $W$:

Algorithm Search (R, W)

Input: An R+-tree rooted at node $R$, and a search window $W$.
Output: All data objects overlapping $W$.

S1 (Intermediate nodes): If $R$ is not a leaf, for each entry $(p, RECT)$ check if $RECT$ overlaps $W$. If so, recursively search the child at $p$, restricting the window to $S \cap RECT$.
S2 (Leaf nodes): If $R$ is a leaf, return all entries whose $RECT$ overlaps $W$.

Because intermediate node MBRs are disjoint, a query window $W$ can overlap at most the nodes whose MBRs it intersects, and since those MBRs don't overlap each other, the search is much better focused than in an R-tree. For a point query, the query window is a single point, and it can lie in at most one intermediate MBR at each level—so the search follows exactly one path from root to leaf.

Intuition — Why point queries are so much faster

In an R-tree, a point can lie in the MBRs of multiple sibling nodes because those MBRs overlap. Each such node must be searched. In an R+-tree, since intermediate MBRs are disjoint, a single point can lie in at most one intermediate MBR at each level. The search is therefore a single root-to-leaf path—the same cost as a B-tree lookup. For a database of 100,000 rectangles with a branching factor of 50, that is roughly 3 disk reads versus potentially dozens in an R-tree.

6. Insertion and Node Splitting

Insertion into an R+-tree is more complex than in an R-tree because a single inserted rectangle may need to be placed in multiple leaf nodes. The insertion algorithm works as follows: to insert rectangle $IR$ into the tree, find all leaf nodes whose covering MBR overlaps $IR$, and add $IR$ (or the clipped portion of it) to each.

When a leaf node overflows (exceeds $M$ entries), the SplitNode procedure is invoked. Unlike an R-tree split, which simply divides the node's entries into two groups, the R+-tree SplitNode must find a partition—a vertical or horizontal line—that divides the covered space into two disjoint sub-regions. This partition then propagates downward: any rectangles in the leaf that straddle the partition line are clipped and placed in both new leaf nodes. The partition also propagates upward: the parent's entry for this node is updated, and if the parent overflows, it too must be split.

Complexity — Downward Split Propagation

A critical difference from R-trees is that splits can propagate downward as well as upward. If a parent node $A$ must be split, and the split boundary cuts through the covering rectangle of a child node $B$ of $A$, then $B$ must also be split along that boundary. This downward propagation makes the insertion algorithm more expensive than in an R-tree, but the authors argue that for search-heavy workloads, the improved search performance more than compensates.

The SplitNode algorithm uses a Partition procedure that searches for a "good" partition boundary using several criteria: nearest neighbors (minimize the number of rectangles that must be split by the partition), minimal total area covered by the two sub-regions, minimal total space coverage, and minimal number of rectangle splits. These criteria are evaluated using a Sweep algorithm that sweeps a line across the space along the x- or y-axis, selecting the split point that optimizes the chosen criterion.

7. The Packing Algorithm

The paper devotes significant attention to an initial packing algorithm for building an R+-tree from scratch over a given static set of rectangles. Packing is important because it produces a much better-organized tree than dynamic insertion: the nodes are more densely filled, coverage is smaller, and search performance is better.

The Pack algorithm works recursively. Given a set $S$ of rectangles and a fill factor $ff$:

  1. If $|S| \leq ff$, build a single leaf node and return it (no further partitioning needed).
  2. Otherwise, call Partition to divide $S$ into a first sub-region of $ff$ rectangles and a remainder $S'$. The Partition is computed by the Sweep procedure, which slides a line along the x- or y-axis and stops when $ff$ rectangles have been covered.
  3. Rectangles that straddle the partition line are clipped; each sub-rectangle goes to its respective region.
  4. Recursively Pack each sub-region to build intermediate nodes, then combine them into the final tree.

The fill factor determines how densely the nodes are packed. A higher fill factor means more entries per node, a shorter tree, and faster searches—at the cost of more rectangle splits during packing. For static or nearly-static datasets, packing to near capacity is highly desirable. The Sweep algorithm runs in $O(N \log N)$ time (due to the required sort along each axis).

8. Analytical Results and Performance

To analyze search performance, the authors use a mapping technique: rectangles in 2-d space are transformed to points in 4-d space (storing the four coordinates of each rectangle as a single 4-d point). Analysis for 1-d segments (simpler to handle) is used as a stepping stone.

The key analytical result is presented for two-size datasets: a mix of $N_1$ small segments of size $\sigma_1$ and $N_2$ large segments of size $\sigma_2$. The analysis shows that when a small number of large segments coexist with many small ones, R-trees suffer disproportionate performance degradation. The large segments force large, highly overlapping MBRs at intermediate nodes, causing many false-positive subtree descents during queries. The R+-tree clips these large segments, keeping intermediate-node regions small and disjoint.

Experimental comparisons (Figures 5.1 and 5.2 in the paper) show that for point queries on files with thousands of rectangles, R+-trees can require up to 50% fewer disk accesses than R-trees. The advantage is most pronounced when a significant fraction of the indexed objects are large—segments whose size is comparable to the whole dataset extent. As large segments become a smaller fraction, the two structures converge in performance. For segment queries (region queries), savings of a similar magnitude are reported.

Pause — The storage overhead tradeoff

The R+-tree is not free. By clipping large rectangles, each original object may have its identifier stored in multiple leaf pages. This increases storage and also means that a delete operation must find and remove all clipped copies—potentially touching multiple leaf pages. For write-heavy or delete-heavy workloads, the R+-tree may be less attractive than the R-tree. The paper focuses on read-heavy scenarios where this tradeoff is favorable.

9. Significance and Limitations

The R+-tree occupies an important position in the history of spatial indexing. It identified and clearly articulated the overlap problem in R-trees and proposed a principled solution: enforce disjointness at intermediate nodes, even at the cost of clipping data objects. This insight influenced subsequent work significantly, including the R*-tree (Beckmann et al., SIGMOD 1990), which took a different approach—trying to minimize overlap without clipping—and became the most widely adopted spatial index in practice.

The R+-tree is also notable for introducing the pack algorithm as a first-class concern. For spatial databases that are loaded once and queried frequently (cartographic databases, for example), packing produces a dramatically better structure than online insertion. This distinction between static-load and dynamic-update scenarios is now standard practice in spatial database system design.

The limitations are real. The downward propagation of splits during insertion is expensive and can cascade through many levels. Deletions must find all copies of a clipped rectangle. The structure's height can grow relative to an R-tree because splitting a node to enforce disjointness may produce nodes with fewer entries than $M/2$, leading to an underutilized tree. For insertion-intensive applications, the R*-tree's approach of minimizing overlap without clipping is generally preferred.
