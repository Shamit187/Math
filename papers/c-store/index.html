C-Store: A Column-oriented DBMS

Mike Stonebraker, Daniel J. Abadi, Adam Batkin, Xuedong Chen, Mitch Cherniack, Miguel Ferreira, Edmond Lau, Amerson Lin, Sam Madden, Elizabeth O'Neil, Pat O'Neil, Alex Rasin, Nga Tran, Stan Zdonik Proceedings of the 31st VLDB Conference, Trondheim, Norway, 2005
Abstract This paper presents the design of C-Store, a read-optimized relational DBMS that departs sharply from conventional write-optimized row stores. Its key ideas are: storing data by column rather than by row; maintaining overlapping collections of column-oriented projections sorted on different attributes; aggressively coding and compressing columns; separating a small write-optimized Writeable Store (WS) from a large Read-optimized Store (RS) and connecting them with a background Tuple Mover; providing snapshot isolation for read-only queries to avoid locking; and using bitmap indexes extensively to complement B-trees. Preliminary benchmarks on a TPC-H subset show C-Store is substantially faster than commercial row-store and column-store products on read-heavy analytical queries, while using 40% of the disk space of the leading row store.

1. Why Columns?

Every major relational database system you have heard of — Oracle, SQL Server, DB2, PostgreSQL, MySQL — stores data in rows. A row store places all of a record's attributes contiguously on disk: if the EMP table has columns Name, Age, Dept, and Salary, then one disk page might contain (Bob, 25, Math, 10K), (Bill, 27, EECS, 50K), (Jill, 24, Biology, 80K). This design made perfect sense in the 1970s, when the dominant application was OLTP: banking systems that update individual customer records, airline reservation systems that modify one booking at a time. A single-row write requires a single disk seek and a single disk write.

But the database world has evolved. A huge fraction of today's database workloads are analytical: the marketing department wants to know the total revenue by region for the past year; the risk team needs the average salary of every employee in Engineering across 47 countries. These queries touch one or two columns of a table that might have 200 columns. A row store must read all 200 columns from disk to answer a query that only needs 2. This is pure waste.

Intuition — The CPU/Disk Asymmetry Argument

CPUs have been getting faster at roughly Moore's Law pace — doubling every 18 months. Disk bandwidth has improved much more slowly. The bottleneck in analytical queries is therefore disk I/O, not computation. C-Store's core insight is: trade CPU cycles for disk bandwidth. By compressing columns heavily, the system reads fewer bytes from disk, even if decompression requires more CPU. In 2005, this trade-off strongly favored compression; today, with NVMe SSDs, the argument shifts somewhat, but column storage remains the dominant architecture for analytics precisely because of this principle.

A column store keeps all values of a single column contiguously: one file (or segment) for Name, another for Age, another for Salary, and so on. A query computing SELECT AVG(Salary) FROM EMP WHERE Dept = 'Math' reads only the Dept and Salary columns. Everything else stays on disk, untouched. Combined with compression — consecutive Salary values are likely to be numerically close, so delta-encoding compresses them dramatically — the I/O savings are enormous.

2. Projections: The Physical Unit of Storage

C-Store does not store base tables directly. Instead, it stores projections: sorted, potentially overlapping subsets of a table's columns. A projection over table $T$ retains a subset of $T$'s attributes, all sorted on a designated sort key. The same column may appear in multiple projections sorted on different keys.

Example — EMP Projections

Given a table EMP(Name, Age, Dept, Salary) and DEPT(DName, Floor), one possible set of projections is:

EMP1(Name, Age | Age) — sorted by Age
EMP2(Dept, Age, DEPT.Floor | DEPT.Floor) — sorted by Floor
EMP3(Name, Salary | Salary) — sorted by Salary

Notice that Name appears in both EMP1 and EMP3. This redundancy is intentional: it allows a query that filters on Salary to use EMP3 (optimally sorted for that access) without touching EMP1. The query optimizer chooses which projection to use based on which one's sort order best matches the query's predicates and aggregations.

Because each projection stores only a subset of columns, C-Store needs a mechanism to reconstruct full rows when necessary. This is done via join indexes: for each pair of projections over the same table, a join index maps rows in one projection to corresponding rows in the other. Specifically, a join index from projection $T_1$ to $T_2$ is a table of (segment ID, storage key) pairs, one per row in $T_1$, identifying the corresponding row in $T_2$.

The system guarantees that projections form a covering set: for every column of every table, at least one projection contains it. This means any query can always be answered using only the available projections and join indexes, without touching the original table layout. The system is also designed to be K-safe: even if $K$ storage nodes fail simultaneously, there remain enough overlapping projections to reconstruct every column of every table.

3. The Read-Optimized Store (RS)

The RS is the large, read-only, heavily compressed component of C-Store. Every projection is broken into its constituent columns, and each column is stored in the RS as a sorted, compressed sequence. The storage key for a tuple in the RS is its ordinal position within the sorted sequence — it is not physically stored but inferred on the fly, saving space.

The RS supports only one kind of write: the batch insertion of new data migrated from the WS by the Tuple Mover. This restriction allows the RS to be organized entirely around read performance — no update-in-place, no free-list management, no fragmentation. Every disk page is packed as tightly as compression allows.

4. Four Compression Schemes

The choice of compression scheme for a column depends on two factors: whether the column is self-ordered (sorted by its own values, so consecutive entries are close together) or foreign-ordered (sorted by some other column's values, giving potentially random order within this column), and how many distinct values the column contains.

Type 1 — Self-order, few distinct values (Run-Length Encoding)

Represent each run of identical values as a triple (v, f, n) where $v$ is the value, $f$ is the starting position, and $n$ is the run length. A Dept column sorted by Dept that contains 10,000 consecutive "Engineering" entries is represented as a single triple. Clustered B-trees over value fields enable fast lookup.

Type 2 — Foreign-order, few distinct values (Bitmap Encoding)

Represent the column as a collection of bitmaps: one bitmap per distinct value $v$, where the $i$-th bit is 1 if row $i$ contains value $v$. Since bitmaps are sparse, they are run-length encoded. An "offset index" B-tree maps column positions to values to support fast random access.

Type 3 — Self-order, many distinct values (Delta Encoding)

Represent every value as the difference (delta) from the previous value in the sorted sequence. For a salary column sorted by salary, the sequence 1, 4, 7, 7, 8, 12 becomes 1, 3, 3, 0, 1, 4 — small integers that compress far more efficiently than the originals. The first entry of each block stores the absolute value; subsequent entries store deltas.

Type 4 — Foreign-order, many distinct values (Unencoded)

When a column has many distinct values and is not self-sorted, no obvious compact encoding exists. Values are stored uncompressed, but a densepack B-tree provides indexed access. C-Store continues investigating compression techniques for this case.

A critical design choice: C-Store's query executor operates directly on compressed representations wherever possible, without first decompressing. A predicate on a Type 1 column can be evaluated by scanning only the run-length triples, skipping vast swathes of data. This means fewer bytes read from disk, less memory needed in the buffer pool, and — crucially — the compression itself does useful indexing work.

5. The Writeable Store (WS)

The RS cannot support transactional writes: its structure is too rigid. C-Store therefore maintains a small, separate Writeable Store (WS) that absorbs all inserts, updates, and deletes in real time. The WS uses the same logical schema (projections and join indexes) as the RS, but implements them differently: as B-trees on explicit storage keys rather than as compressed column files.

Every logical insert creates a new record in each WS projection for the affected table. The record's storage key (SK) is assigned at insert time and is guaranteed to be larger than any key currently in RS, so WS and RS key ranges are disjoint. Deletes are implemented as an insert-plus-delete: a delete operation inserts the logical record into WS (to ensure the RS projection can be updated) and marks it in a per-projection Deleted Record Vector (DRV), a bitmap that tracks which RS rows have been logically deleted.

Intuition — Why Separate Stores?

If you tried to insert into the RS directly, you would have to re-sort the compressed column to maintain the projection's sort order — an expensive $O(N \log N)$ operation that would fragment the column files and negate the compression benefits. The WS sidesteps this by accepting inserts in arrival order, using traditional B-tree indexing (which supports update-in-place efficiently). Queries must consult both stores and merge the results, but since WS is kept small relative to RS, this merge overhead is modest.

6. Transactions and Snapshot Isolation

Read-only queries — the vast majority in a warehouse — run under snapshot isolation: they see the database as of a particular timestamp $T$ in the recent past, before which all committed transactions are guaranteed visible. This eliminates the need for read locks entirely: read-only transactions never block writers and writers never block readers.

The timestamp mechanism uses a High Water Mark (HWM): the most recent time at which all transactions that started before it have committed. A designated Timestamp Authority (TA) periodically advances the HWM by broadcasting an "end of epoch" message to all sites. Each site acknowledges once all its transactions from that epoch are complete. Once the TA receives all acknowledgments, it sets the new HWM and broadcasts it. Read-only queries set their effective time to the current HWM and can then run without acquiring any locks.

There is also a Low Water Mark (LWM): the earliest timestamp at which a read-only transaction can run. The LWM is needed because WS data structures must retain information for all timestamps between LWM and HWM. Below LWM, records in WS are either moved to RS by the Tuple Mover or discarded. This prevents the WS from growing without bound.

Write transactions use strict two-phase locking and a standard write-ahead log (WAL), but with important differences from traditional logging: C-Store uses NO-FORCE, STEAL policy, logs only UNDO records (no REDO, because recovery uses other projections), and avoids the two-phase commit PREPARE phase by using a simplified distributed COMMIT protocol.

7. The Tuple Mover

The Tuple Mover is a background process that continuously migrates data from WS to RS. It operates on (WS, RS) projection pairs: it finds all WS records with an insertion timestamp at or before the LWM, merges them into the corresponding RS segment to produce a new RS segment RS', updates join indexes, and atomically swaps RS' for the old RS.

Records in WS that were deleted at or before the LWM are simply discarded — they can never be visible to any future query. Records that were not deleted, or were deleted after the LWM, are written into RS' in sort-key order alongside the surviving RS records. The resulting RS' is a newly sorted, fully compressed column file, free of the fragmentation or deleted-record gaps that would accumulate in an update-in-place system.

Pause — The Elegance of the Tuple Mover

This design means RS is always in a clean, fully sorted, fully compressed state. There is no background vacuum process needed to reclaim space from dead tuples (unlike PostgreSQL's VACUUM). There is no "hole" in the column file from an in-place delete. The Tuple Mover's merge operation is the same kind of operation that LSM-trees (Log-Structured Merge-Trees) use, and indeed the WS/RS split is structurally similar to the LSM-tree design independently developed by O'Neil et al. C-Store's insight was to apply this idea specifically to columnar projection storage.

8. Query Execution on Columns

The C-Store query executor defines 10 operators that work natively on columns and projections. The most important are: Decompress (converts a compressed column to uncompressed Type 4 representation), Select (applies a predicate and returns a bitstring of matching positions rather than a copy of matching values — this keeps intermediate results small), Mask (restricts a projection to rows where the corresponding bitstring bit is 1), Project (the relational projection), Sort, Aggregation Operators, Concat (combines projections with the same sort order), Permute (reorders a projection according to a join index), Join, and Bitstring Operators (BAnd, BOr, BNot — bitwise operations on selection bitstrings).

The key architectural choice is that operators communicate blocks of column data rather than individual tuples. Each call to the standard iterator interface returns 64 KB of values from a single column, matching modern CPU cache lines and dramatically reducing the per-tuple overhead of function-call dispatch that plagues row-store executors.

Query optimization in C-Store is novel in two respects: it must reason about compressed representations (should a predicate be evaluated on compressed or decompressed data?), and it must decide when to apply the Mask operator to a projection (early masking avoids decompressing unwanted rows; late masking allows bitstring operations to prune work in downstream operators).

9. Performance Results

The benchmark uses TPC-H at scale 10 (60 million line items, 1.8 GB of raw data). Three systems are compared: C-Store, a popular commercial row-store DBMS, and a popular commercial column-store DBMS, each given a 2.7 GB storage budget. C-Store uses only 1.987 GB — 40% less than the row store (4.48 GB) and 25% less than the commercial column store (2.65 GB), because C-Store's aggressive compression and absence of padding gives it a significant space advantage.

On the seven TPC-H-derived queries, C-Store is on average 164 times faster than the commercial row store and 21 times faster than the commercial column store within the same storage budget. Even in a space-unconstrained comparison (where the row store is given 4.5 GB and the column store 4.09 GB), C-Store is 6.4 times faster than the row store and 16.5 times faster than the column store. The authors attribute this to three factors: column-only I/O for queries touching few attributes; operation on compressed data; and the use of multiple overlapping projections sorted for each query's access pattern.

Caveat — Preliminary Results

The WS and Tuple Mover are not fully integrated at the time of publication. All reported benchmarks are read-only queries on the RS. The authors acknowledge that WS overhead and tuple mover latency may significantly affect update performance in the full system. A comprehensive write-performance analysis is deferred to future work.

10. Legacy and Influence

C-Store is arguably the most influential database architecture paper of the 2000s. It spawned Vertica (the commercial product, co-founded by Stonebraker in 2005), which became one of the leading data warehouse systems of the next decade. It directly influenced MonetDB, Apache Parquet (the de-facto columnar storage format used by Spark, Hive, and virtually every modern analytics engine), and Apache Arrow (the in-memory columnar format). Google's Dremel, Amazon Redshift, Snowflake, and ClickHouse all implement variants of C-Store's core ideas: column-oriented storage, projection-like materialized views, aggressive compression, and vectorized execution.

The WS/RS split with a Tuple Mover also proved prescient. Modern columnar systems (Delta Lake, Apache Iceberg) use exactly this architecture — a fast write-optimized layer (often an LSM-tree or a write-ahead log) that gets periodically compacted into a read-optimized columnar store — under the name lake house architecture. C-Store described this idea in 2005.

Why This Paper Matters for the Learner

Before C-Store, column storage was known (Sybase IQ had been selling it since the mid-1990s) but considered a niche product. C-Store's contribution was not the column store idea itself, but the complete system design that showed column storage could support transactions, high availability, and competitive write performance alongside world-class read performance — all in a single coherent architecture. It transformed column storage from a special-purpose tool into a general-purpose alternative to the row store.
