Scientific Paper · VLDB 2001

Generic Schema Matching with Cupid

Jayant Madhavan, Philip A. Bernstein, Erhard Rahm Proceedings of the 27th VLDB Conference, Roma, Italy, 2001
Abstract Schema matching — automatically finding correspondences between elements of two different database schemas — is a critical step in data integration, XML message mapping, and data warehouse loading. Most existing tools either use linguistic name matching or structural analysis, but rarely combine both well. This paper investigates the problem of generic schema matching: matching outside any particular data model or application. The authors present a taxonomy of past approaches, then propose Cupid, a new algorithm that discovers mappings between schema elements using their names, data types, constraints, and structural context. Cupid's key innovations include a thesaurus-based linguistic normalization phase, a bottom-up structural tree-matching algorithm that propagates similarity between nodes' leaf sets, and a bias toward leaf structure (where real data content resides). Experimental comparison with two other systems — DIKE and MOMIS-ARTEMIS — demonstrates that Cupid produces correct mappings in cases those systems miss, including context-dependent mappings that distinguish the same element name appearing in different structural contexts.

1. The Schema Matching Problem

Imagine you are building a data warehouse that consolidates purchase order information from two suppliers. Supplier A uses an XML schema called PO; supplier B uses a schema called PurchaseOrder. Both describe purchase orders, but their structures differ: what PO calls Lines with sub-element Item, PurchaseOrder calls Items with sub-element Item. What PO calls Qty (a shorthand), PurchaseOrder calls Quantity. What PO calls Uom (unit of measure), PurchaseOrder calls UnitOfMeasure.

A human expert can quickly see these correspondences. An algorithm must discover them automatically. This is the schema matching problem.

Definition — Schema Matching

Given two input schemas S1 and S2 in any data model, and optionally an initial mapping and auxiliary information (dictionaries, thesauri), produce a set of mapping elements — pairs (e1, e2) where e1 is an element of S1 and e2 is an element of S2 — indicating that these elements are semantically related. The mapping should pass user validation; the goal is automatic discovery, not replacement of human review.

Schema matching is inherently hard for three reasons. First, schemas are subjective: two different designers modeling the same domain will produce different schemas, and there may be multiple reasonable mappings. Second, schemas can differ in naming conventions: the same concept might be spelled out fully or abbreviated, use synonyms, or employ domain-specific jargon. Third, schemas can differ in structure: what one schema models as a single flat table, another might model as a nested hierarchy with foreign keys.

The paper's broader motivation is the Model Management vision of Bernstein, Halevy, and Pottinger: a general system for managing database models and schemas, where operations like Match, Merge, and Compose can be applied to schemas as first-class objects. Cupid is the Match operation implementation for that vision.

2. A Taxonomy of Matching Techniques

The paper organizes past schema matching approaches along several orthogonal axes. Understanding this taxonomy helps appreciate what makes Cupid different.

Schema-based vs. Instance-based. Schema-based matchers use only the structural information in the schema (names, types, constraints, hierarchy). Instance-based matchers also look at actual data values to infer correspondences. Cupid is purely schema-based — a deliberate choice, since instance data is often unavailable (e.g., when matching two schema files before any data has been loaded).

Element-level vs. Structure-level. Element-level matchers compare individual schema elements in isolation. Structure-level matchers compare combinations of elements — how they relate to their neighbors in the schema. Cupid is both: it begins with element-level linguistic matching, then uses structural analysis to refine those initial scores.

Linguistic vs. Constraint-based. Linguistic matchers use names, annotations, and text descriptions. Constraint-based matchers use data types, uniqueness constraints, referential integrity, cardinalities. Cupid uses both — names are the primary signal, but data type compatibility initializes the structural similarity.

Intuition — Why One Approach Is Never Enough

Pure linguistic matching fails when schemas use different abbreviations (Qty vs. Quantity) or when the same word appears in multiple contexts with different meanings (a schema might have both a Bill-of-Materials "Item" and an Invoice "Item" — which pairs with which?). Pure structural matching fails when schemas have similar names but very different structures, or when the structures are similar but names are totally different. Cupid combines both signals, using each to guide and constrain the other.

3. The Cupid Approach: Overview

Cupid computes two similarity coefficients for each pair of schema elements (s, t) where s is from schema S1 and t is from schema S2:

lsim(s, t) — the linguistic similarity, computed in Phase 1 from names, data types, and text annotations. Values are in the interval [0, 1], with 1 being a perfect linguistic match.

ssim(s, t) — the structural similarity, computed in Phase 2 from the similarity of the structural contexts (ancestors, siblings, and descendant leaves) of the two elements. Also in [0, 1].

The final weighted similarity is:

$$\text{wsim}(s,t) = w_{\text{struct}} \times \text{ssim}(s,t) + (1 - w_{\text{struct}}) \times \text{lsim}(s,t)$$

where $w_{\text{struct}}$ is a tunable constant in [0, 1] that controls how much weight to give structural vs. linguistic evidence. A mapping element is generated for a pair (s, t) when $\text{wsim}(s,t) \geq th_{\text{accept}}$, where $th_{\text{accept}}$ is an acceptability threshold.

The crucial design choice is that Cupid is biased toward leaves. Leaf nodes in a schema tree are the atomic elements — column values, XML attributes — where the actual data content lives. Non-leaf nodes (tables, XML elements with children) are structural containers. The authors observe that most schema content resides in leaves, and structural similarity between non-leaves is most reliably computed from the similarity of their leaf descendants rather than their immediate children.

4. Linguistic Matching

The first phase of Cupid computes linguistic similarity between pairs of schema elements. It proceeds in three steps: normalization, categorization, and comparison.

Normalization transforms schema element names into a canonical token set. This involves tokenization (splitting on punctuation, case changes — e.g., "ItemNumber" becomes ["Item", "Number"]), expansion (looking up abbreviations and acronyms in a thesaurus — "Qty" expands to "Quantity", "Uom" expands to "UnitOfMeasure"), and elimination of prepositions and articles. The result is a set of normalized tokens for each element name.

Categorization groups schema elements into categories based on their data types and linguistic content. For example, one category might contain elements representing monetary amounts (those with names tokenizing to words like "price", "cost", "amount" and with numeric data types). Categorization reduces the number of comparisons needed: only elements in the same or compatible categories are compared.

Comparison computes lsim coefficients between elements in the same categories. The thesaurus provides synonym and hypernym relationships, allowing "Bill" and "Invoice" to be recognized as synonyms, and "City" and "Municipality" as related. Sub-string matching catches cases where the thesaurus is incomplete.

Example — Linguistic Matching at Work

The PO schema has element Uom; the PurchaseOrder schema has UnitOfMeasure. After normalization: Uom expands (via thesaurus) to ["Unit", "Of", "Measure"] → tokens ["unit", "measure"]. UnitOfMeasure tokenizes directly to ["unit", "of", "measure"] → tokens ["unit", "measure"]. The token sets are identical after elimination of "of", so lsim = 1. Similarly, Qty expands to ["quantity"] which matches Quantity's tokens exactly. The thesaurus entry that "Bill" and "Invoice" are synonyms allows the system to recognize that POBillTo maps linguistically to InvoiceTo even though the names share no common tokens.

5. Structural Matching

After Phase 1 produces lsim coefficients, Phase 2 refines them by computing structural similarity. The key insight is that two schema elements that appear in similar structural contexts are more likely to be semantically related than two elements with similar names but very different contexts.

Cupid models schemas as schema trees. A simple relational schema maps naturally: the root represents the schema, each table is a child of the root, and each column is a leaf child of its table. An XML schema similarly maps to a tree of elements. The matching algorithm is defined on these trees.

The structural similarity of two leaf nodes s and t is initialized to the data type compatibility of their corresponding data types. Identical data types get compatibility 0.5 (a max of 0.5 leaves room for increases as structural evidence accumulates). Compatible types (e.g., INTEGER and FLOAT) get lower values. Incompatible types get 0.

For non-leaf nodes, structural similarity is computed as the fraction of leaves in the two subtrees that have at least one strong link — a link to a leaf in the other subtree with weighted similarity above the acceptance threshold:

$$\text{ssim}(s,t) = \frac{|\{x \mid x \in \text{leaves}(s) \wedge \exists y \in \text{leaves}(t),\, \text{stronglink}(x,y)\}| \;\cup\; |\{x \mid x \in \text{leaves}(t) \wedge \exists y \in \text{leaves}(s),\, \text{stronglink}(y,x)\}|}{|\text{leaves}(s) \cup \text{leaves}(t)|}$$

In plain words: two non-leaf nodes are structurally similar to the degree that their leaf descendants "match" each other. A node whose leaves all have strongly-matching counterparts in the other subtree gets a high structural similarity score.

6. The TreeMatch Algorithm

The TreeMatch algorithm computes structural similarities in post-order traversal — leaves first, then their parents, then grandparents, up to the roots. This bottom-up order ensures that when a non-leaf node's structural similarity is computed, all leaves in its subtree have already been compared.

The algorithm has a mutual feedback mechanism. When a pair of leaf nodes (s, t) has high weighted similarity ($\text{wsim}(s,t) \geq th_{\text{high}}$), the structural similarity of all leaf pairs in the same subtrees is increased by a factor $c_{\text{inc}}$. The rationale: if the leaves of two subtrees are highly similar, the leaves of the same subtrees in other positions are also likely to be related, so they deserve a structural boost.

Conversely, when a pair of leaf nodes has low weighted similarity ($\text{wsim}(s,t) < th_{\text{low}}$), the structural similarities of other leaf pairs in those subtrees are decreased by a factor $c_{\text{dec}}$. This propagates negative evidence: if the leaves of two subtrees mostly don't match, it is unlikely that other leaves in those subtrees are related either.

Intuition — Mutual Reinforcement

Think of the algorithm as building a case from multiple pieces of evidence. If I find that POBillTo and InvoiceTo have leaves City and Street that both match strongly (because their names are identical and their data types match), then I should increase my confidence that other leaves of POBillTo and InvoiceTo — like PostalCode and ZipCode — also correspond, even if their name similarity alone is low. The structural boost propagates this confidence. This is why context matters: the algorithm learns that POBillTo and InvoiceTo are in the same structural neighborhood, so their leaves are likely related.

The post-order traversal ensures that these similarity updates are computed before the parent nodes are processed. The result is a mutually consistent set of similarity scores: leaves that appear together in a well-matched subtree reinforce each other's scores.

7. Combining Similarities and Generating Mappings

After TreeMatch completes, each pair (s, t) has both an lsim and an ssim score. The final weighted similarity is computed as above. Mapping elements are generated for pairs where wsim exceeds the acceptance threshold.

For leaf elements, mapping generation is straightforward: for each leaf t in the target schema, find the leaf s in the source schema with the highest weighted similarity above the threshold, and report the mapping element (s, t).

For non-leaf elements, a second post-order traversal is needed: after the leaf-level mappings may have changed leaf similarity scores during TreeMatch, non-leaf structural similarities must be recomputed to reflect the final state.

The resulting mapping may be 1:n — one source element mapping to multiple target elements — since Cupid allows a single source leaf to map to many target leaves. Whether 1:1 mappings are required depends on the downstream tool consuming the match result (e.g., a query discovery module might require 1:1 mappings).

8. Extending to General Schemas

Real schemas are rarely pure trees. Relational schemas have foreign keys that create cross-table references. XML schemas have shared types referenced by multiple elements. UML schemas have class hierarchies and associations.

Cupid handles these by converting general schemas to schema trees via a pre-order traversal that expands each element's multiple paths into separate tree nodes (one per path). For example, if an XML element Address is referenced by both DeliverTo and InvoiceTo, the schema tree gets two copies of the Address subtree — one under DeliverTo and one under InvoiceTo. This expansion enables context-dependent matching: DeliverTo.City can match a different target than InvoiceTo.City.

Referential integrity constraints (foreign keys in relational schemas, ID/IDREF pairs in XML DTDs) are modeled as join view nodes — virtual nodes that aggregate the source table's foreign key column and reference the target table's primary key. These nodes allow Cupid to match a join relationship in one schema against a flat relationship in the other: if one schema expresses a customer-order relationship as a foreign key join and another expresses it as a nested element, the join view node makes them structurally comparable.

9. Experimental Comparison

Cupid was compared against DIKE (a rule-based schema-based matcher using a Lexical Synonymy Property Dictionary) and MOMIS-ARTEMIS (a linguistic and structural matcher that works on ER models, using ODB-Tools for name affinity and clustering). The comparison used both canonical test schemas designed to isolate specific properties, and real-world XML purchase order schemas (CIDX and Excel formats from BizTalk.org).

Key findings from the canonical example comparison:

All three systems correctly handle identical schemas and schemas with same names but different data types. Cupid and DIKE handle different nesting (item 5 in the paper's Table 1); MOMIS-ARTEMIS does not. Only Cupid handles type-substitution / context-dependent mappings (item 6) — distinguishing between two elements with the same name appearing under different parents, and mapping each to its correct counterpart.

In the real-world CIDX-Excel purchase order example, Cupid correctly identifies all the expected XML-attribute matching pairs, including the difficult case of CIDXline mapping to Excel.itemNumber (which has no supporting thesaurus entry — the match was made purely from data-type and structural similarity). DIKE misses several mappings because it requires explicit LSPD dictionary entries. MOMIS-ARTEMIS clusters related elements together and misses attribute-level matches when elements with the same name (like Street1–Street4 in one schema) are not mapped 1:1.

10. Impact and Legacy

The Cupid paper became a foundational reference for the schema matching community. Its taxonomy of matching techniques — schema-based vs. instance-based, element-level vs. structure-level, linguistic vs. constraint-based, individual vs. combinational — remains the standard framework for classifying and comparing matching approaches.

The specific ideas of leaf-biased structural similarity and post-order bottom-up propagation with mutual reinforcement were influential. They appeared in subsequent work on ontology matching, XML schema integration, and mediation systems throughout the 2000s.

Perhaps most importantly, the paper demonstrated that schema matching could be studied as an independent computational problem — not just as a component inside a larger integration system. This framing enabled subsequent benchmark efforts, public datasets, and systematic algorithm comparisons that advanced the field considerably. The Ontology Alignment Evaluation Initiative (OAEI), which began in 2004 and continues today, follows the competitive evaluation spirit of this paper's comparative study.
