F1: A Distributed SQL Database That Scales

Jeff Shute, Radek Vingralek, Bart Samwel, Ben Handy, Chad Whipkey, Eric Rollins, Mircea Oancea, Kyle Littlefield, David Menestrina, Stephan Ellner, John Cieslewicz, Ian Rae, Traian Stancescu, Himani Apte Proceedings of the VLDB Endowment, Vol. 6, No. 11 · PVLDB 2013
Abstract F1 is a distributed relational database system built at Google to support the AdWords business — Google's primary revenue engine. It is a hybrid database combining the high availability and scalability of NoSQL systems like Bigtable with the consistency and usability of traditional SQL databases. F1 is built on top of Spanner, which provides synchronous cross-datacenter replication and strong consistency. Synchronous replication implies higher commit latency (50–150 ms), but F1 mitigates that latency through a hierarchical schema model with structured data types, and through careful application design. F1 also includes a fully functional distributed SQL query engine and automatic change tracking and publishing.

1. Introduction

The name F1 is a genetics term. A Filial 1 hybrid is the first generation offspring from a cross mating of two distinctly different parental types — and that metaphor captures the paper's central claim precisely. F1 the database is such a hybrid: it takes the relational power of traditional SQL databases and welds it onto the scalability backbone of Google's NoSQL infrastructure. The result should, in theory, be impossible. Prior work argued that strong consistency, high availability, and SQL-level usability are mutually exclusive at global scale. F1 is Google's demonstration that they are not.

Before F1, AdWords ran on a sharded MySQL deployment. MySQL is excellent for small-to-medium workloads, but sharding introduces a set of problems that compound as scale increases. Shards are rigid: resharding data without breaking applications is painful and time-consuming. Joins across shards require application-level logic. Availability suffers because each shard is a single point of failure. The engineering team found themselves spending enormous effort working around the limitations of sharded MySQL rather than building features. Google decided to replace it entirely.

The Four Design Goals of F1

The paper enumerates four non-negotiable requirements that drove every design decision:
Scalability — trivially add capacity by adding machines, with no manual resharding.
Availability — five nines even during datacenter outages and planned maintenance.
Consistency — full ACID transactions; applications must always see correct, non-stale data.
Usability — full SQL, secondary indexes, ad hoc queries; things developers expect from a real database.

These goals had long been considered mutually exclusive. The NoSQL wave of the 2000s was premised on the idea that you give up consistency and SQL to get scalability. F1's thesis is that this trade-off is not fundamental — it is merely the result of engineering choices made when building disk-oriented, single-machine relational databases. Build fresh, with Spanner as the storage substrate, and you can have all four.

2. The Problem with MySQL at Scale

To understand F1's design, you have to understand what went wrong with sharded MySQL. The AdWords team had horizontally partitioned their data across many MySQL servers — each server owned a range of customer accounts. This approach works until it doesn't. Here is what breaks first.

Example — The Resharding Nightmare

Suppose a new large advertiser joins AdWords and their data lands on shard 3. As their campaigns grow, shard 3 becomes the hot shard. To rebalance, engineers must migrate rows from shard 3 to a new shard 7. During migration, applications need to know which shard to talk to, so every application needs to be updated or a routing layer needs to be modified. If anything goes wrong mid-migration — a server crash, a network partition — the data may be inconsistent across shards. This process took weeks and required application changes. F1 on Spanner makes this completely transparent: Spanner re-partitions data automatically, and F1 servers never hold data locally, so there is nothing to migrate.

Beyond resharding, sharded MySQL made joins expensive. AdWords queries routinely need to join a customer's campaigns with their ad groups with their keywords. In a sharded schema, those tables live on the same shard only if all rows happen to be co-located by customer ID. Cross-shard joins require application code to fetch from multiple servers and stitch results together. This logic is hard to write correctly and even harder to maintain.

Availability was the final nail. A sharded MySQL deployment with three replicas per shard can tolerate one server failure per shard, but a datacenter outage takes down an entire geographic region. Google's AdWords operations require five-nines availability — roughly 5 minutes of downtime per year. Sharded MySQL, even with heroic operational effort, could not guarantee that.

3. Basic Architecture

F1 is deliberately designed to be stateless at the server layer. Clients talk to one of many F1 servers, which are responsible for reading and writing data from remote data sources and coordinating query execution. The underlying storage is Spanner, which handles persistence, caching, replication, fault tolerance, data sharding, and transactions. F1 servers do not own data, so adding or removing them requires no data movement whatsoever.

Intuition — Why Stateless Servers Are Powerful

In a traditional database, the server and the storage are the same machine. This coupling means that every failure of the server is also a data availability event. In F1, the server is just a query execution engine — a piece of software that translates SQL into Spanner RPCs. If an F1 server dies, the client simply reconnects to another F1 server and retries. No data is lost. No recovery is needed. This separation of computation from storage is the same architectural insight behind cloud databases today — F1 was doing it at production scale in 2013.

The F1 cluster has several additional components. A load balancer distributes incoming requests across F1 servers. An F1 master monitors server health and maintains a list of available slave processes. A slave pool consists of F1 processes that exist to execute subplans of distributed queries — they are the workers that fan out across the data when a large OLAP query is run. F1 also integrates with Google's MapReduce framework for large-scale batch processing.

Below F1 servers sit the Spanner servers, co-located in the same datacenters. In the AdWords deployment, five datacenters are spread across the US, using 5-way Paxos replication. Every committed write is synchronously acknowledged by a majority of replicas before it is considered durable. This is the source of F1's strong consistency guarantee — and its latency cost.

4. Hierarchical Schema and Data Model

The most distinctive design choice in F1 is its hierarchical schema. This is the primary mechanism by which F1 hides the latency of a globally distributed storage layer from applications.

In a traditional relational schema, tables are flat and independent. You might have a Customer table keyed by CustomerId, a Campaign table keyed by CampaignId with a foreign key to Customer, and an AdGroup table keyed by AdGroupId with a foreign key to Campaign. In physical storage, these three tables are scattered independently across the storage system. To retrieve all campaigns and ad groups for a given customer, you need three separate reads — potentially three separate round trips to three separate storage nodes.

Definition — Hierarchical Clustering in F1

In F1's hierarchical schema, child tables are physically interleaved within the rows of their parent tables. A child table's primary key must contain the parent's primary key as a prefix. For example, Campaign's primary key is (CustomerId, CampaignId), and AdGroup's is (CustomerId, CampaignId, AdGroupId). Physically, Spanner stores all Campaign and AdGroup rows for a given Customer together in a single directory — a contiguous range of the key space that is typically stored on one server. This means all the data for one customer can be read with a single Spanner request.

The performance implication is substantial. With traditional flat tables, reading a customer's complete advertising hierarchy requires sequential dependent RPCs — fetch campaigns, then for each campaign fetch ad groups, and so on. With hierarchical clustering, F1 issues one request to Spanner for the whole directory, and Spanner returns the data in an interleaved depth-first order. F1 then uses a cluster join algorithm that streams through this interleaved output in one pass, producing joined rows without buffering entire tables. The number of Spanner RPCs drops from O(depth) to O(1).

Intuition — The Analogy to Nested Files

Think of hierarchical clustering like a folder structure. In the traditional schema, Customer, Campaign, and AdGroup files are scattered across different directories on different drives. To assemble a complete customer record you have to open three different drawers. In F1's schema, everything for Customer 42 is in one folder: the Customer row is the folder itself, and Campaign rows and AdGroup rows are filed inside it in order. Fetching Customer 42's data means opening one drawer and reading everything inside, in sequence, with no random seeks.

The hierarchical schema also enables a key optimization for writes. In a transaction that updates data under a single root row — a single advertiser's hierarchy — all the modified data is in one Spanner directory. The transaction involves only one Spanner group, so it uses single-phase commit rather than two-phase commit (2PC). This saves one network round trip per transaction, which at the 50 ms inter-datacenter latency scale is not trivial. The paper recommends that application developers design their schemas to keep most transactions within a single root, and the AdWords team found this to be achievable for the vast majority of workloads.

F1 also supports Protocol Buffer columns. Protocol Buffers are Google's schema-and-binary-encoding library for structured data interchange. In F1's schema design, columns can hold entire protocol buffer messages, including nested messages and repeated fields. This allows a table to store a rich structured object in a single column without breaking it across multiple child rows. Protocol Buffer columns reduce impedance mismatch between the database and application code — the application already works with protocol buffers everywhere in Google's stack — and they can dramatically reduce the number of child tables required in a schema.

5. Indexing Strategy

All indexes in F1 are transactionally consistent and fully maintained — they never lag behind the data, unlike eventually-consistent secondary indexes in some NoSQL systems. Indexes are stored as separate tables in Spanner, keyed by the index key concatenated with the indexed table's primary key.

F1 distinguishes two types of indexes by their physical placement. A local index key must begin with the root row's primary key, so index entries live in the same Spanner directory as the rows they index. Updating a local index costs no additional Spanner participants — the transaction stays within its existing directory, and commit latency is unaffected.

A global index, by contrast, spans all root rows. An example is an index on Keyword across all customers — useful for finding which customers use a given keyword across the entire AdWords ecosystem. Because global index entries are not co-located with any particular root, updating them requires a 2PC transaction across multiple Spanner groups. This adds latency and can become a scalability bottleneck at high write rates. The paper advises using global indexes sparingly and designing applications to use small write transactions when tables have global indexes.

Watch Out — Global Indexes and 2PC

Consider a transaction that inserts 1,000 rows, each requiring a global index update. Those 1,000 index entries may be spread across hundreds of Spanner index directories. The 2PC transaction now has hundreds of participants, multiplying both latency and abort probability. The paper explicitly warns against this pattern and recommends batching writes or using local indexes wherever business requirements permit.

6. Asynchronous Schema Changes

Schema changes in a massively distributed system are surprisingly hard. In a single-server database, adding a column or an index briefly locks the table. In F1, "briefly locking the table" means blocking all transactions across hundreds of F1 servers in five datacenters — a plainly unacceptable user experience for a 24/7 advertising platform.

F1's solution is to make all schema changes non-blocking and asynchronous. The schema change is applied at different times on different F1 servers, meaning that at any moment, some servers are using schema $S_1$ and others are using schema $S_2$. This is fine as long as you can guarantee consistency. The danger is illustrated by a concrete example in the paper: if server $M_1$ uses the old schema (without index $I$) and server $M_2$ uses the new schema (with index $I$), then $M_2$ may insert a row and its index entry, but $M_1$ may later delete the row without deleting the index entry — leaving a spurious dangling index reference.

The F1 schema change algorithm prevents this by enforcing that at most two different schemas are active across all F1 servers at any time. It subdivides each schema change into multiple fine-grained phases, where consecutive phases are guaranteed to be mutually compatible. For example, when adding index $I$, the algorithm first introduces a phase where $I$ exists in a write-only mode — all servers begin maintaining $I$ on new writes, but reads cannot yet use it. Only after a full backfill of all existing rows does the index transition to read-write mode and become visible to queries. This eliminates the category of anomalies described above.

Pause and Reflect

The schema change problem is a microcosm of distributed systems design. The naive approach — broadcast the change to all servers simultaneously — fails because "simultaneously" is impossible across a wide-area network. The sophisticated approach — reason carefully about which pairs of schema states are safe to co-exist — allows a live system to evolve its structure without a maintenance window. This same challenge reappears in any system that stores state redundantly across replicas.

7. Transactions: Three Flavors

F1 provides three transaction types, each suited to different workloads and with different consistency and latency profiles. All are built on top of Spanner's native transaction support.

Definition — Snapshot Transactions

Snapshot transactions are read-only transactions with snapshot semantics. Every snapshot transaction reads data as of a fixed Spanner snapshot timestamp. By default, this is Spanner's global safe timestamp — a timestamp guaranteed to be in the past by 5–10 seconds, such that no in-flight transaction can possibly commit at or before it. Reads at this timestamp can run on any replica, including read-only replicas, and they never take locks and never block. This is the default mode for SQL queries and MapReduce jobs in F1.

Definition — Pessimistic Transactions

Pessimistic transactions map directly to Spanner's built-in pessimistic transactions, which use strict two-phase locking. All requests within a single pessimistic transaction must go to the same F1 server for the duration of the transaction. Reads can request shared or exclusive locks. This mode is appropriate when the application needs to hold locks to prevent concurrent modification — for example, enforcing uniqueness invariants or maintaining a counter.

Definition — Optimistic Transactions

Optimistic transactions are the default for client-initiated read-write transactions. They proceed in two phases. During the read phase — which may take arbitrarily long and never acquires Spanner locks — the transaction reads data normally. Each row returned by F1 carries a hidden lock column containing the last-modification timestamp. During the short write phase, the client sends all reads' lock columns back to an F1 server, which creates a short-lived pessimistic Spanner transaction, re-reads every lock column, and checks whether any has been modified since the client read it. If yes, the transaction aborts (conflicting write detected). If no, the writes are sent to Spanner and committed.

Optimistic transactions have substantial advantages in a geo-distributed environment. Because the read phase holds no locks, long-running reads (including those involving user interaction or expensive computation) cannot cause lock contention. If the client crashes mid-transaction, there are no orphaned locks to time out. The commit is self-contained and can be retried on a different F1 server after a transient failure. These properties are critical in the AdWords ecosystem, which has thousands of applications and diverse transaction patterns.

Watch Out — Optimistic Transaction Pitfalls

Optimistic transactions have two important limitations. First, they cannot detect insertion phantoms — if a transaction reads a set of rows and another transaction inserts a new row into that set before commit, the optimistic transaction will not detect this (since modification timestamps only exist on rows already present). The paper recommends using parent-table lock columns to guard against phantoms. Second, under high write contention — for example, a counter that many clients increment concurrently — most optimistic transactions will abort at commit time because their read timestamps are stale. In such cases, pessimistic transactions with exclusive locks are more appropriate.

8. Change History

Change History is a first-class feature of F1, not an afterthought. The motivation comes directly from AdWords business requirements: the approval system needs to know when new ads are inserted; billing needs an audit trail; caching layers need to know exactly what changed and when, so they can apply incremental updates rather than reloading entire datasets.

In the old MySQL system, change history was maintained by Java application libraries that inserted records before and after each write. This was never 100% reliable — Python scripts, manual SQL updates, and some classes of changes bypassed the library entirely. F1 moves change history into the database engine, where it can be guaranteed.

Every transaction in F1 creates one or more ChangeBatch protocol buffer messages containing the primary key and before/after values of every changed column. ChangeBatches are stored as child rows of the root row they describe, in normal F1 tables. Because they are stored close to the data they describe, they do not add extra participants to Spanner transactions, and their write cost is minimal.

Example — Using Change History for Cache Invalidation

The AdWords web UI maintains an in-memory cache of customer data. When a user commits an update, the next page they render must reflect that update — stale cache data would be a visible bug. The cache client stores the root row key and the commit timestamp of the last write it must see. When it reads from the cache, it checks whether the cache's watermark is newer than that timestamp. If the cache is behind, the client reads Change History records newer than its checkpoint and applies those delta changes to the in-memory state. This is far cheaper than reloading the entire customer record and far more reliable than a cache-invalidation message that might be lost.

9. Query Processing

F1 includes a fully functional distributed SQL query engine. It supports both centralized execution — the whole query runs on one F1 server, appropriate for short OLTP-style queries — and distributed execution — the query plan is fanned out across many F1 slave workers in the slave pool, appropriate for large OLAP queries.

A distributed query plan is organized as a directed acyclic graph (DAG) of plan parts. Each plan part represents a set of worker processes executing the same subplan. Data flows from leaves to a single root node — the query coordinator — which performs final aggregation and returns results to the client. Plan parts communicate by streaming data over the network in RPCs; there is no disk spilling in the normal case.

Intuition — Why Batching Matters More Than Caching

Traditional databases optimize to minimize disk seeks and cache as much data in memory as possible, because disk is slow and memory is fast. In F1, all data is remote — it lives in Spanner, across the network. The relevant dichotomy is not disk vs. memory but sequential vs. random network access. A single RPC to Spanner that fetches 50 MB of sequential data in one shot is cheap. Thousands of individual RPC round-trips to fetch the same data one row at a time is expensive. F1's query operators are designed around this insight: the lookup join operator, for example, accumulates up to 50 MB worth of outer-table keys before issuing a single simultaneous lookup into the inner table. Batching transforms what would be serial latency into parallel throughput.

For repartitioning — the operation of redistributing data among workers by a different key — F1 uses hash repartitioning exclusively. Range partitioning would require global statistics about key distributions, which are hard to maintain accurately. Hash repartitioning is stateless and deterministic: a hash function maps each row's key to one of $N$ worker buckets, and any worker can independently determine its bucket assignment. Modern network switch hardware allows all F1 workers to communicate at close to full line rate simultaneously, making hash repartitioning practical at the scale of a single cluster.

The cluster join algorithm is another query processing innovation specific to F1's hierarchical data model. When joining a parent table with a child table that are co-located in Spanner's hierarchical clustering, F1 can issue one request to Spanner that returns both tables' rows in interleaved depth-first order. The cluster join operator processes this stream one row at a time, maintaining only one buffered row per table, and emits joined rows as they arrive. This requires zero disk spilling and minimal memory, regardless of table size.

10. Latency, Throughput, and Lessons

The AdWords F1 deployment uses five datacenters spread across the continental US, with 5-way Paxos replication. With leaders on the east coast, a commit requires a round trip to the two nearest replicas. The 50 ms inter-datacenter latency means commit latency is typically 50–150 ms — significantly higher than local MySQL, which committed in under 5 ms.

The paper reports that despite this, observable user-facing latency on the main AdWords web application is approximately 200 ms — about the same as the old MySQL system. How? The engineering team restructured client code to avoid serial reads. With the new ORM, user requests typically require at most 10 reads, all of which can be issued in parallel. The reads are batched into a small number of Spanner RPCs. The minimum latency is slightly higher than MySQL (due to network round-trip cost), but the latency tail — the worst-case latency for large customers — is dramatically better, because F1 uses parallelism that MySQL could not.

Example — Throughput for Bulk Applications

For applications that need throughput rather than low latency — such as batch processing pipelines that update billions of rows per day — F1 achieves very high throughput for parallel writes. A pipeline designed to run 500 transactions per second with single-directory transactions (one Spanner group each, no 2PC) is practical. F1 and Spanner do not become a bottleneck; the rate limits are usually chosen to protect downstream Change History consumers.

The paper is candid about resource costs: F1 queries use an order of magnitude more CPU than equivalent MySQL queries. MySQL stored data uncompressed on local disk and was bottlenecked on I/O. F1 starts from compressed network data and passes it through decompression, processing, recompression, and network transmission — all CPU-intensive steps. The authors identify this as an area for future improvement.

11. Impact and Legacy

F1 went into production on AdWords in early 2012 and by the time of the paper managed over 100 TB of data, serving hundreds of thousands of requests per second and scanning tens of trillions of data rows per day. Availability reached five nines even in the presence of unplanned outages. The observable latency tail for AdWords web applications did not increase compared to the old MySQL system.

The paper's conclusion is significant: it refutes the conventional wisdom that scalable, available, and consistent databases are mutually exclusive. The trade-off is not fundamental — it is merely the artifact of building databases on local disk-based storage with single-machine transaction models. By building on Spanner's global consistent storage and choosing architectural patterns (hierarchical schema, stateless servers, optimistic transactions, async schema change) that are compatible with high latency, Google showed that a SQL database can scale horizontally without sacrificing ACID guarantees or SQL expressiveness.

F1's influence is visible in the generation of cloud-native relational databases that followed: Google Cloud Spanner (the externalized version of Spanner, with F1-like SQL on top), CockroachDB (which explicitly cites Spanner and F1), YugabyteDB, and others. The hierarchical data model reappears in document-oriented databases. The asynchronous online schema change algorithm has been replicated in open-source tools like gh-ost and pt-online-schema-change used widely in the MySQL ecosystem. The paper is one of the most influential systems papers of the 2010s.
