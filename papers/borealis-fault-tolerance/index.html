Fault-Tolerance in the Borealis Distributed Stream Processing System

Magdalena Balazinska, Hari Balakrishnan, Samuel Madden, Michael Stonebraker ACM SIGMOD, June 2005, Baltimore, Maryland
Abstract Borealis is a distributed stream processing engine that must keep producing results even when nodes crash, network links fail, or partitions split the system. This paper presents a replication-based fault-tolerance protocol that trades the degree of output inconsistency against availability using a user-specified time threshold. Replicas are kept in sync by a deterministic serializing operator called SUnion, which orders tuples from multiple input streams into a canonical sequence. When an upstream neighbor becomes unavailable, a node may continue processing on partial inputs, emitting tentative tuples that can be corrected later. After the failure heals, nodes reconcile their internal state via either checkpoint/redo or undo/redo techniques and stabilize their outputs. Experiments show that checkpoint/redo achieves faster reconciliation while undo/redo consumes less memory, and that continuously processing new tuples during both failure and reconciliation (the "Process & Process" strategy) best satisfies the availability requirement while producing the fewest tentative tuples.

1. The Problem: Streams in the Wild

Imagine a network-monitoring application that ingests packet-header streams from hundreds of routers simultaneously. The application joins these streams, computes traffic anomaly scores, and pushes alerts to a security dashboard — all in real time. Traditional database systems are useless here: data arrives continuously, results must be produced within seconds, and the volume is far too large to store-and-query in the classic sense. What is needed is a stream processing engine (SPE), a system that evaluates continuous queries over time-windowed data as it flows through a directed graph of operators.

Borealis, the successor to Aurora and Medusa developed at MIT and Brandeis, is exactly such an engine. But stream processing at scale is inherently distributed: data sources are geographically dispersed, and the operator graph is spread across many processing nodes to handle load. Distributed systems fail. Nodes crash. Links partition. The question the authors address is: how can a distributed SPE keep producing useful results despite failures, without necessarily halting until every fault is repaired?

Intuition — why streaming fault-tolerance is different from database fault-tolerance

In a traditional database, correctness means serializability: either a transaction committed or it did not. A database can simply refuse to answer queries while it recovers. In a stream engine, refusing to produce output is itself a failure: the intrinsic value of a stream result is its timeliness. A security system that stops alerting for 30 seconds during a router failure may miss the attack window entirely. The designers of Borealis therefore deliberately separate two orthogonal concerns: availability (does the system keep producing output at all?) and consistency (are those outputs correct?). Neither fully implies the other, and both must be managed explicitly.

Prior work on high-availability streaming either ignored network failures entirely (handling only node crashes) or required that at least one fully connected copy of the query network exist to continue processing, which is an extremely strong assumption. Borealis relaxes both constraints, offering a configurable trade-off governed by a single user-specified parameter: the maximum delay $X$. Any new input tuple must be processed and a result produced within delay $X$, regardless of what other streams are doing. Choosing a larger $X$ gives the system more time to wait for a stable upstream replica, thus producing fewer wrong answers but sacrificing timeliness. Choosing a smaller $X$ keeps latency tight but forces the system to proceed on partial information, producing more tentative tuples.

2. Model and Design Goals

The system model is a directed acyclic graph of operators — filters, aggregates, joins, unions — spread across $G$ processing nodes. Each node may have $N$ replicas (including itself), and the system tolerates up to $N - 1$ simultaneous node failures. Failures are either fail-stop (node crashes cleanly) or network partitions (nodes lose connectivity to one another). Data sources and clients communicate with the SPE through proxies that log input tuples persistently before forwarding, so all replicas eventually see the same input sequence despite source failures.

Definition — Tentative vs. Stable Tuples

A stable tuple is the result of processing a complete, consistent set of inputs. It is immutable. A tentative tuple is the result of processing a subset of inputs (because some upstream streams were unavailable); it may subsequently be amended. An undo tuple signals that a suffix of previously emitted tuples should be deleted and replaced. Tentative tuples are marked as such so downstream nodes can decide whether to act on them immediately or wait for stabilization.

The core design goal is to minimize the number of tentative tuples $N_{\text{tentative}}$ produced, subject to the constraint that the processing delay for every new tuple remains below $X$. Because tentative tuples are a proxy for replica inconsistency, minimizing them directly reduces the downstream burden of reconciliation. The authors also require eventual consistency: once all failures heal, every client must eventually receive the correct, complete, stable output stream.

3. Stable vs. Tentative: The Data Model

Borealis extends the standard stream tuple to include two fields: tuple_type (STABLE, TENTATIVE, UNDO, BOUNDARY, etc.) and tuple_time, a logical timestamp. Tuples on a stream are never re-ordered within that stream because nodes communicate over reliable in-order channels (TCP). The challenge arises at operators with multiple input streams — joins and unions — where tuples from different streams may arrive at wildly different rates.

To handle multi-stream ordering, the authors introduce boundary tuples: periodic heartbeats sent by data sources with a guaranteed property — no tuple with a $\texttt{tuple\_time}$ smaller than the boundary's will ever arrive after it on that stream. Boundary tuples play the role of "punctuation" in the stream, allowing operators to close and output time windows as soon as all inputs for that window have been seen. Without them, a join would have to wait indefinitely for the slower stream.

Example — Why a Join Blocks Without Boundaries

Suppose a join combines a fast stock-price stream (1000 tuples/s) with a slow reference stream (1 tuple/s). The join cannot output a result for time window [t, t+d] until it knows no more tuples in that window will arrive from the slow stream. Without boundaries, it must buffer the fast stream indefinitely. With boundaries, the slow stream periodically asserts "I have sent all tuples up to time $t$," allowing the join to flush the window safely.

4. SUnion: The Key to Replica Consistency

The central technical contribution is a new operator called SUnion (Serializing Union). Its purpose is deceptively simple but crucial: given multiple input streams (one per replica of an upstream operator), SUnion merges them into a single output stream with a deterministic, canonical ordering that all replicas produce identically.

Why does ordering matter? Because the state of a stateful operator — like an aggregate computing a running sum — depends on the sequence of inputs it has processed, not just the set. If replica A processes tuple $p$ before tuple $q$ and replica B processes them in the opposite order, their internal states diverge even though both processed the same tuples. SUnion ensures that every downstream replica sees tuples in the same order, so their states remain identical and they produce identical outputs.

Definition — How SUnion Works

SUnion places incoming tuples into fixed-width time buckets based on their tuple_time value. It then sorts the contents of each bucket using a deterministic function (typically by increasing tuple_time, with ties broken by a secondary rule). A bucket is declared stable only after boundary tuples from all input streams guarantee that no further tuples with timestamps in that bucket can arrive. At that point, SUnion forwards the bucket's contents to downstream operators as stable tuples, in the canonical order.

SUnion is similar to the Input Manager in the STREAM system, but with a critical difference: it explicitly distinguishes failures (missing data that will never arrive) from delays (data that is late but will eventually arrive). This distinction is what allows Borealis to implement the availability/consistency trade-off: a delayed SUnion can choose to forward tentative results when the delay budget $X$ is about to expire, rather than blocking forever.

5. The Three-State Machine

Each node in Borealis runs a state machine with three states: STABLE, UP_FAILURE, and STABILIZATION. Understanding these states is the key to understanding the whole fault-tolerance protocol.

Definition — Node States

STABLE: All upstream neighbors are reachable and sending stable data. The node processes tuples normally and passes stable results downstream.

UP_FAILURE: At least one upstream neighbor has become unavailable. The node must decide whether to suspend (block), delay new tuples, or process them tentatively. It emits tentative tuples marked as such.

STABILIZATION: The failed upstream neighbor has come back (or a STABLE replica has been found). The node must reconcile its internal state by correcting the tentative tuples it emitted during UP_FAILURE, and stabilize its output before returning to STABLE.

The transitions are managed by two auxiliary operators inserted into every query network. SUnion, placed at each node's inputs, handles upstream monitoring and data ordering. SOutput, placed at each output stream crossing a node boundary, handles output stabilization — it buffers output tuples, generates the undo tuple when stabilization begins, and forwards the corrected stable versions when reconciliation completes.

Intuition — Why "Process During Failure" Beats "Block"

Blocking during UP_FAILURE produces zero tentative tuples but violates the delay bound $X$ for any failure lasting longer than $X$. Delaying tuples (buffering new arrivals) keeps the door open to finding a stable replica in time, producing fewer tentatives than immediate processing, but also eventually violates $X$ for long failures. Processing immediately produces the most tentatives but always meets the delay bound. For a distributed chain of nodes, the authors find that Process during both UP_FAILURE and STABILIZATION is the strategy that best maximizes availability while minimizing tentative tuples — a counter-intuitive result that falls out of the cascade effect in reconciliation.

6. Reconciliation: Checkpoint vs. Undo/Redo

After a failure heals, the node enters STABILIZATION and must reconcile its state: revert to what it should have computed had all inputs been available, then re-process. The paper explores two approaches borrowed and adapted from traditional database recovery theory.

Checkpoint/Redo Reconciliation

Periodically during STABLE operation, the system takes a full snapshot (checkpoint) of every operator's state and the boundary tuple identifiers at that point. SUnion buffers all input tuples received after the checkpoint. When reconciliation begins, the node reloads the checkpoint and replays all buffered inputs from that snapshot forward. The replay is deterministic and, with the full set of inputs now available, produces the correct stable output. This approach requires storing the operator state snapshot (size $S$) plus all tuples buffered since the checkpoint.

Undo/Redo Reconciliation

Rather than checkpointing state, each operator implements an undo method. When a tentative tuple must be retracted, the operator scans backward through its input buffer to the oldest tuple that still contributes to the current window — the stream marker — undoes its effects, and reprocesses forward from there. SUnion buffers only the tentative input tuples (not stable ones, which can be discarded). This consumes less memory than checkpoint/redo because there is no need to store a full state snapshot, but it requires more CPU time during reconciliation because the state must be rebuilt by re-processing rather than loading from a snapshot.

Pause and Compare

Both approaches have the same goal — restore the node to the correct state — but they differ in their time/space trade-off. Checkpoint/redo's reconciliation time is roughly $S \cdot p_{\text{copy}} + (D + 0.5l)\lambda \cdot p_{\text{proc}}$, where $D$ is the failure duration, $l$ is the checkpoint interval, and $\lambda$ is the aggregate tuple rate. Undo/redo's time is dominated by replaying the entire undo log plus re-processing, so it is slower when the operator state is large. In experiments, checkpoint/redo is faster for large operator state sizes; undo/redo uses less memory (no state snapshot needed) and can propagate reconciliation only along the paths actually affected by the failure.

7. Experimental Results

The authors implement both mechanisms in the Borealis prototype and run experiments on single nodes and multi-node chains. The basic setup is a query network of three input streams, an SUnion, a Join, and an SOutput, processing 3000 tuples/s in aggregate. Failures are simulated by temporarily disconnecting one input stream.

The key finding from single-node experiments is that, for failures shorter than $\alpha X$ (where $\alpha$ is roughly 0.9 in the experiment), the node can simply delay new tuples and produce zero tentative output, because it is likely to find a stable replica before the delay budget expires. For longer failures, the node must process and accept tentative output. The number of tentative tuples grows linearly with both the delay parameter $\alpha X$ and the failure duration.

For multi-node chains of length 1 through 4, the Process & Process strategy (process new tuples without delay during both UP_FAILURE and STABILIZATION) dominates: it keeps $\text{Delay}_{\text{new}}$ bounded by $k \cdot X$ where $k$ is the chain length, while minimizing $N_{\text{tentative}}$. Strategies that suspend tuples during STABILIZATION compound their delays multiplicatively at each node — for a chain of 4, this can push $\text{Delay}_{\text{new}}$ far beyond $X$.

Example — Reconciliation Overhead

With a 5-second failure and a state size of 1000 tuples, checkpoint/redo reconciliation completes in roughly 1 second (dominated by the cost of copying the state snapshot), while undo/redo takes about 1.5 seconds (dominated by rebuilding the state by re-processing the undo log). However, the SUnion serialization delay adds a latency overhead proportional to the bucket size: at a 200 ms boundary interval, the average end-to-end delay is about 234 ms — a modest price for deterministic replica ordering.

8. Lasting Impact

Borealis's fault-tolerance paper introduced several ideas that have become standard vocabulary in the stream processing literature. The notion of tentative vs. stable outputs — and the explicit use of undo tuples to correct downstream state — prefigures the speculative execution and retraction mechanisms in Apache Flink and Apache Beam. The SUnion operator's design, which separates the ordering problem from the failure-detection problem, influenced the "watermark" abstraction central to the Dataflow model (Google, 2015), which uses punctuation-like signals to close time windows without blocking.

The configurable availability/consistency trade-off — governed by a single user-visible parameter $X$ — also anticipated the CAP theorem's practical consequences (Brewer, 2000; Gilbert & Lynch, 2002) for streaming systems: you cannot simultaneously have perfect consistency, perfect availability, and tolerance to partitions. Borealis made this trade-off explicit and quantifiable, giving operators a concrete dial to turn rather than a binary choice.

Caveat — Scope of the Approach

The paper assumes operators are convergent-capable — their state converges to a consistent value regardless of input order, given the same final input set. Arbitrary operators, such as those with external side effects or non-monotone window functions that can produce different outputs depending on arrival order even after undo, require additional mechanisms beyond what SUnion provides. The authors acknowledge this and leave it as future work.
