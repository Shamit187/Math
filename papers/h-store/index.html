VLDB 2007 · Scientific Paper

The End of an Architectural Era (It's Time for a Complete Rewrite)

Michael Stonebraker, Samuel Madden, Daniel J. Abadi, Stavros Harizopoulos, Nabil Hachem, Pat Helland VLDB '07, September 23–28, 2007, Vienna, Austria
Abstract This paper argues that the dominant relational DBMS architecture — inherited from System R, which was designed in the mid-1970s for disk-based storage, shared-memory multiprocessors, and dumb terminals — is fundamentally ill-suited for modern OLTP workloads. Specialized systems have already demonstrated 1–2 orders of magnitude performance superiority over general-purpose RDBMSs in data warehousing, text processing, and stream processing. This paper presents H-Store, an experimental OLTP engine designed from scratch for the modern hardware environment, and shows that H-Store runs TPC-C a factor of 82 faster than a commercial RDBMS. The key design choices: all data in main memory; single-threaded, run-to-completion execution per site; no redo logging; no locking; no buffer management; stored procedures in lieu of JDBC/ODBC; and a no-knobs self-managing architecture. The paper concludes that the RDBMS community should abandon incremental patching of legacy code and start over.

1. The Thesis: An Era Is Over

IBM's System R, the direct ancestor of DB2 and SQL Server, was designed in 1974–1977. Oracle implemented a similar architecture from the start. These systems share a common set of assumptions that made perfect sense in 1975: data lives on disk (RAM was enormously expensive), multiple queries run simultaneously on a shared-memory machine (CPUs were scarce), and users interact through dumb terminals issuing ad-hoc SQL. The core architectural features that follow from these assumptions are disk-oriented storage and B-tree indexing; multi-threading to hide disk I/O latency; locking-based concurrency control; and write-ahead logging (WAL) for crash recovery.

In 2007, when this paper is written, the world is radically different. A commodity server has 32 GB of RAM. Moore's Law means RAM prices continue to fall. Most OLTP databases fit entirely in main memory today, or will within a few years. CPUs have gotten thousands of times faster; disk bandwidth has not kept pace. And web applications — the dominant new OLTP workload — run transactions of roughly 200 records, completing in under one millisecond, with no user stalls during execution.

Intuition — The Overhead Accounting Argument

The authors profiled a popular commercial RDBMS running TPC-C and found that only about 12% of its execution time was spent doing useful work — actually executing the transaction logic. The other 88% was overhead: buffer pool management (reading and writing disk pages that, in a main-memory system, are always already in RAM), latching (acquiring and releasing short-term locks on data structures to protect them from concurrent threads), locking (acquiring and releasing long-term row locks for transaction isolation), logging (writing WAL records to a persistent log before every modification), and JDBC/ODBC interface overhead (marshalling data across process boundaries for each query call). Every single one of these overheads exists specifically to support the assumptions of 1975. Remove those assumptions, and you can remove the overhead.

2. Five Architectural Overheads to Eliminate

The authors identify five specific sources of overhead in traditional RDBMSs and argue that each can be eliminated in a clean-slate design for OLTP.

1. Disk-Oriented Storage and Buffer Management

A traditional DBMS manages a buffer pool: a cache of disk pages in RAM. When a transaction accesses a record, the system checks whether the page is in the buffer pool, reads it from disk if not, and pins it for the duration of the access. This buffer management code is sophisticated and expensive. In a main-memory DBMS, every record is always in RAM. The entire buffer pool subsystem — page table management, LRU eviction, dirty-page tracking, double-write protection — can be eliminated. Data structures can be optimized for cache lines (typically 64 bytes) rather than disk pages (typically 8–64 KB), improving cache efficiency dramatically.

2. Multi-Threading to Hide Latency

Traditional RDBMSs use multi-threading to allow other queries to run while one query waits for a disk I/O. In a main-memory system, there are no disk waits. Multi-threading becomes pure overhead: the OS scheduler must context-switch between threads, threads must acquire latches on shared data structures before modifying them, and B-tree code must be hardened against concurrent modification. In H-Store, every logical site is single-threaded and executes each transaction to completion without interruption. No latches are needed on any data structure. The code simplification is enormous.

3. Locking-Based Concurrency Control

Row-level locking in traditional RDBMSs protects against lost updates and dirty reads when multiple transactions run concurrently. In H-Store, since each site is single-threaded and executes one transaction at a time, there can be no concurrent access to the same data at the same site. Locking is eliminated entirely for the common case. Transactions that span multiple sites use an optimistic scheme rather than two-phase locking, since OLTP transactions are very short-lived (sub-millisecond) and therefore almost never hold conflicting locks simultaneously.

4. Write-Ahead Logging (Redo Log)

WAL requires writing a log record to persistent storage before any data modification takes effect. For TPC-C on the commercial system, the authors observe that logging is the primary bottleneck: the system spends two-thirds of its elapsed time inside the logging subsystem. Even with group commit, forced writes to the log add milliseconds to each transaction. In H-Store, which maintains multiple replicas (buddies) for high availability, recovery after a crash is accomplished by copying data from a live replica — no redo log is needed. An undo log (in main memory only, discarded at commit) handles transaction rollback.

5. JDBC/ODBC and Client/Server Overhead

Every SQL call through JDBC or ODBC involves serializing the query string, sending it across a network socket or named pipe, parsing it, optimizing it, executing it, serializing results, and sending them back. For a transaction that executes 20 simple SQL statements, this round-trip overhead dominates useful work. H-Store eliminates this by requiring all transaction logic to be expressed as stored procedures written in C++ (later planned as Ruby-on-Rails), compiled and registered with H-Store at transaction-definition time. At runtime, a client sends only the procedure name and parameter values; all SQL executes as local function calls inside the DBMS process, with data returned in a shared array — no serialization overhead.

3. Main Memory Changes Everything

The authors present a Moore's Law argument that deserves to be read carefully. In the late 1970s, a large machine had about 1 MB of RAM. By 2007, large machines have 100 GB. The OLTP benchmark TPC-C requires about 100 MB per physical distribution center (warehouse). A very large retail enterprise with 1000 warehouses requires 100 GB — fitting in the RAM of a single high-end server, or distributed across a grid of commodity machines each with 32 GB. Within a few years of the paper, a terabyte of main memory will not be unusual for a shared-nothing grid of 20 nodes.

The implication: the time is coming — and for many workloads has already arrived — when the disk-oriented architecture of System R descendants is simply wrong for OLTP. The database must fit in RAM, and the entire system should be designed around that assumption. Any code that exists only to manage the disk abstraction (buffer pool, WAL, disk-oriented B-tree layouts) should be deleted.

What About Durability?

If data lives only in RAM, a power failure destroys everything. H-Store addresses this with two mechanisms. First, replication: each table fragment has one or more buddies — exact copies held on different physical machines. If one machine loses power, its data survives on its buddy and the system continues normally. Second, for longer-term persistence, H-Store can periodically dump data to disk in columnar (no-overwrite) format, similar to a data warehouse checkpoint. This is dramatically simpler than WAL-based recovery and imposes zero overhead on the normal transaction path.

4. Single-Threaded Execution

The single-threaded design deserves more explanation, because it seems counter-intuitive: surely more threads means higher throughput on a multi-core machine? The H-Store answer is: not for OLTP transactions.

OLTP transactions are extremely short. TPC-C's heaviest transaction, new_order, touches about 200 records and completes in under one millisecond on H-Store. In that time, context-switching between threads, acquiring latches on B-tree nodes, and coordinating concurrent access to shared state all consume significant fractions of the available CPU budget. A single thread that runs each transaction to completion — without any interruption, no latches, no locking — finishes the transaction faster than a multi-threaded system that must coordinate at every shared data structure.

To exploit multiple cores, H-Store partitions the database across multiple logical sites, one per available CPU core. Each logical site is an independent, single-threaded processing unit with its own partition of the data, its own B-tree indexes, and its own transaction queue. Transactions that access only one partition (single-sited transactions) run entirely within one logical site with zero cross-site communication — the fast path. Transactions that span multiple partitions require coordination between sites, which H-Store handles with a lightweight protocol designed to minimize round trips.

5. Transaction Classes and Commutativity

H-Store requires the complete workload to be specified in advance as a collection of transaction classes. Each class has fixed SQL statements; only runtime constants (parameter values) vary. This is not as restrictive as it sounds: in practice, web-facing OLTP systems almost never allow users to issue arbitrary ad-hoc SQL — they call well-defined stored procedures with user-supplied parameters.

Given the full set of transaction classes upfront, H-Store can analyze which pairs of classes can conflict — that is, which pairs of transactions, if interleaved, could produce a different final state than if run in serial order. Two transaction classes commute if any interleaving of their single-site sub-plans produces the same database state. A class that commutes with all other classes (including itself) is called sterile.

Definition — Single-Sited, One-Shot, and Two-Phase Transactions

A transaction is single-sited if all its SQL commands access data on exactly one partition. It is one-shot if all its commands can be decomposed into independent single-site sub-plans dispatched in parallel without requiring intermediate results. A transaction is two-phase if it has a read-only Phase 1 (whose results determine whether to proceed or abort) followed by a write Phase 2. TPC-C's five transaction classes are all two-phase and, with appropriate replication of read-only tables, can all be made single-sited and one-shot — allowing H-Store to run TPC-C with zero concurrency control overhead.

6. H-Store Architecture Sketch

H-Store runs on a grid of $G$ nodes. Each node has multiple cores; each core is mapped to one logical site. Sites hold rows of tables contiguously in main memory with conventional B-tree indexing, tuned to the L2 cache line width of the physical machine. The database administrator (or an automatic physical design tool) specifies how tables are horizontally partitioned: typically, a root table is range- or hash-partitioned on its primary key, and all other tables are co-partitioned with rows belonging to the same root record residing on the same site.

Each logical site is single-threaded and executes incoming SQL commands from transactions to completion without interruption. Transaction logic is compiled stored procedures that make local procedure calls rather than JDBC round-trips. Data is returned in a shared data array, avoiding serialization. Replicas (buddies) are kept transactionally consistent: all writes are directed to all replicas synchronously, with ordering guaranteed by a site-unique timestamp consisting of (site_id, local_counter) pairs synchronized using NTP.

The Database Designer is an automatic tool (similar in spirit to C-Store's schema designer) that accepts a schema and a workload and outputs the optimal horizontal partitioning, buddy locations, and indexed fields. For TPC-C, the designer's output is a straightforward Warehouse-partitioned schema that makes all transaction classes single-sited and one-shot.

7. TPC-C: 82 Times Faster

TPC-C is the industry-standard benchmark for OLTP systems. It simulates a wholesale supplier with warehouses, districts, customers, orders, and inventory, and defines five transaction classes: new_order, payment, order_status, delivery, and stock_level. The benchmark is measured in transactions per minute (tpmC).

The experimental setup uses a dual-core 2.8 GHz desktop machine with 4 GB of RAM and 250 GB SATA disks. Both H-Store and a popular commercial RDBMS run on the same hardware. All transaction logic is implemented as stored procedures in both systems. The same driver generates transactions at the maximum rate for both systems. High availability and user terminal simulation are excluded.

Results: H-Store processes 70,416 TPC-C transactions per second. The commercial RDBMS processes 850 transactions per second. The speedup is a factor of 82.8 — nearly two orders of magnitude. When logging is turned off on the commercial system, its throughput rises to about 2,500 transactions per second, confirming that logging is the primary bottleneck. Even without logging, H-Store is still about 28 times faster, attributable to eliminated buffer management, locking, latching, and JDBC overhead.

Pause — Is 82x Realistic?

The benchmark excludes think time (users "stalling" between requests), which TPC-C requires in its official specification. With think time, the effective throughput advantage shrinks because the system is underloaded regardless. The authors acknowledge this explicitly. However, the relevant comparison for a research system is maximum throughput, not think-time-throttled throughput — the question being asked is "how fast can the engine go?" not "how does it perform at typical retail utilization?" Additionally, the TPC website lists the highest-performing official TPC-C results at about 133,000 transactions per second on a 128-core machine — about 1,000 transactions per second per core. H-Store achieves 35,000 transactions per second per core, which is a genuine 35x superiority even against the best-tuned commercial systems.

8. One Size Does Not Fit All

The paper's second major argument is that the relational model, SQL, and the general-purpose RDBMS paradigm are all inappropriate responses to the diversity of modern database markets. The authors identify five distinct markets:

OLTP (business data processing) — H-Store's target. Needs main-memory storage, single-threaded execution, stored procedures, no WAL. Data Warehouses — served by column stores like C-Store/Vertica. Needs columnar storage, vectorized execution, aggressive compression, minimal updates. Stream Processing — served by systems like Borealis/StreamBase. Needs continuous query evaluation over time windows, real-time output, fault tolerance for partial inputs. Text and Search — served by engines like Google, Yahoo search, Lucene. The relational model is wrong here; inverted indexes and ranking models are native primitives. Scientific Computing — served by array stores like MATLAB and SciDB. The table is not the right data model; arrays with named dimensions are.

The authors predict that these specialized engines will come to dominate each market, leaving RDBMSs competitive only in "hybrid" markets where no single engine excels. The appropriate response, they argue, is not to patch the monolithic RDBMS with yet another feature, but to retire it and build a collection of clean, purpose-built systems — each designed from scratch for its target market's workload and hardware environment.

Intuition — Why SQL Is Not the Answer for OLTP Either

In an OLTP system there are no ad-hoc queries — users never type SELECT * FROM Employees WHERE Salary > 50000 directly into the production system. Every interaction is a stored procedure call with typed parameters. SQL's generality (its ability to express arbitrary queries) adds parsing, planning, and optimization overhead that is pure waste for a fixed workload. A better interface is a strongly typed stored-procedure API in a high-level language (the authors advocate Ruby-on-Rails), compiled to native code, with SQL calls as internal subroutines rather than the primary interface. SQL remains useful as a design-time specification language, but as a runtime interface it is a costly abstraction.

9. Legacy: VoltDB and Beyond

H-Store was commercialized as VoltDB in 2010, co-founded by Stonebraker and Madden. VoltDB implements all of H-Store's core ideas — main-memory storage, single-threaded sites, stored procedures, no WAL, peer-to-peer HA via synchronous replication — and has been used in production for high-frequency trading systems, telecommunications billing, and real-time fraud detection. NuoDB, SingleStore (formerly MemSQL), and CockroachDB all incorporate significant design inspiration from H-Store.

The paper's broader prediction — that the "one size fits all" RDBMS paradigm would fragment into specialized engines — has proven remarkably accurate. By 2025, the database landscape includes dozens of purpose-built systems: Snowflake (warehouse), ClickHouse (OLAP), MongoDB (document), Redis (key-value), Apache Kafka (streams), Elasticsearch (text), InfluxDB (time series), and many more. No single system dominates all workloads. The paper's title has proved prophetic.

What H-Store Cannot Do

H-Store assumes the entire workload is specified in advance as a fixed set of transaction classes. Ad-hoc analytical queries cannot be run efficiently against H-Store's main-memory row structures — for that you need a column store. Long-running OLAP joins that produce large intermediate results are not OLTP operations and are explicitly outside H-Store's scope. H-Store also assumes relatively stable schemas and transaction profiles; schema migrations require careful engineering in a system where the physical design is optimized for a specific workload. These constraints make H-Store/VoltDB most suitable for write-heavy, high-throughput OLTP with well-understood access patterns — not as a general-purpose database replacement.
