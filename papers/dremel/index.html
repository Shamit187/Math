Scientific Paper · PVLDB 2010

Dremel: Interactive Analysis of Web-Scale Datasets

Sergey Melnik, Andrey Gubarev, Jing Jing Long, Geoffrey Romer, Shiva Shivakumar, Matt Tolton, Theo Vassilakis Proceedings of the VLDB Endowment, Vol. 3, No. 1, 2010
Abstract Dremel is a scalable, interactive ad-hoc query system for analysis of read-only nested data, developed and used in production at Google. By combining a multi-level execution tree borrowed from distributed search engines with a novel columnar storage format designed specifically for nested records, Dremel can execute aggregation queries over trillion-row tables in seconds. It has thousands of users at Google and runs on clusters of thousands of CPUs processing petabytes of data. The paper introduces two core technical contributions: a lossless columnar encoding for nested data using repetition levels and definition levels, and a multi-level serving tree that aggregates partial results in a parallel fan-out. Dremel complements MapReduce rather than replacing it, and is often used to rapidly prototype or validate results from MR pipelines.

1. Introduction

Google's data is fundamentally nested. A web document has a URL (a string), a list of Links (each Link having a Forward list and a Backward list of DocIds), and a list of Names (each Name having a URL and a list of Languages, each Language having a Code and optional Country). This is not an academic example — it is the actual structure of the document schema that appears throughout the Dremel paper, and it typifies how web-scale data looks in practice. Relational tables, with their flat rows of typed columns, cannot naturally represent this kind of hierarchically nested, multiply-repeated structure.

Google's answer to nested data representation is Protocol Buffers — a language-neutral, binary serialization format that encodes records as nested trees of fields. A Dremel table is a collection of Protocol Buffer records. The challenge Dremel addresses is: how do you run analytical SQL-like queries over trillions of such nested records interactively — in seconds rather than hours?

The naive approach would be to scan all records top-to-bottom for every query. At Google's scale, reading one terabyte of compressed data in one second requires tens of thousands of disk spindles working in parallel. This is the hardware reality Dremel operates in, and it explains why every design decision — storage format, query execution, serving tree topology — is oriented around minimizing the amount of data that must be read from disk for any given query.

The Core Idea in One Sentence

Store each field of a nested record in its own contiguous column on disk, tagged with enough metadata to reconstruct the original nesting structure, and let a search-engine-style serving tree fan queries out to thousands of leaf servers that each scan their local column stripes in parallel.

2. The Nested Data Model

Dremel's data model is based on strongly-typed nested records. A schema is a tree of fields, where each field is either atomic (integer, string, etc.) or a record (a named group of sub-fields). Fields are annotated with a multiplicity label: a field is either required (must appear exactly once), optional (may appear zero or one times), or repeated (may appear zero or more times). This is the same type system as Protocol Buffers.

Example — Document Schema 
message Document {
  required int64 DocId;
  optional group Links {
    repeated int64 Backward;
    repeated int64 Forward;
  }
  repeated group Name {
    repeated group Language {
      required string Code;
      optional string Country;
    }
    optional string Url;
  }
}

A Document has one required DocId, an optional Links group (which itself contains repeated Forward and Backward link lists), and a repeated Name group (each Name having a repeated Language subgroup and optional Url). A single document record can have multiple Names, and each Name can have multiple Languages. This creates a tree structure that a flat CSV cannot represent.

The paper works through two concrete sample records, $r_1$ and $r_2$, that instantiate this schema with different values. Record $r_1$ has DocId 10, two Forward Links (20 and 40) and one Backward Link (60), two Names (the first with two Languages — "en-us" and "en" — and Url "http://A"; the second with one Language "en-gb" and Url "http://B"). Record $r_2$ is simpler: DocId 20, one Backward Link (10), one Forward Link (80), one Name with no Language and Url "http://C". These two records are the running example for all the encoding algorithms.

3. Repetition and Definition Levels

Storing a nested record in a columnar format is the central algorithmic challenge of the paper. The naive approach — store each leaf field's values contiguously — immediately runs into a problem: how do you know, when you encounter a value in the Name.Language.Code column, whether it belongs to the first Language of the first Name of record $r_1$, or the second Language of the same Name, or a Language of the second Name? You have lost the nesting structure.

Dremel's solution is to store two small integers alongside every value: a repetition level and a definition level.

Definition — Repetition Level

The repetition level of a value tells you at what level in the field's path the most recent repeated field has repeated. More precisely: starting from the root of the schema tree, follow the path to the current field. The repetition level is the index of the last field in that path that actually repeated (started a new occurrence) to produce this value.

A repetition level of 0 means this value starts a brand new top-level record. A higher level means we are seeing a repeated occurrence of some nested field — and the level tells you which field repeated. In the Name.Language.Code column of $r_1$, the values "en-us", "en", and "en-gb" have repetition levels 0, 2, and 1 respectively: level 0 starts a new record, level 2 means Language repeated (within the same Name), and level 1 means Name repeated.

Definition — Definition Level

The definition level of a value tells you how many fields in the path to the current field are actually defined (present in the record), counting only optional and repeated fields. A NULL value (absent optional or repeated field) gets a definition level equal to how far down the path the structure exists before becoming absent. This encodes precisely which ancestor is responsible for the value being missing.

For example, in the Name.Language.Country column: Country is optional, and Language is repeated, and Name is repeated. When a Name exists but has no Language, the NULL Country gets definition level 1 (Name is defined, but Language is absent). When a Language exists but has no Country, the NULL gets definition level 2 (Name and Language are defined, but Country is absent). This distinction matters for record reconstruction.

Pause — Why Two Numbers?

Repetition levels alone would tell you which repeated field started over, but they do not tell you which optional fields are absent. Definition levels alone would tell you which fields are present, but not where repeated structures begin. Together, the two integers provide a lossless encoding of the complete record structure: every original record can be reconstructed exactly from the columnar encoding, with no information lost.

In practice, these integers require very few bits. If the maximum definition level of a field is 3, then 2 bits suffice per definition level. If the maximum repetition level is 2, then 2 bits suffice. For fields that are required and never repeated, definition level is always the full depth and repetition level is always 0 — so these can be omitted entirely. The overhead of the level encoding is minimal compared to the actual field values.

Example — Column Stripe for Name.Language.Code

Scanning the two sample records and writing out the Name.Language.Code column with (repetition level r, definition level d) pairs: 

value      r  d
'en-us'    0  2    ← new record; Name[0], Language[0] both present
'en'       2  2    ← Language repeated within same Name
NULL       1  1    ← Name repeated; but this Name has no Language
'en-gb'    1  2    ← Name repeated; Language[0] present
NULL       0  1    ← new record r₂; Name exists but no Language

Reading these five values back with their levels, a finite-state machine can reconstruct the exact nesting structure of both original records. The NULL with r=1, d=1 tells us: Name has repeated (repetition level 1), and only one level of the path is defined (Name is present, but Language is absent within it).

4. Record Assembly from Columns

Reading a subset of fields from columnar storage and reconstructing the output records efficiently is the inverse problem. Dremel solves this with a finite-state machine (FSM) per selected field. Each FSM state corresponds to a FieldReader for one of the selected fields. State transitions are labeled with repetition levels: after reading a value from one field, the next repetition level determines which field-reader to visit next.

The construction of this FSM is non-trivial but follows from the schema tree structure. For any two fields whose paths share a common repeated ancestor, the FSM will transition between their readers at the repetition level of that ancestor. The algorithm (shown in the paper's Appendix C) produces a compact FSM that traverses all selected fields exactly once per record, in schema order, with no backtracking. Crucially, it never reads fields that are not selected — this is what makes columnar storage fast.

Skipping Unneeded Fields is the Point

A Google schema may have thousands of fields. A typical analytical query touches perhaps five. Columnar storage means only those five columns are ever read from disk. With record- oriented storage, reading any field requires reading the entire record. At trillion-record scale, this difference in I/O dominates all other costs. Dremel's FSM-based assembly makes it possible to select a small subset of fields, read only their column stripes, and produce correct output records — never materializing complete records.

5. Query Language and Execution

Dremel's query language is SQL-like, extended to handle nested structure. The key extension is the WITHIN keyword for within-record aggregation. For example:

Example — Within-Record Aggregation 
SELECT DocId AS Id,
       COUNT(Name.Language.Code) WITHIN Name AS Cnt,
       Name.Url + ',' + Name.Language.Code AS Str
FROM t
WHERE REGEXP(Name.Url, '^http') AND DocId < 20;

The WITHIN Name clause tells the query to count Language codes within each Name subrecord, producing a separate count per Name rather than a global count per document. The output is a nested table where each document has a list of Name groups, each group containing the Url, the per-Name language count, and a list of concatenated strings. This kind of within-record aggregation is impossible to express in standard flat SQL.

The execution engine avoids materializing full records during query processing. Instead, it uses a select-project-aggregate evaluation algorithm that operates directly on column stripes with their repetition and definition levels, producing aggregated output at the correct nesting level without ever assembling complete Protocol Buffer records. This is what makes Dremel fast: the query answers emerge from a single coordinated pass over the selected columns.

6. The Multi-Level Serving Tree

The second major contribution of Dremel is its execution architecture. Dremel borrows a pattern from distributed search engines: a multi-level serving tree in which a single query is rewritten at each level and fanned out to thousands of servers working in parallel.

Serving Tree Architecture

A Dremel cluster has three tiers. The root server receives queries from clients, determines which tablets (horizontal partitions of a table) must be scanned, and rewrites the query as a union of partial-results queries to be sent to the next level. Intermediate servers receive their assigned query fragment, further decompose it to the servers below, collect partial aggregations on the way up, and return partially-aggregated results to the root. Leaf servers read column stripe data from the storage layer (Google File System) or local disk, execute the query against their tablets, and return partial aggregate values up the tree.

A simple aggregation query like SELECT A, COUNT(B) FROM T GROUP BY A gets rewritten at the root as a union of partial sub-queries. At level 1, each server receives a query of the form:

Query Rewriting in the Serving Tree 
-- root broadcasts to level-1 servers:
SELECT A, SUM(c) FROM (R₁¹ UNION ALL ... R₁ⁿ) GROUP BY A

-- each level-1 server rewrites for its leaf servers:
Rᵢ¹ = SELECT A, COUNT(B) AS c FROM Tᵢ¹ GROUP BY A

Where $T_i^1$ is the disjoint set of tablets assigned to leaf server i. The leaf servers compute local counts; the intermediate servers sum them; the root sums the intermediate totals. This aggregation "up the tree" is what enables the system to produce a global GROUP BY result from thousands of independent partial scans.

A critical feature is the query dispatcher's handling of stragglers — leaf servers that take disproportionately long due to hardware variability, other workloads, or network delays. The dispatcher sets a parameter specifying the minimum fraction of tablets that must be processed before returning a result. Setting this to 98% rather than 100% can dramatically speed up queries: the system returns an approximate answer (missing 2% of tablets) without waiting for the slowest machines. For many analytical queries, this small approximation is acceptable.

The execution capacity is measured in slots, where one slot is one execution thread on one leaf server. A system with 3,000 leaf servers running 8 threads each has 24,000 slots. A table spanning 100,000 tablets can be scanned by assigning roughly 5 tablets per slot at once, cycling through all tablets in batches. The tablet histogram experiments show that 99% of tablets are processed in under one second per slot, meaning most queries complete well within interactive response times.

7. Experimental Results

The paper tests Dremel on five large production datasets at Google, the largest of which (T4 and T5) have over one trillion rows, spanning 20–105TB of compressed columnar data. These are datasets used for real Google production analytics — crawled web documents, Android app install tracking, crash reports, spam analysis.

Columnar vs. record-oriented storage (local disk). On a 300K-row fragment of T1 stored on a single disk, reading a single field from columnar storage takes approximately 0.5 seconds (read + decompress). Reading the same field from record-oriented storage takes about 3 seconds (read + decompress + parse entire record). The advantage of columnar storage grows linearly with the number of fields in the schema but is already roughly 6× for a single field. Record assembly — reconstructing complete records from columns — adds roughly 50% overhead but is still faster than record-oriented storage for queries touching fewer than a handful of fields.

MapReduce vs. Dremel. For a query counting the average number of terms in a text field (Query $Q_1$), MapReduce on record-oriented storage takes approximately 1,000 seconds (about 17 minutes) for 85 billion records. MapReduce on columnar storage (reading only the one needed field) takes about 180 seconds. Dremel on the same data takes about 7 seconds. The three-orders-of-magnitude improvement from hours to seconds for the same logical query is what makes interactive analytics at this scale possible.

Serving tree topology. For an aggregation returning a few hundred records (Query $Q_2$), the serving tree depth makes little difference — 2, 3, or 4 levels all finish in about 3 seconds because the result is small enough that aggregation cost is negligible. For an aggregation returning 1.1 million distinct domain names (Query $Q_3$), adding a level halves the execution time because partial aggregation at intermediate nodes dramatically reduces the data flowing up the tree.

Scalability. Running a top-k query ($Q_5$) on a trillion-row table (T4, 4.2TB compressed) with 1,000 to 4,000 leaf servers, the total CPU time is constant at about 300,000 CPU-seconds in all configurations — the same amount of work is done regardless of cluster size. But the wall-clock time decreases near-linearly: 4× as many servers gives roughly 4× the speed. This near-linear scaling is the key result validating Dremel's architecture.

8. Impact and Legacy

Dremel is the direct ancestor of Google BigQuery, which exposed Dremel's capabilities as a public cloud service in 2010. BigQuery's SQL-over-petabytes model, columnar storage, and serverless elastic scaling all trace directly to the ideas in this paper. The columnar storage format described here (with repetition and definition levels) became the basis of Apache Parquet, the dominant open-source columnar file format for the Hadoop ecosystem. Parquet is today the default storage format for Spark, Hive, Presto/Trino, and most data lakehouse architectures.

The serving-tree execution architecture influenced Apache Drill and Presto, both of which adopted multi-level distributed execution with partial aggregation at intermediate nodes. The insight that nested data can be stored and queried in columnar format without flattening — and that doing so is essential for performance at scale — has become a foundational principle of modern data engineering.

Academically, the paper's encoding scheme for nested columnar data is one of the most carefully worked-out encoding algorithms in the systems literature. The repetition and definition level scheme is elegant, minimal (requires only a few bits per value), lossless, and directly supports both selective projection (read only needed fields) and correct record reconstruction (reassemble full records when needed). Understanding this encoding is prerequisite knowledge for anyone building or extending columnar storage systems.
