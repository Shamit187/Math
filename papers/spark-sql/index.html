Scientific Paper · SIGMOD 2015

Spark SQL: Relational Data Processing in Spark

Michael Armbrust, Reynold S. Xin, Cheng Lian, Yin Huai, Davies Liu, Joseph K. Bradley, Xiangrui Meng, Tomer Kaftan, Michael J. Franklin, Ali Ghodsi, Matei Zaharia ACM SIGMOD 2015 · Melbourne, Victoria, Australia
Abstract Big data pipelines rarely fit neatly into either the relational world (SQL, declarative, optimized) or the procedural world (MapReduce, Spark RDDs, arbitrary code). In practice, practitioners must chain the two together awkwardly, losing optimizations at every boundary. Spark SQL bridges this gap with two contributions. First, a DataFrame API — a distributed collection of structured records that looks like a relational table but can be constructed from and manipulated within Spark programs. Second, the Catalyst optimizer — an extensible query optimizer built in Scala that uses functional programming and pattern matching to make adding new rules, data sources, and types genuinely easy. Together they make it possible to write a single Spark program that mixes SQL queries, machine learning transformations, and custom procedural logic, with the optimizer reasoning across all of it.

1. The Two-World Problem

By 2015, Apache Spark had become the dominant platform for large-scale data processing. Its core abstraction — the Resilient Distributed Dataset (RDD) — gave programmers a fault-tolerant, distributed collection they could manipulate with familiar functional operations like map, filter, and reduce. This was a massive improvement over MapReduce, and Spark attracted an enormous user base.

But RDDs had a fundamental limitation: the Spark engine was largely opaque to them. When you wrote rdd.map(f).filter(g), Spark had no idea what f and g actually computed — they were arbitrary Scala or Python functions. So it could not reorder operations, push filters closer to data sources, or use columnar encoding. You got fault tolerance but not a smart optimizer.

Intuition — Why opacity hurts

Consider a pipeline that reads a 100-column table, applies a filter, and selects 3 columns. A smart optimizer would push the filter into the data source (so you never read irrelevant rows) and prune columns (so you never deserialize 97 unnecessary fields). An RDD pipeline cannot do either — it reads everything, deserializes everything, then discards most of it. For terabyte-scale datasets on a 100-node cluster, this translates directly to dollars and minutes wasted.

At the same time, pure SQL systems could not easily incorporate the procedural logic that practitioners needed: machine learning algorithms, custom parsing, graph traversals. Systems like Hive and Shark tried to bring SQL to Hadoop/Spark, but they had a critical limitation: you could not easily mix SQL with native Spark operations in a single logical plan. Every hand-off between SQL and Spark code broke the optimization chain.

Spark SQL's insight: give structured data a first-class, lazy representation inside Spark — the DataFrame — so that the optimizer can see across the entire computation before executing anything.

2. Spark Background

To appreciate Spark SQL's contribution, a brief review of its substrate is helpful. Spark programs manipulate RDDs — immutable, partitioned collections of objects distributed across a cluster. Operations on RDDs are lazy: they build a lineage graph (a DAG of transformations) and do not execute until an "action" (like count() or save()) is called. This lazy evaluation is what enables some pipelining optimizations, but it cannot help with algebraic rewrites because the operations are opaque functions.

Spark's predecessor for relational queries was Shark, which modified Hive to run on Spark's engine. Shark was limited to data in the Hive catalog, required constructing query strings (error-prone in modular programs), and used an optimizer designed for Hadoop-style batch processing. It had no way to query data that lived inside a Spark program as an RDD. Spark SQL replaces Shark entirely.

3. The DataFrame API

The central user-facing concept in Spark SQL is the DataFrame: a distributed collection of rows with a known schema. This is conceptually equivalent to a table in a relational database, or a data frame in R or Python's Pandas library. The crucial difference from an RDD is that a DataFrame carries its schema explicitly, and all operations on it are expressed through a small domain-specific language (DSL) of relational operations — not arbitrary functions.

Example — DataFrame operations in Scala

The following code counts female employees per department. The DataFrame API allows writing this as a chain of relational operations that Catalyst can fully inspect and optimize: 

employees
  .join(dept, employees("deptId") === dept("id"))
  .where(employees("gender") === "female")
  .groupBy(dept("id"), dept("name"))
  .agg(count("name"))

Each method call — join, where, groupBy, agg — does not immediately execute anything. It appends a node to an abstract syntax tree (AST) that Catalyst will later optimize. At no point does Spark execute any code until an output operation is triggered.

DataFrames can be created from many sources: Hive tables, JSON files, Parquet files, JDBC connections to relational databases, and — crucially — from existing Spark RDDs of Java or Python objects. For RDDs of typed objects (e.g., a Scala case class User(name: String, age: Int)), Spark SQL uses reflection to automatically infer the schema. For Python RDDs, it samples the data at runtime.

DataFrames can also be registered as temporary tables and queried with SQL strings. This allows business intelligence tools (which connect via JDBC/ODBC and speak only SQL) to benefit from the same optimizer as the programmatic API. The two entry points are completely unified: a SQL query and the equivalent DataFrame chain compile to the same Catalyst tree.

Key property — Laziness enables cross-boundary optimization

Because every DataFrame operation returns another DataFrame (a logical plan, not a result), Catalyst can see the entire computation before deciding how to execute any of it. A filter applied after a join can be pushed before the join. Projection pruning can eliminate columns before they are ever deserialized. Column statistics gathered from a Parquet file can inform join ordering. None of this is possible when the computation is expressed as opaque functions on RDDs.

4. The Catalyst Optimizer

Catalyst is the optimizer underlying Spark SQL. Its design philosophy is different from traditional query optimizers, which typically require a domain-specific language (DSL) for writing rules and a separate "optimizer compiler" to translate those rules into executable code. This imposes a steep learning curve and makes the optimizer hard to extend.

Catalyst instead uses standard features of the Scala programming language — specifically algebraic data types and pattern matching — to represent query plans as immutable trees and transformations as ordinary Scala functions. Any developer who knows Scala can add a new optimization rule without understanding the internals of the optimizer. This openness was key to Spark SQL's rapid adoption.

Definition — Trees and Rules in Catalyst

A tree in Catalyst is a recursive data structure where each node has a type (e.g., Add, Filter, Join) and zero or more child nodes. Trees are immutable: transformations produce new trees. A rule is a function from one tree to another, typically expressed as a Scala pattern-match. For example, a rule that constant-folds additions is simply: 

tree.transform {
  case Add(Literal(c1), Literal(c2)) => Literal(c1 + c2)
}

Catalyst applies rules repeatedly (in batches) until the tree reaches a fixed point — no more rules apply. This functional style makes rules easy to write, test, and compose.

5. Four Phases of Query Planning

Catalyst processes every query through four sequential phases, each operating on a different kind of tree. Understanding these phases is the key to understanding what Spark SQL can optimize and why.

Phase 1 — Analysis

Input: an unresolved logical plan — a tree that may contain references to columns or tables whose types are unknown. The analyzer consults a Catalog (the registry of data sources and schemas) to resolve attribute names, assign data types, detect errors (wrong column names, type mismatches), and produce a fully resolved logical plan. This is like a type-checking pass in a compiler.

Phase 2 — Logical Optimization

Input: the resolved logical plan. This phase applies standard algebraic rewrites using Catalyst rules: predicate pushdown (move filters as early as possible), projection pruning (drop unused columns), constant folding, Boolean simplification, null propagation. The rules are written in ~800 lines of Scala code. No cost model is consulted here — these rewrites are algebraically equivalent transformations that are always beneficial.

Phase 3 — Physical Planning

Input: the optimized logical plan. The physical planner maps logical operators to physical implementations (e.g., Join can become broadcast join, sort-merge join, or hash join). For small tables, a broadcast join sends the smaller table to every node, avoiding a shuffle entirely. The physical planner uses a cost model for join selection (based on estimated table sizes) and also applies additional rule-based physical optimizations, such as pipelining projections and filters into a single Spark map operation.

Phase 4 — Code Generation

Input: the selected physical plan. Rather than interpreting the tree at runtime (which involves large numbers of virtual function calls), Catalyst generates Java bytecode for the expression evaluation. It does this using Scala quasiquotes — a metaprogramming feature that lets you construct ASTs for Scala code at compile time and feed them to the Scala compiler at runtime. The generated code is equivalent to hand-written Java and avoids the overhead of boxing, virtual dispatch, and generic collections.

Intuition — Why code generation matters for numeric loops

Consider evaluating the expression $x + x + x$ for $10^9$ integer values. The interpreted approach walks the expression tree for every value, calling virtual functions at each node — an enormous constant factor. Code generation produces a tight inner loop in bytecode that runs at JIT-compiled speed. In the paper's benchmark (Figure 4), interpreted evaluation takes ~38 seconds, hand-written Scala takes ~12 seconds, and Catalyst-generated code takes ~5 seconds — faster than hand-written because the compiler can apply optimizations that a human would not bother with.

6. Advanced Features

Beyond the core optimizer, Spark SQL introduces three features that address practical challenges in large-scale analytics.

Schema inference for semistructured data. JSON is ubiquitous in big data, but JSON has no fixed schema. Spark SQL's JSON data source performs a single-pass reduction over the records to infer a schema: it generalizes types (if a field appears as an integer in some records and a float in others, it becomes FLOAT), handles nested objects and arrays, and produces a STRUCT schema that can be used for column pruning and predicate pushdown. Users can then query JSON directly with SQL, including accessing nested fields using dot notation.

Integration with the MLlib machine learning library. Machine learning pipelines in Spark had used RDDs of domain-specific types (e.g., LabeledPoint). By introducing DataFrames as the universal data representation, Spark SQL enabled a new high-level ML API (MLlib Pipelines) where each algorithm is a transformer or estimator that takes a DataFrame and produces a DataFrame. This makes it trivial to compose preprocessing, feature extraction, dimensionality reduction, and model training into a single optimizable plan.

Query federation to external databases. The Catalyst extension point for data sources allows pushing predicates into remote systems. A JDBC data source can translate a Spark SQL filter into a SQL WHERE clause and send it to MySQL, fetching only the matching rows over the network. This is dramatically more efficient than fetching all rows and filtering in Spark.

7. Performance

The paper evaluates Spark SQL on three dimensions. For SQL query performance, it uses the AMPLab big data benchmark (web analytics workload), comparing against Shark and Impala on a 110 GB Parquet dataset. Spark SQL is substantially faster than Shark on all query types, and competitive with Impala (a C++-based, Hadoop-native SQL engine often considered the state-of-the-art). The key gap versus Impala comes on join-heavy queries where Impala's cost-based optimizer makes better decisions; otherwise Spark SQL matches or beats it.

For DataFrame versus native Spark code, the comparison is striking. A distributed aggregation of 1 billion integer pairs using the Python RDD API took ~170 seconds. The same computation using the DataFrame API took ~12 seconds — a $14\times$ speedup — because the DataFrame plan is compiled to efficient JVM bytecode rather than being interpreted by the Python runtime.

For pipeline performance, the paper compares a two-stage pipeline (SQL query + separate Spark job) against an equivalent integrated DataFrame job. The integrated version is $\approx 2\times$ faster because Spark SQL eliminates the need to write intermediate results to HDFS between stages and can pipeline the filter operation into the word count operation in a single pass.

8. Impact and Legacy

Spark SQL was released in May 2014 and became one of the most actively developed components in Apache Spark almost immediately. By the time this paper was published in 2015, it had over 400 contributors. The DataFrame API became the standard data representation across all of Spark's libraries — replacing RDDs in MLlib, Graph processing, and streaming.

More broadly, Spark SQL demonstrated two things to the systems community. First, that functional programming — immutable trees, pattern matching, composable rules — is a genuinely effective way to build extensible query optimizers, not just an academic curiosity. Second, that the boundary between "relational" and "procedural" processing is artificial and unnecessary: a single unified API with a smart optimizer can serve both communities better than either approach alone.

Lasting influence

Catalyst's architecture directly influenced the design of query optimizers in subsequent systems. The idea of expressing optimizer rules as pattern-matched functions on immutable trees appears in Databricks' Photon engine, in several academic systems, and in the design of Apache Calcite — which has become the standard query optimizer framework for the Java ecosystem (used in Flink, Hive, Druid, and others). The DataFrame abstraction is now so universal that most practitioners do not remember a time when Spark's native API was anything else.
