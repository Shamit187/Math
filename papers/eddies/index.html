Scientific Paper · SIGMOD 2000

Eddies: Continuously Adaptive Query Processing

Ron Avnur, Joseph M. Hellerstein ACM SIGMOD International Conference on Management of Data, 2000
Abstract In large federated and shared-nothing databases, resources exhibit widely fluctuating characteristics. Assumptions made at query submission time will rarely hold throughout the duration of processing. Traditional static query optimization — pick a plan, execute it — is therefore ineffective in these environments. This paper introduces the eddy, a query processing operator that sits between data sources and join operators, continuously reordering those operators on a tuple-by-tuple basis as it runs. The key ideas are: identifying moments of symmetry when reordering is cheaply possible, using the back-pressure of a fluid-dynamics model to favor cheaper operators, and overlaying a lottery scheduling algorithm so the eddy learns operator selectivities over time. Initial experiments show eddies performing nearly as well as a static optimizer in static environments, and dramatically better when conditions change mid-query.

1. The Problem with Static Plans

When you submit a SQL query to a traditional database, the query optimizer chooses a join order and access method before a single tuple has been fetched. It might decide, say, to join Employees with Departments first, then filter by salary. That decision is frozen into a query plan — a tree of operators — and the execution engine follows it faithfully until the last tuple is produced.

This works well when the optimizer's assumptions are accurate. But in wide-area and federated systems — the paper's context is the Telegraph system at UC Berkeley, which runs queries across networked data sources — three things commonly go wrong mid-query:

Intuition — Why Static Plans Break

Hardware and workload fluctuation. A remote server that was fast at query start may become slow. A disk whose outer tracks have high bandwidth may rotate to inner tracks. Network congestion spikes unpredictably.

Selectivity change. A selection predicate salary > 100000 applied to an employee table clustered by age will become more and more selective over time as older (higher-paid) employees exhaust. What began as a highly selective filter may become a pass-through filter halfway through execution.

Delayed data sources. In federated queries over the internet, one data source might not begin delivering data for 30 seconds after execution starts. A static plan that depends on that source early wastes time and resources.

The authors' solution is not to run the optimizer again mid-query — that is expensive and complex. Instead, they merge the optimization and execution phases entirely. The eddy is a single operator that is the optimizer, running continuously as tuples flow.

2. Moments of Symmetry

Before describing the eddy, the paper asks a precise question: when can a join order be changed without corrupting the results? Changing the order of operators mid-execution is dangerous. An operator like merge join maintains state — it remembers how far it has advanced through a sorted input. Swapping inputs mid-stream could yield duplicates or miss tuples.

Definition — Moment of Symmetry

A moment of symmetry for a join algorithm is a point during execution at which the join's two inputs are in an equivalent position — specifically, a point where either input could be designated as the "outer" (driving) relation without repeating already-performed work or producing incorrect results. At such a moment, you can reorder the inputs to the join without any state modification.

Different join algorithms have very different moment-of-symmetry profiles. Understanding these is central to knowing how often eddies can reoptimize.

Example — Join Algorithms and Their Symmetry

Pipelined hash join (specifically the ripple join family developed by Haas and Hellerstein): after every tuple from either input is joined with all tuples so far from the other input, both inputs are in an equivalent position. These joins have moments of symmetry at every corner of the ripple — extremely frequent, making them ideal for eddies.

Nested-loops join: the outer relation drives the inner scan. There is a barrier — the outer relation's cursor — after which reordering would require re-scanning the inner. Moments of symmetry occur only at the end of each full inner scan: infrequent.

Merge join: both inputs are treated symmetrically by definition. Moments of symmetry are very frequent, but merge join requires sorted inputs, creating ordering constraints that limit how freely operators can be reordered.

The Ripple Join family is therefore the preferred join algorithm for use with eddies: it has frequent moments of symmetry, adaptive or non-existent synchronization barriers, and minimal ordering constraints. The paper focuses on block, index, and hash ripple joins.

Pause and Reflect

Think of a moment of symmetry as the join algorithm "surfacing for air" — at that instant, it does not care which input it processes next. The eddy exploits these moments: it is allowed to route the next tuple to whichever operator is currently most efficient. Between moments of symmetry, the tuple must stay with its current operator. The more frequent the moments of symmetry, the finer-grained the eddy's control.

3. The Eddy Architecture

Architecturally, an eddy is an n-ary tuple router. It sits between n input relations and a set of query operators (selections, joins). Every tuple that enters the system passes through the eddy's buffer; the eddy decides which operator to send each tuple to next.

Definition — Ready Bits and Done Bits

Each tuple carries a tuple descriptor — a vector of two bit arrays. The Ready bits indicate which operators are currently eligible to process this tuple (i.e., all their input dependencies are satisfied). The Done bits indicate which operators have already processed this tuple. The eddy sends a tuple only to an operator whose Ready bit is on. After an operator processes a tuple and returns it, the corresponding Done bit is turned on. When all Done bits are on, the tuple has passed through the full query plan and is sent to the output.

The eddy's buffer is implemented as a priority queue. Tuples enter with low priority (they are new, unprocessed). When an operator returns a tuple to the eddy, the tuple is given high priority — it has already had work done on it and should be driven to completion before new tuples are consumed from the inputs. This ensures tuples flow completely through the eddy before new ones are admitted, preventing the buffer from becoming clogged.

The eddy explicitly merges the concept of a multi-way join plan into a single operator. In a conventional system, a 3-table query R JOIN S JOIN T is represented as a tree of two binary join nodes. The eddy collapses this into a single n-ary router, which can generate any order of the join operators as tuples flow through. This is equivalent to being able to represent any spanning tree of the join graph — any bushy or left-deep or right-deep plan — without modifying code.

4. Routing Tuples: Fluid Dynamics and Lottery Scheduling

Having established the architecture, the paper studies how the eddy should choose which operator to route each tuple to. The routing policy determines the system's efficiency.

4.1 Naive Eddy: Fluid Dynamics

The simplest policy gives no explicit information about operator costs or selectivities to the eddy. Instead, the eddy exploits the natural back-pressure that arises in a River-style dataflow system, where each operator runs as an independent thread connected by fixed-size message queues.

Here is the key insight: a low-cost selection operator consumes tuples quickly, so the queue feeding it tends to stay empty — it can always accept more work. A high-cost operator consumes tuples slowly, so its input queue fills up and creates back-pressure. Since the eddy routes tuples to whatever eligible operator has queue space, it naturally sends most tuples to the cheaper operator first. No explicit cost model is needed.

Example — Naive Eddy with Two Selections

Consider SELECT * FROM U WHERE s1() AND s2(), with two selection predicates of equal selectivity (50%) but different costs: s2 costs 5 delay units and s1 costs between 1 and 9 across runs. The naive eddy, with no explicit cost information, nearly matches the best static ordering in all cases. When s1 costs 1, the fluid dynamics routes most tuples to s1 first (it drains the queue faster). When s1 costs 9, the dynamics flip and route most tuples to s2 first. This happens automatically, without any statistics.

However, fluid dynamics alone does not capture selectivity differences. If two operators have the same cost but one filters out 90% of tuples and the other filters only 10%, the fluid-dynamics eddy performs mid-way between the two static orderings — not as good as the best ordering.

4.2 Lottery Scheduling: Learning Selectivities

To handle selectivity differences, the authors add a lightweight learning algorithm: Lottery Scheduling, adapted from operating systems work by Waldspurger and Weihl (1994).

Definition — Lottery Scheduling in an Eddy

Each operator maintains a count of lottery tickets. When the eddy is ready to send a tuple to an eligible operator, it holds a lottery among the eligible operators — each operator's chance of winning is proportional to its ticket count. When the eddy gives a tuple to an operator, that operator is credited one ticket. When an operator returns a tuple to the eddy, one ticket is debited from that operator's running count. An operator's ticket count therefore tracks its net throughput — how efficiently it drains tuples from the system. Operators that process tuples quickly and return many output tuples accumulate more tickets; operators that process slowly or filter many tuples accumulate fewer.

The lottery scheme elegantly captures both cost and selectivity simultaneously. An operator's ticket count reflects both how fast it runs (cost) and how many tuples it produces (selectivity). Low selectivity means many tuples are filtered: fewer tuples returned, fewer tickets accumulated, lower probability of winning the lottery. High cost means slow processing: back-pressure accumulates, fewer tuples processed, fewer tickets. Both effects push the operator toward a lower lottery share.

The lottery-based eddy handles both the changing-cost and changing-selectivity scenarios effectively, slightly outperforming the naive back-pressure scheme in cost experiments and significantly outperforming it in selectivity experiments. Importantly, the lottery continuously re-learns: as conditions change, ticket counts shift to reflect the new reality.

Important Caveat — Forgetting the Past

A naive lottery accumulates all past experience equally. If an operator was very efficient early in the query and accumulates many tickets, those historical tickets will make it hard for a newly fast operator to win the lottery later. The authors address this with a windowed lottery: the query execution is divided into time windows. Each window maintains two ticket counts — banked tickets (earned in prior windows) and escrow tickets (earned in the current window, acting as a measure of recent efficiency). At the start of each new window, banked tickets are reset to the escrow value. This way, recent performance dominates, and the eddy can adaptively re-learn as conditions change.

5. Experimental Results

The experiments were conducted on a Sun Ultra-1 workstation running Solaris 2.6 with 160 MB RAM, using the Euphrates implementation of the River dataflow framework. Relations had 100-byte tuples and cardinalities as shown in the paper's Table 1 (R: 10,000 tuples; S: 80,000; T: 10,000; U: 50,000).

The key experiment compares four policies against two 50%-selectivity selections of varying relative cost: the best static ordering (cheaper operator first), the worst static ordering (more expensive first), a naive back-pressure eddy, and a lottery-based eddy.

Intuition — Reading the Graphs

In the static-cost experiment (Figure 4 of the paper), when s2 costs 5 and s1 varies from 1 to 9, the naive eddy nearly matches the best static ordering throughout — this is the fluid dynamics at work. In the variable-selectivity experiment (Figure 5), where both operators cost 5 but selectivity of s1 varies from 0 to 100%, the naive eddy performs mid-way (as expected), while the lottery eddy tracks close to optimal, demonstrating that the ticket scheme has learned the selectivity difference.

For joins (Section 4.4 of the paper), the authors tested a 3-table query over R, S, and T with a selective index join between S and T, and a hash join between R and S. The lottery-based eddy performs nearly optimally in all cases, correctly routing most tuples through the hash join first when it is cheaper, and switching to favor the index join when its selectivity advantage dominates.

6. Dynamic Fluctuations and Adaptation

The most dramatic demonstration of eddies is in dynamic environments — exactly the federated, wide-area scenarios that motivated the paper. Two key experiments:

Changing join costs (Section 4.5). A 3-table equijoin over two external index servers. Initially one server (I_fs) is fast (no delay) and the other (I_sf) is slow (5 seconds per lookup). After 30 seconds, the speeds swap. Both static plans therefore pay a large penalty: the plan optimized for the initial assignment has the wrong order for the second half. The eddy using a windowed lottery runs for the duration of the query faster than either static plan, adapting its ordering shortly after the swap occurs.

Delayed data source (Section 4.5.1). In a federated query, relation R is delayed by 10 seconds (its data source is slow to respond). A static plan that relies on R early wastes time. The eddy initially routes most tuples to the RS join, but quickly adjusts when it observes that R produces no output — it throttles the RS join and routes more tuples to the ST join, processing data that is actually available. The eddy outperforms both static plans significantly.

Limitation Noted by the Authors

In the delayed-delivery experiment, the eddy does not adapt as well as theoretically possible. The windowed lottery scheme weighs all past observations equally within a window: early observations where the RS join appeared fast (because S was producing output before R arrived) inflate the ticket count of the RS join. The authors note this as an open problem: how to best discount stale observations and adapt more aggressively to initial delays.

7. Impact and Legacy

The eddies paper established a research agenda that influenced a generation of adaptive query processing work. Its most lasting contributions are conceptual:

Merging optimization and execution. Before eddies, optimization and execution were considered separate phases. The paper demonstrated that they could be merged into a single continuous process — an idea that has become central to streaming systems and adaptive databases.

Moments of symmetry as a formal concept. The characterization of when joins can be reordered gave researchers a precise vocabulary for reasoning about adaptive reoptimization. This concept was extended and formalized in subsequent work.

The Telegraph and STREAM lineages. The eddy mechanism became central to the Telegraph distributed query processing system and influenced the design of stream processing systems including STREAM (also at Stanford/Berkeley). The idea that a query processor should treat data as a flow to be routed — not a tree to be traversed — became a foundational paradigm for data stream management.

The routing-as-scheduling analogy. The use of lottery scheduling from operating systems to control tuple routing was an early example of importing scheduling theory into database query processing — a connection that researchers continue to exploit in modern systems that handle mixed workloads and uncertain arrival patterns.
