Scientific Paper · SIGMOD 2016

The Snowflake Elastic Data Warehouse

Benoit Dageville, Thierry Cruanes, Marcin Zukowski, Vadim Antonov, Artin Avanes, Jon Bock, Jonathan Claybaugh, Daniel Engovatov, Martin Hentschel, Jiansheng Huang, Allison W. Lee, Ashish Motivala, Abdul Q. Munir, Steven Pelley, Peter Povinec, Greg Rahn, Spyridon Triantafyllis, Philipp Unterbrunner ACM SIGMOD/PODS 2016 · San Francisco, CA, USA
Abstract Traditional data warehouses were designed for fixed clusters of homogeneous machines with local storage, deep ETL pipelines, and manually tuned physical designs. The cloud changes everything: storage is virtually infinite, compute nodes appear and disappear in minutes, workloads are heterogeneous, and data arrives in semi-structured, schema-less formats. Snowflake is a completely new data warehouse built from scratch for this environment. Its defining architectural decision is the radical separation of storage and compute: data lives in Amazon S3 (shared, durable, infinite), and query execution runs in stateless elastic clusters called virtual warehouses that can be created, resized, or destroyed without moving any data. A third layer of shared Cloud Services handles metadata, transactions, and optimization. The system supports full ANSI SQL with ACID transactions, native semi-structured data types (VARIANT, ARRAY, OBJECT), time travel, cloning, and end-to-end encryption — all with zero tuning knobs for the user.

1. Why Existing Warehouses Failed the Cloud

For decades, data warehousing meant buying a cluster of expensive, identically configured machines, running complex ETL pipelines to load and transform data into a carefully designed star or snowflake schema, and then tuning the physical layout (sort keys, distribution keys, indices) to match the expected query workload. Systems like Teradata, Netezza, and later Redshift were optimized for this world. They were designed as shared-nothing architectures: each node owns its local disks, and data is partitioned across nodes so that most queries touch only the local storage of the nodes that own the relevant data.

Shared-nothing architectures scale well for homogeneous workloads on static clusters. But they have a fundamental problem on the cloud: storage and compute are tightly coupled. If you want to add more compute power, you must also add more storage nodes (even if your storage is fine) and shuffle large amounts of data to re-balance the partitions. If you want to resize the cluster, you trigger an expensive data redistribution. If nodes fail during a resize, the operation can corrupt the cluster state.

The three failure modes of shared-nothing on the cloud

Heterogeneous workload: Cloud instances vary widely in their I/O and CPU characteristics, so a configuration optimized for bulk loading (high I/O, light compute) performs poorly for complex analytical queries (low I/O, heavy compute). You cannot win with one hardware configuration when the workload changes constantly.

Membership changes: Node failures on the cloud are the norm, not the exception. Because shared-nothing nodes own their local data, any failure requires replication and recovery that can involve massive data movement.

Online upgrades: In a tightly coupled system, upgrading software requires coordinating every node simultaneously — there is no way to run two versions of the software side-by-side when every node participates in every query.

Snowflake's founding premise: the coupling of storage and compute is the root cause of all three problems. Separate them completely, and all three go away.

2. The Core Architectural Decision

The central design choice in Snowflake is to use Amazon S3 as the storage layer and handle all query execution in a separate compute layer of stateless virtual machines. S3 is a blob store — you PUT objects, GET objects, and DELETE objects. It has no concept of a filesystem, no local reads, and relatively high access latency compared to local disk. At first glance this seems like a disaster for a high-performance analytical system.

The Snowflake engineers made a crucial observation: for analytical workloads, the bandwidth of sequential reads from S3 is entirely adequate. Analytical queries read large, contiguous chunks of data (entire columns of a table file), not random small records. S3 supports range GET requests — you can download just the bytes you need from a specific offset in an object — which is exactly what columnar storage requires. The high latency of S3 is amortized over large sequential reads.

Intuition — Why decoupling storage and compute is so powerful

Consider two users of the same data warehouse. User A is running complex analytical queries in the morning: she needs lots of CPU and can tolerate higher latency. User B is bulk-loading a terabyte of new data in the afternoon: he needs high I/O throughput and almost no compute. In a coupled system, both users share the same cluster configuration, which is a bad fit for both. In Snowflake, each user can spin up a virtual warehouse of exactly the right size for their workload — independently, simultaneously, against the same shared data — and pay only for the time they actually use.

3. Three-Layer Architecture

Snowflake is structured as three independently scalable, loosely coupled layers that communicate via RESTful interfaces. Each layer can be scaled and upgraded independently without affecting the others.

Layer 1 — Data Storage (Amazon S3)

All table data and query results are stored in S3. Tables are horizontally partitioned into large, immutable files (conceptually equivalent to blocks in a traditional DBMS). Within each file, columns are stored together in a compressed, hybrid columnar format called PAX (Partition Attributes Across). Each file header contains the offsets of each column within the file, so queries can use S3 range GET requests to fetch only the columns they need without reading the entire file. S3 handles replication, durability, and geographic distribution. Snowflake does not manage any of this — it gets 99.999999999% durability for free.

Layer 2 — Virtual Warehouses (Compute)

Virtual warehouses (VWs) are clusters of EC2 instances that execute queries. Each VW is completely isolated — worker nodes are never shared across VWs. VWs can be created, resized, or destroyed at any time without touching the data in S3. Users interact with VWs through abstract "T-shirt sizes" (X-Small through XX-Large) rather than specifying node counts. Each query runs on exactly one VW. Creating or destroying a VW has no effect on the database state — only on query throughput.

Layer 3 — Cloud Services (The Brain)

Cloud Services is a collection of long-lived, multi-tenant services that manage everything that is not query execution: authentication, access control, query parsing, query optimization, transaction management, schema storage, statistics collection, and encryption key management. These services are stateless from the user's perspective (all state lives in a distributed metadata store) and are replicated for high availability. Because they are shared across all users, multi-tenancy amortizes their cost dramatically.

4. Data Storage on S3

Understanding Snowflake's storage design requires understanding what S3 is and is not. S3 is a PUT/GET/DELETE blob store — objects can be written only in full (no in-place updates, no appends), and GET requests can specify a byte range. These constraints had a profound influence on Snowflake's table format and concurrency model.

Because you cannot update a file in place, every write operation (INSERT, UPDATE, DELETE) on a table produces a newer version of the table by adding new files and removing old ones. Old files are not immediately deleted — they are retained for a configurable duration (currently up to 90 days). This file-retention mechanism is the foundation of Snowflake's time travel feature: you can query the state of any table at any point in the retention window.

Snowflake implements ACID transactions via Snapshot Isolation (SI), built on Multi-Version Concurrency Control (MVCC). Every transaction sees a consistent snapshot of the database as of the transaction's start time. Read-only transactions never block writers, and writers never block readers — a critical property for analytical workloads that run long queries concurrently with data loads.

Intuition — How immutable files make MVCC natural

Traditional MVCC systems store old row versions alongside new ones in complex on-disk structures. In Snowflake, the "versions" are entire files. A transaction that started before a file was replaced can still read the old file — it has not been deleted yet. The metadata layer (in Cloud Services) tracks which set of files corresponds to each table version, and the transaction manager knows which version each transaction should see. Implementing MVCC on top of immutable S3 files is not a compromise — it is elegant.

5. Virtual Warehouses

Virtual warehouses are the "muscle" of Snowflake — they execute all queries. Each worker node in a VW maintains a local disk cache of recently accessed table files (S3 objects). The cache is shared across all queries running on that worker node and uses a simple LRU replacement policy. When the cache is warm, performance approaches or even exceeds a pure shared-nothing system because the local cache is much faster than S3.

Cache consistency uses consistent hashing: the query optimizer assigns input file sets to specific worker nodes using a hash of the file name. This means subsequent queries that access the same files will tend to run on the same workers and find those files already in cache. When the set of workers changes (due to failure or VW resize), consistent hashing is lazy — files are not immediately reshuffled. Instead, the LRU cache gradually adapts over subsequent queries. This eliminates the expensive immediate data-shuffle required by eager cache invalidation.

Example — Elasticity in practice

A data load that takes 15 hours on a 4-node VW might take only 2 hours on a 32-node VW. Since Snowflake charges per compute-hour (not per wall-clock hour), the total cost is similar. But the user experience is radically different: analysts can spin up large VWs for time-sensitive queries and shut them down when done, matching resource usage to momentary demand. Multiple teams can run separate VWs simultaneously, querying the same shared data in S3, without interfering with each other.

The execution engine inside each VW is columnar, vectorized, and push-based. Columnar means data is stored and processed one column at a time (better cache utilization, SIMD opportunities). Vectorized means operators process data in batches of a few thousand rows rather than row-by-row or materializing the full result (inspired by MonetDB/X100). Push-based means operators push their output downstream rather than waiting to be pulled (eliminates the overhead of the Volcano-style pull model and improves pipelining).

6. Cloud Services

Cloud Services is the brain of the system. Unlike Virtual Warehouses (which are ephemeral and user-specific), Cloud Services is long-lived and multi-tenant — all users share the same Cloud Services infrastructure, though data isolation is enforced at every level.

The query optimizer in Cloud Services follows a Cascades-style approach with top-down cost-based optimization. All statistics needed for optimization are automatically maintained as data is loaded and updated — no user-invoked ANALYZE or VACUUM commands. Because Snowflake does not use indexes, the plan search space is smaller than in systems that consider index usage, which makes the optimizer more robust (fewer bad plans due to stale index statistics).

An important optimization technique is pruning: instead of indexes, Snowflake maintains small materialized aggregates (min and max values, also called zone maps) for each column in every table file. Before scanning a file, the optimizer checks these aggregates against the query predicates. If the predicate can never match any value in the file (e.g., the query asks for WHERE x >= 6 and the file's max value for x is 5), the file is skipped entirely. This is called micro-partition pruning and can eliminate the vast majority of I/O for selective queries.

Definition — Static and Dynamic Pruning

Static pruning happens during query optimization: the optimizer checks zone maps against the query predicates before generating the execution plan and marks files as irrelevant. Dynamic pruning happens during execution: as Snowflake processes a hash join's build side, it collects statistics on the join keys and uses them to skip files on the probe side that cannot possibly match. This is especially powerful for star-schema queries where a small dimension filter should eliminate most of the large fact table.

7. Feature Highlights

Continuous availability and online upgrades. Because all hard state lives in the distributed metadata store (not in VW worker nodes), Snowflake can run two versions of the software side-by-side simultaneously. When a new version is deployed, user accounts are progressively switched to the new version. All in-flight queries complete on the old version. Once all users and queries have migrated, the old version is shut down. There is no maintenance window, no downtime. The paper reports weekly production deployments managed this way.

Time travel and cloning. Because old file versions are retained, any table can be queried at any past timestamp within the retention window: 

SELECT * FROM my_table AT(TIMESTAMP => '2015-05-01 16:20:00');

Cloning a table is instantaneous — it copies only the metadata (the list of files that make up the table), not the actual data files. Both the original and the clone point to the same S3 files. Either can be modified independently thereafter; Snowflake uses copy-on-write semantics (new files are added for modifications, original files remain). This makes it trivially cheap to take snapshots before risky operations.

End-to-end encryption. Snowflake uses AES-256 encryption with a hierarchical key model anchored in AWS CloudHSM. There are four layers: root keys, account keys, table keys, and file keys. Each layer encrypts the layer below. Table keys rotate monthly; after one year, data is rekeyed using new keys. This ensures that even if a key is compromised, only a bounded amount of data is at risk. Critically, the cloud provider (Amazon) never sees any data in the clear — all encryption and decryption happens client-side before data is written to or after it is read from S3.

8. Semi-Structured Data

One of Snowflake's most distinctive features is its native support for semi-structured, schema-less data. Traditional data warehouses required data to be transformed into a fixed relational schema before loading — a process that can take months to design and days to execute. Snowflake introduces the VARIANT type, which can store any JSON, Avro, or XML value.

A column of type VARIANT is stored in a serialized binary representation that supports fast key-value lookup, type tests, and comparison. But Snowflake goes further: when a VARIANT column is stored, the system performs statistical analysis of the documents to identify paths that are frequently present and have consistent types. These paths are automatically extracted and stored as separate typed columns in the same compressed columnar format as regular relational data. This is called optimistic conversion.

Intuition — Schema-on-read without sacrificing performance

Imagine a table of JSON records where 95% of records have a numeric field user_id. Snowflake detects this pattern and stores user_id as a native integer column alongside the original VARIANT column. A query that filters on user_id can use the extracted integer column (enabling pruning, efficient comparison, and columnar compression) rather than deserializing every JSON document. The original VARIANT column is still available for documents that do not have the field, or for schema-exploration queries. The user sees schema flexibility; the optimizer sees typed columns.

Snowflake also supports SQL extensions for navigating semi-structured data: dot notation and bracket notation for field extraction, FLATTEN for converting arrays into rows, and ARRAY_AGG for the reverse. These SQL extensions make it possible to write complex JSON transformation queries without writing any application code.

9. Lessons Learned

The paper closes with a candid lessons-learned section that is unusually honest for an academic paper about a commercial system. Among the key points:

The SaaS model transformed development. With a single production version deployed continuously, the team could release features and fix bugs weekly rather than annually. Users got improvements immediately. The team discovered problems faster and fixed them faster. The development model itself became a competitive advantage.

Hadoop did not replace RDBMSs — it complemented them. Many early Snowflake customers used Hadoop for storing JSON and Snowflake as the SQL interface for analysis. Rather than displacing Hadoop, Snowflake found itself being used alongside it.

Core query performance was not the bottleneck. Because elastic virtual warehouses could always provide more compute, the team's greatest challenges were in the SaaS and multi-tenancy aspects — handling hundreds of users with varying workloads, managing node failures at scale, and maintaining security across a shared infrastructure. Interestingly, the paper notes that a zero-knob approach (no tuning parameters) turned out to be both a design goal and a genuine differentiator: most users simply did not have the database administration expertise to tune traditional systems, and removing that requirement opened Snowflake to an entirely new class of customers.

Lasting impact

Snowflake's multi-cluster shared-data architecture became the blueprint for cloud-native data warehousing. Amazon Redshift Serverless, Google BigQuery, Microsoft Azure Synapse Analytics, and Databricks' Photon engine all adopt variations of the storage/compute separation Snowflake pioneered. The paper is frequently cited as the first rigorous description of a production cloud-native OLAP system built around commodity blob storage, and its lessons shaped the design of virtually every major data warehouse introduced after 2016.
