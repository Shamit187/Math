Accelerating Approximate Analytical Join Queries over Unstructured Data with Statistical Guarantees

Yuxuan Zhu, Tengjun Jin, Chenghao Mo, Daniel Kang — University of Illinois Urbana-Champaign Proceedings of the ACM on Management of Data, Vol. 4, No. 3 (SIGMOD) · June 2026 · doi:10.1145/3802004
Abstract Analysts increasingly want to run SQL-style aggregate queries — COUNT, SUM, AVG — over joins whose condition is semantic: "these two company descriptions refer to firms that build similar products," "these two video frames show the same car." Deciding whether a pair satisfies such a condition requires an expensive machine-learning model or LLM, called here the Oracle. Running the Oracle on every pair (the exact answer) is prohibitively costly — quadratic in table size, exponential in the number of tables. Two cheaper approximations exist, and each fails in its own way: embedding-based blocking keeps only high-similarity pairs but silently discards true matches, biasing the answer and producing invalid confidence intervals (errors up to 79% larger than reported); sampling stays unbiased but is crippled when positive pairs are rare. This paper proposes Blocking-augmented Sampling (BaS), which orchestrates the two by splitting the search space along the embedding's own failure modes — using the Oracle directly where false positives dominate, and importance sampling where false negatives dominate — and adaptively allocating a fixed Oracle budget between them. BaS delivers valid confidence intervals and reduces root-mean-squared error by up to 19× over state-of-the-art baselines across text, image, and bimodal datasets.

1. The Problem: Aggregates over Semantic Joins

A join in classical SQL matches rows on an exact key: orders.customer_id = customers.id. The match is cheap, deterministic, and indexable. Now consider an investor who wants the average stock-price gap between pairs of companies that build similar products. There is no key for "builds similar products." The only reliable way to decide whether two company descriptions match is to ask a capable model — a fine-tuned classifier, a vision-language model, or an LLM. The query reads:

Motivating query — average price gap among similar companies 
SELECT AVG(c1.price - c2.price)
FROM   companies AS c1 JOIN companies AS c2
ON     NL('Company: {c1.description} and Company: {c2.description}
          build similar products');

NL(·) is a natural-language join predicate. Its truth value for any given pair is decided by the Oracle. The aggregate is ordinary SQL; the cost is anything but.

Definition — the Oracle

The Oracle is a method that takes a pair of records and returns the ground-truth label for whether they satisfy the join condition. It is assumed to be the state-of-the-art decision procedure — an LLM judging whether two sentences name the same entity, a fine-tuned model judging whether two images show the same car, or even a human annotator. Crucially, the Oracle is treated as ground truth: it defines what "true" means for the join, so anything that disagrees with it — such as the embedding — is by definition the thing that is wrong. (This is what lets us speak of a "false positive" or "false negative" later.) The Oracle is accurate but expensive, so the whole game is to invoke it as few times as possible while still answering the aggregate accurately.

How expensive? Labelling every pair in the Magellan Company dataset with the Oracle method means $567$ million tokens — about \$709\text{K}$ with GPT-4o, or \$43\text{K}$ with GPT-4o mini. The number of Oracle calls grows at least quadratically with the number of records and exponentially with the number of tables joined. Exact pairwise evaluation is simply off the table for analytics.

The one-sentence problem

We want an aggregate over a join, the join predicate can only be checked by an expensive model, and we have a fixed budget of how many times we may call that model. Spend the budget to return both a good estimate and an honest confidence interval around it.

2. Query Syntax and Semantics

JoinML — the prototype system in this paper — extends SQL with a budget and a confidence level. The user writes a linear aggregate (COUNT, SUM, or AVG) over one or more joins with natural-language conditions, and adds a clause stating how much Oracle work is permitted and how confident the interval should be.

JoinML query syntax 
SELECT {AVG | SUM | COUNT} {field | EXPR(field)}
FROM   table_1 JOIN table_2 JOIN ...
ON     NL(join_condition) AND ...
ORACLE BUDGET b WITH PROBABILITY p

Two ingredients define the semantics. The Oracle (above) gives ground truth on a pair. The embedding similarity is a cheap proxy: embed each record individually with a pre-trained model, then take the cosine similarity of the two vectors,

$$\operatorname{sim}\big(e(r_1), e(r_2)\big) = \frac{e(r_1) \cdot e(r_2)}{\lVert e(r_1)\rVert \, \lVert e(r_2)\rVert}.$$

Because the embedding is computed per record rather than per pair, it is orders of magnitude cheaper than the Oracle — but it does not see the joint semantics of a pair, so it is only an approximation of the truth. The entire method is built around exploiting this cheap signal while being honest about where it lies.

Query semantics & the guarantee

A JoinML query returns a point estimate $\hat{\theta}$ and a confidence interval $[L, U]$. Let $\theta$ be the answer that exhaustive Oracle evaluation would give. With budget $b$ and probability $p$, JoinML guarantees: (1) the Oracle is called on no more than $b$ pairs; and (2) $P[L \le \theta \le U] \ge p$.

3. Use Cases

Semantic joins show up wherever the matching rule is fuzzy. The paper highlights three, each with a natural aggregate.

  • Business analysis — the motivating AVG query above: compare related companies' prices by joining on "build similar products."
  • Plagiarism analysis — join an article's sentences against a reference corpus on "is paraphrased from," then COUNT the matches to get a paraphrase rate.
  • Traffic analysis — join two roadside videos on "shows the same car," then AVG the timestamp difference to estimate travel time across a segment.
Plagiarism: a COUNT over a paraphrase join 
SELECT COUNT(*)
FROM   article JOIN db
ON     NL('{article.sentence} is paraphrased from {db.sentence}');

A fourth, more subtle use case is join-order optimization. Planning a multi-way semantic join well requires cardinality estimates for its sub-joins, but those estimates are exactly the expensive COUNTs above. Because BaS can produce a tight COUNT confidence interval from a small budget, a query optimizer can use it to pick a good join order without ever materializing the full pairwise evaluation.

4. The Two Baselines and How Each Fails

Before the new method, it helps to see precisely why the two standard tools break. They fail for opposite reasons, and that opposition is what BaS later exploits.

4.1 Embedding-based Blocking — fast but biased

A concrete example of both tools

Picture matching products across two catalogs. Table A holds "Apple iPhone 13, 128 GB, Blue" and Table B holds "iPhone 13 — 128GB, colour: blue, unlocked". To a human these are obviously the same phone, so the Oracle would label this pair a match. Watch how each baseline treats it.

Blocking turns each record into an embedding vector and keeps a pair only if their cosine similarity clears a threshold, say $\tau = 0.75$. The wording differs enough — "Apple" vs. no brand, "Blue" vs. "blue, unlocked" — that the embedding scores this true match at only $\cos = 0.62$. Because $0.62 < 0.75$, blocking discards the pair and the real match is never counted — a textbook false negative. Meanwhile an unrelated pair, "Apple iPhone 13" vs. "Apple iPhone 13 screen protector", shares more surface words and scores $\cos = 0.81$, so blocking keeps it even though it is not a match. Fast, but the mistakes are baked in.

Sampling ignores the embedding and draws pairs uniformly at random from the full cross product. With $100{,}000$ records on each side there are $10^{10}$ candidate pairs but perhaps only $50{,}000$ genuine matches — a selectivity of $5 \times 10^{-6}$. A random draw lands on a true match roughly once in every two hundred thousand pairs, so you must call the Oracle an enormous number of times before you have seen enough matches to trust the estimate. Honest, but expensive — exactly the tension Section 4.2 quantifies.

Yes — and what "sampled enough" really means

Your picture is exactly right: uniform sampling keeps drawing random pairs, asks the Oracle whether each one matches, and the number it returns is an approximation of the true aggregate, never the exact value. Two refinements sharpen the "after a while, this is probably the result" intuition.

First, it does not stop on a hunch. The budget $b$ — the maximum number of Oracle calls allowed — is fixed before sampling begins, so "enough" simply means "the budget is spent," not a feeling that we have seen plenty. Second, "probably the result" is made precise. The confirmed matches feed a running average, and the central limit theorem turns that average into a point estimate $\hat{\theta}$ together with a confidence interval $[L, U]$ that says how far the approximation might sit from the truth — so the method reports not just a guess but an honest margin around it.

The catch is the very thing this section is about: when matches are rare — a selectivity of $5 \times 10^{-6}$ in the example above — a random draw almost never lands on one, so the budget runs out long before the interval $[L, U]$ is narrow enough to be useful. The estimate stays honest, but it can be too loose to act on. Closing that gap is exactly what Blocking-augmented Sampling does later in the paper.

Blocking, the workhorse of entity-matching systems, keeps only pairs whose embedding similarity exceeds a threshold $\tau$ and runs the Oracle on just those. The threshold can even be calibrated on a validation set. The trouble is the false negative: a genuinely matching pair whose embedding similarity happens to be low gets filtered out and never counted.

Why blocking has no statistical guarantee

Discarding low-similarity matches skews every aggregate toward the high-similarity region. As the Oracle budget grows, blocking's point estimate converges — but to the wrong limit: a fixed bias that does not vanish no matter how large the budget gets. Meanwhile its confidence interval shrinks toward zero width. An interval can be narrow yet wrong — shrinking it around a biased center just makes blocking confidently wrong. Eventually the true error sits outside the reported interval: the paper measures errors up to 79% larger than the confidence interval claims, even with a calibrated threshold. Blocking is fast but cannot tell you when it is wrong.

4.2 Sampling — honest but inefficient

Uniform sampling draws pairs at random, runs the Oracle on the sample, and uses the central limit theorem to build a valid confidence interval. It is unbiased and honest. But positive pairs (the pairs the Oracle labels as matching) in a cross product (the set of all candidate pairs, one per combination of records across the tables) are extremely sparse. The selectivity — the fraction of all candidate pairs that actually match — in the paper goes as low as $5 \times 10^{-10}$. Hitting enough positives to pin down the answer takes an enormous sample: reaching just 5% error on the Company dataset needs about $1.4 \times 10^{7}$ Oracle calls — roughly $20$ billion tokens, or \$26\text{K}$ with GPT-4o.

The tension, stated plainly

Blocking trusts the embedding too much (and inherits its false negatives as bias). Sampling ignores the embedding entirely (and pays for it in variance). Neither uses the embedding for exactly what it is good at. The contribution of this paper is a method that uses the embedding where it is reliable and falls back to honest sampling where it is not.

5. Weighted Wander Join: Embeddings as an Approximate Index

The first building block sharpens sampling. Wander Join is an efficient join-sampling algorithm for structured data: it performs random walks across tables, at each step jumping only to records that satisfy the join condition. That requires an index over the join key — which semantic joins do not have. Without an index, Wander Join degenerates into uniform sampling.

Weighted Wander Join (WWJ) replaces the missing exact index with an approximate one built from embeddings. At each step of the walk it samples the next record with probability proportional to its embedding similarity to the current one, rather than uniformly. High-similarity (likely-matching) records get visited more often.

WWJ is importance sampling in disguise

The idea is importance sampling: sample promising items more often, then divide each observation by the probability of having sampled it, so the average stays unbiased. Each complete walk from table $T_1$ to $T_n$ corresponds to one tuple in the cross product. At every step the per-step similarities to the candidate next records are normalized into a probability distribution, and the walk draws from it; the resulting sampling weight of a tuple is the product of those per-step similarities:

$$w(t_1, \dots, t_n) = \frac{1}{|T_1|} \prod_{i=2}^{n} \operatorname{sim}\big(e(t_{i-1}), e(t_i)\big).$$

The probability that the walk selects a given tuple is proportional to this weight. Dividing each Oracle observation by that selection probability gives an unbiased estimate and a valid confidence interval by the standard recipe — upweighting promising pairs reduces variance without introducing bias. (One knob here is the weight exponent: the similarity score is raised to a power before being normalized into the per-step probability, sharpening or flattening the walk's preference for high-similarity records. The paper finds the best results at exponent $1$ — i.e. the raw similarity.)

Why WWJ is cheap

Enumerating the cross product to do importance sampling naively would cost $O\!\left(\prod_{i} |T_i|\right)$ — exponential in the number of tables. WWJ instead decomposes the walk into sequential steps, comparing the current tuple only against the next table's records. For a budget $b$ the cost scales as $O\!\left(b \cdot \sum_i |T_i|\right)$ — linear in table size, sidestepping the combinatorial blowup.

WWJ's failure mode: false positives

WWJ is only as good as the embedding's precision. When high-similarity pairs really are matches, WWJ converges to indexed Wander Join — the best case. But when there are many false positives — pairs that look similar yet violate the join condition — WWJ keeps spending budget sampling them, and its efficiency collapses back to that of uniform sampling or worse. State-of-the-art embeddings still produce these false positives (e.g. a 99% false-positive rate for OpenAI embeddings on the Company dataset).

6. Blocking-augmented Sampling: Using Each Tool Where It Wins

Here is the central idea. The two baselines fail on opposite halves of the similarity spectrum. Blocking is wrecked by false negatives, which live among low-similarity pairs. WWJ is wrecked by false positives, which live among high-similarity pairs. So split the space at the threshold and apply each method where it actually wins.

The two regimes of BaS

BaS treats the blocking threshold not as a static filter but as a dynamic decision boundary that partitions the cross product $S = S_b \cup S_s$:

  • Blocking regime $S_b$ — high similarity, high false-positive risk. Here BaS runs the Oracle directly on every pair, eliminating the variance WWJ would suffer from repeatedly sampling false positives.
  • Sampling regime $S_s$ — low similarity, high false-negative risk. Here BaS runs WWJ (the importance-sampling estimator of Section 5), which (unlike blocking) does not ignore the true matches that blocking would have discarded — restoring the statistical guarantee.

For a linear aggregate the two regimes simply add. With the Oracle giving the exact value over $S_b$ and WWJ estimating the rest:

$$\widehat{\mathrm{COUNT}} = \mathrm{COUNT}_{S_s} + \mathrm{COUNT}_{S_b}, \qquad \widehat{\mathrm{SUM}} = \mathrm{SUM}_{S_s} + \mathrm{SUM}_{S_b}.$$

Because the WWJ estimator over $S_s$ is unbiased and the blocking-regime contribution is exact, the combined COUNT and SUM estimators are unbiased. AVG is a ratio of two such estimators, and the expectation of a ratio is not the ratio of the expectations — so even with unbiased numerator and denominator the ratio carries a finite-sample bias (of order $O(1/b)$), which is why it is only asymptotically unbiased. The paper adds a Taylor-expansion bias correction that removes the leading term, dropping the bias to order $O(1/b^2)$.

Why this is more than stratified sampling

In ordinary stratified sampling the strata are fixed in advance. In BaS the boundary between "compute exactly" and "sample" is itself the decision variable, chosen to minimize error. Two questions remain, and they are the heart of the method: where exactly should the boundary go, and how do we get a valid confidence interval after stitching two regimes together?

7. Adaptive Allocation via Two-Stage Stratified Sampling

Choosing the boundary tuple-by-tuple over a trillion-pair cross product is hopeless, so BaS lifts the problem to strata. It sorts the top-similarity pairs and cuts them into $m$ equal-size strata; the goal is to decide which strata go into the blocking regime so as to minimize the mean-squared error of the estimate under the budget.

The allocation problem

Given strata $S_0, \dots, S_m$, an aggregate, similarity scores, and budget $b$, find the allocation $A^\ast$ — a subset of strata sent to blocking, the choice that minimizes the estimator's mean-squared error (MSE) — the average squared gap between estimate and truth, which we want small:

$$A^\ast = \arg\min_{A \subseteq \{S_1, \dots, S_m\}} \operatorname{MSE}_{\mathrm{AGG}}(A, b, \dots).$$

Recall a stratum is just one equal-size group of pairs, and a regime is the method (blocking or sampling) applied to a group. For the unbiased SUM and COUNT estimators the MSE is simply the sum of the per-stratum sampling variances over the strata left in the sampling regime — a stratum sent to blocking contributes zero variance because the Oracle gives its exact value. (For AVG and MEDIAN the objective also carries a bias term, so it is not a pure sum of variances.) The catch: that variance depends on the Oracle labels, which we have not yet paid for. The solution is a two-stage scheme.

The two stages

Stage 1 — pilot sampling. Spend a small slice $b_1$ of the budget to draw pilot samples and estimate each stratum's variance. From these estimates, solve the allocation problem to get the boundary $\hat{A}$.
Stage 2 — execute. Spend the remaining budget $b_2$ running the Oracle on the chosen blocking strata and WWJ on the rest, assigning each sampling stratum a budget proportional to its summed similarity scores. This is the WWJ proposal rule — it matches importance sampling's own weighting, and is distinct from classical variance-optimal (Neyman) allocation. Concretely, a stratum holding, say, 30% of the sampling regime's total similarity mass receives about 30% of the sampling budget, drawn via WWJ walks. Oracle results from the pilot stage are cached so no pair is labelled twice.

The paper proves the estimated allocation converges to the true optimum at rate $O\!\left(1/\sqrt{b_1}\right)$, since the sample mean and variance used to choose the boundary converge at that rate and the arithmetic that turns them into an MSE does not change it. Two distinct knobs are in play here. The pilot slice $b_1$ is a few percent of the budget spent on Stage 1 to estimate variances; the paper found values from 0.1% to 10% all preserve validity, so there is no single magic default. Separately, the blocking reserve is the slice held back for the "maximum blocking regime" BaS stratifies over — the cold-start recommendation is 15–30% of the budget. BaS also auto-tunes $m$, the number of strata, so each stratum gets at least 1,000 Oracle calls (enforcing a minimum of $m = 5$ for small budgets).

8. Confidence Intervals via Bootstrap-t

Stitching two dependent stages together breaks the usual recipe for intervals. The combined sample is not independent and identically distributed — the pilot stage chose where the second stage sampled — so applying the central limit theorem naively would yield intervals that cover the truth less often than advertised.

Bootstrap-t resampling for valid coverage

BaS instead constructs intervals by resampling the observed data. The bootstrap fakes many fresh datasets by re-drawing, with replacement, from the one sample we already have, to see how much the estimate wobbles. Given the sample $X$ and confidence $p$:

  1. Compute the estimate $\hat{\theta}$ and its variance $\hat{\sigma}^2$.
  2. Draw a resample $X^\ast$ of size $|X|$ from $X$ with replacement; recompute $\hat{\theta}^\ast, \hat{\sigma}^{\ast 2}$.
  3. Form the studentized statistic — the deviation scaled by its own estimated standard error — $z^\ast = (\hat{\theta}^\ast - \hat{\theta}) / \hat{\sigma}^\ast$.
  4. Repeat 1,000 times and take percentiles of $z^\ast$. Note the crossover: the lower percentile $z_{\ell}$ forms the upper endpoint and the upper percentile $z_{u}$ the lower endpoint, as the displayed formula does by subtracting each from $\hat{\theta}$: $[\hat{\theta} - z_{u}\hat{\sigma},\; \hat{\theta} - z_{\ell}\hat{\sigma}]$.

Two separate guarantees are at work. First, the estimator is smooth enough that the bootstrap is consistent — the resampled intervals are asymptotically valid (this is the first-order guarantee, proved via Hadamard differentiability of the estimator; Theorem 23.9 of van der Vaart, where SUM and COUNT are linear functionals and AVG a ratio of differentiable ones). Second, and under extra smoothness, the studentization buys a refinement: it corrects for skew and tightens coverage accuracy to order $O(1/b^2)$. Notably, the interval computation is independent of the allocation — skipping it saves time but does not change accuracy, so latency-bound users can spend that time on a larger Oracle budget instead.

9. Beyond SUM: Other Aggregates and Queries

The SUM machinery extends to the rest of the analytic vocabulary, each requiring a twist:

  • AVG — a ratio estimator with the Taylor bias correction of Section 6; its MSE is estimated from the variances of SUM and COUNT. Because SUM and COUNT are computed on the same sample they are in fact correlated, so treating the SUM and COUNT estimators as independent is an approximation — the bootstrap-t step corrects the resulting coverage.
  • MIN / MAX — here the goal is not minimizing global variance but maximizing the probability the true extremum lands in the blocking regime. The largest value in a sample does not follow the usual bell curve, so the standard normal-based interval does not apply; BaS models each stratum's value distribution with Extreme Value Theory and allocates accordingly. Since the sample maximum is non-normal in this sense, the interval uses the observed max as a lower bound and the global (join-ignoring) max as an upper bound.
  • MEDIAN — BaS estimates the CDF by combining the exact distribution from blocking with the weighted empirical distribution from sampling, then inverts at $0.5$; allocation focuses variance reduction on strata near the estimated median.
  • GroupBy — instead of total variance, BaS minimizes the maximum relative error across groups, prioritizing strata dense in hard-to-estimate "tail" groups, with simultaneous intervals across groups.

BaS also handles selection queries with a recall target. Recall here is the fraction of the true matches the query actually returns; a query is approximately correct if it returns at least a fraction $\gamma$ of the true matches with probability $p$. BaS maximizes the output threshold by allocating data to minimize the recall burden left to the sampling regime, using an upper bound on the count — with $v$ the estimated count and $s^2$ its variance:

$$\mathrm{UB}(v, s^2, p, b) = v + \sqrt{2\, s^2 \log\tfrac{1}{1-p}}.$$

A TopK heavy-hitter query — the $k$ entities appearing most often — is handled by estimating each entity's COUNT and minimizing the swapping probability between the $k$-th and $(k{+}1)$-th ranked entities, using simultaneous bootstrap-t intervals so the lower bound of rank $k$ exceeds the upper bound of rank $k{+}1$.

10. Theoretical Guarantees

The theory answers two questions: does adaptive allocation reach the optimum, and is BaS ever worse than plain WWJ?

Theorem 6.1 — convergence to the optimal allocation

The MSE under the estimated minimizer $\hat{A}$ approaches the MSE under the true minimizer $A^\ast$ at rate

$$\frac{\operatorname{MSE}(\hat{A}) - \operatorname{MSE}(A^\ast)}{\operatorname{MSE}(A^\ast)} = O\!\left(\frac{1}{\sqrt{b_1}}\right).$$

More pilot budget $b_1$ buys a sharper boundary, and the gap to optimal shrinks at the canonical square-root rate.

Theorem 6.2 — BaS outperforms or matches WWJ

If a separating allocation exists for which the sampling-regime distribution is closer to the ideal — the optimal importance-sampling distribution — and the sampling regime's matching tuples are sparser, then BaS strictly improves on WWJ by a shrinkage coefficient $\alpha$ (less than 1):

$$\operatorname{MSE}^{\mathrm{BaS}}_{\mathrm{SUM}} = \alpha \cdot \operatorname{MSE}^{\mathrm{WWJ}}_{\mathrm{SUM}} + O\!\left(b_1^{-1} b^{-1/2}\right),$$

with coefficient $\alpha < 1$. When those conditions do not hold, the two methods are equal up to a term that vanishes faster than the MSE itself — so BaS is never asymptotically worse than WWJ.

Reading the two conditions

The first condition says: pruning false positives via blocking makes the sampling distribution look more like the ideal one. The second says: when the embedding has high recall, the blocking regime already swallows most true matches, leaving the sampling regime genuinely sparse. Both are exactly the situations real embeddings create — which is why BaS wins in practice, not just in theory.

On cost: BaS's CPU-side bookkeeping (sorting the top records, stratifying) is more expensive than uniform sampling but trivially cheap next to the Oracle. The paper measures up to 90 seconds of CPU time costing about \$0.03$ on AWS per query — set that against the millions of Oracle calls (and the thousands of dollars) an exhaustive or uniform approach would spend on the same query, and the bookkeeping is roughly $10^6\times$ cheaper than the Oracle calls it saves. For cross products too large to materialize, BaS swaps exact thresholding for nearest-neighbor blocking and keeps the same favorable scaling.

11. Evaluation

BaS is implemented in a prototype, JoinML, and evaluated on 16 datasets spanning text, image, and bimodal data — six real-world (Company, Quora, Webmasters, Roxford, Flickr30K, VeRi), seven from the SemBench benchmark, and three synthetic stress tests. Join selectivities range across ten orders of magnitude, and cross products reach 1.3 trillion pairs. Baselines are Uniform sampling; Blocking (a proxy for Ditto — deep entity matching); Abae (stratified-sampling approximate query processing, AQP) and BlazeIt (video-aggregation AQP with control variates) for state-of-the-art AQP with ML predicates; and, for selection queries, SUPG (recall-guaranteed selection) and LOTUS (LLM semantic queries).

11.1 Statistical guarantees hold; blocking's do not

The validity metric is the error ratio: the true error divided by the half-width of the reported interval. A valid 95% interval needs its 95th-percentile error ratio to stay at or below 1.

$$\text{Error ratio} = \frac{|\hat{\theta} - \theta|}{(U - L)/2}.$$

Across COUNT, SUM, AVG and MEDIAN and over 500 repetitions per budget, BaS keeps its 95th-percentile error ratio below 1 everywhere — valid intervals. Blocking fails on every query, with true error up to 79% beyond its interval, and it gets worse as the budget grows, because its interval shrinks around a biased estimate. BaS stays valid even at a tiny budget of 1,000 Oracle calls and across pilot fractions from 0.1% to 10%.

11.2 End-to-end accuracy

Headline numbers
  • BaS reduces relative RMSE by 1.04×–19.5× versus the best of Uniform, Abae and BlazeIt, and by up to 17.2× versus WWJ.
  • Overall, up to 21× lower error and up to 188× cost savings on real datasets.
  • On the 6-way Company-Scale join (selectivity $5 \times 10^{-10}$), Uniform sampling failed to find enough positives to estimate at all; BaS stayed low-error.
  • Non-linear aggregates: up to 1.4× lower error for MEDIAN, 2.0× for MAX, 3.0× for MIN, and 2.1× across groups for GroupBy.

BaS adapts to selectivity. In low-selectivity (rare-match) regimes it wins big — up to 19.5× — because blocking concentrates the budget where matches actually are. In high-selectivity regimes, where blocking offers little, BaS adaptively shifts budget toward sampling and simply matches WWJ rather than regressing like Blocking does. It also extends cleanly to multi-way joins (3-, 4-, and 6-way), where Abae and BlazeIt do not natively apply.

11.3 Selection, join ordering, and ablations

For selection queries at matched 95% recall, BaS improves precision by 2.6–43.8% over LOTUS and 3.0–68.6% over Uniform; on a TopK heavy-hitter query (where LOTUS has no guaranteed support) BaS gains 9.6–10.7% precision. Plugged into a DPccp join-order optimizer, BaS's accurate COUNT estimates cut the execution cost of a multi-way semantic join by up to 12.7% versus Uniform- or WWJ-based estimates.

Does the adaptive allocation actually find the optimum?

The ablation compares adaptive allocation against brute-forced optimal and worst fixed allocations. Adaptive lands within 1.61–18.9% of optimal (7.04% on average), while the worst fixed allocation can be up to 99.9% worse — confirming both that allocation matters enormously and that BaS's pilot-based choice is close to ideal. A sensitivity study shows BaS stays ahead of baselines across nine embedding models, blocking ratios from 10–30%, and weight exponents, with the best results at exponent 1.

A counter-intuitive finding

On the Company dataset, old-fashioned TF-IDF sometimes beats modern dense embeddings (e.g. OpenAI): the join needs sharp lexical precision — a radio company is not a television company — and dense embeddings cluster same-industry firms together, manufacturing false positives (99% FPR for OpenAI vs. 27% for TF-IDF). The lesson is not "use TF-IDF" but that BaS provides valid guarantees regardless of embedding quality, and improves further as embeddings improve.

12. Related Work and Conclusion

BaS sits at the intersection of three lines of work. Approximate query processing contributes join-sampling algorithms — correlated sampling, universe sampling, ripple join, and Wander Join — all of which assume structured keys that semantic joins lack. Entity matching contributes blocking, from rule-based suffix arrays and sorted neighborhoods to learning-based blockers like Ditto. AQP for unstructured data contributes systems like BlazeIt, SUPG and Abae that give guarantees for selection or aggregation over ML predicates, but not for joins. BaS's contribution is to bring statistical guarantees to the semantic-join case by combining sampling and blocking rather than choosing one. Work that optimizes the physical cost of the join operator (e.g. batching many pairs into one LLM prompt) is complementary: BaS decides which pairs to check; the complementary line of work reduces the cost of checking each one.

The takeaway

Embeddings are an unreliable narrator: cheap, informative, but prone to both false positives and false negatives. Blocking believes the narrator; sampling ignores it. BaS does neither — it reads the narrator's two failure modes off the similarity axis, runs the Oracle where the narrator over-claims and samples where it under-claims, and adaptively tunes the boundary from a cheap pilot. The result is the first method to give both honest confidence intervals and high efficiency for analytical joins over unstructured data — up to 19× lower error and 188× cheaper than the state of the art.
