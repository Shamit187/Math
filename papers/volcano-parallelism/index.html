Encapsulation of Parallelism in the Volcano Query Processing System

Goetz Graefe Proceedings of ACM SIGMOD 1990 · University of Colorado, Boulder
Abstract Volcano is a new dataflow query processing system designed for database systems research and education. The uniform interface between operators makes Volcano extensible by new operators. All operators are designed and coded as if they were meant for a single-process system only. When attempting to parallelize Volcano, the authors had to choose between two models of parallelization—the bracket model and the operator model. By rejecting the bracket model, they introduce the novel operator model and provide details of Volcano's exchange operator that parallelizes all other operators. The exchange operator encapsulates all parallelism issues and therefore makes implementation of parallel database algorithms significantly easier and more robust. Included in this encapsulation is the translation between demand-driven dataflow within processes and data-driven dataflow between processes.

1. The Volcano System

Volcano was built at the University of Colorado as a testbed for database systems research. Its design goals were extensibility—the ability to add new operators easily—and efficiency, without sacrificing either for the other. The system is small: fewer than two dozen core modules totaling about 15,000 lines of C. Those modules include a file system, buffer management, sorting, top-down B*-trees, and a pair of algorithms for natural join, semi-join, outer join, anti-join, aggregation, duplicate elimination, division, union, intersection, difference, anti-difference, and Cartesian product.

The most important module—and the focus of this paper—is the exchange operator. It was designed and implemented after all other modules, with a specific goal: to parallelize every existing query algorithm without modifying a single line of their implementations. This goal was almost entirely achieved.

Intuition — The core promise

Parallelism in query processing is normally implemented by modifying each algorithm to be aware of multiple processes, partitioned data, and inter-process communication. This is expensive and error-prone: every time a new algorithm is added, its parallel version must be written separately. Volcano's insight is to factor all of this complexity into one module—the exchange operator—so that algorithm developers never think about parallelism at all. Write once for a single process, parallelize automatically.

2. The Iterator Model: Open, Next, Close

Before understanding the exchange operator, you need to understand how Volcano structures query execution. All query processing operators in Volcano are implemented as iterators that support a simple three-procedure interface: open, next, and close. This model, sometimes called the Volcano iterator model or the pull model, works as follows:

Definition — The Iterator Interface
  • open(): Initialize the operator's state record. For a hash join, this might allocate the hash table. For a file scan, it opens the file. After open, the operator is ready to produce its first tuple. Critically, open calls open on all input operators recursively—the entire query tree initializes in one top-down open traversal.
  • next(): Return the next output tuple, or an end-of-stream indicator if no more tuples are available. The return value is a NEXT_RECORD structure: a record identifier and a record address in the buffer pool. To get the next tuple, an operator typically calls next on its inputs, processes the result, and returns an output tuple.
  • close(): Shut down the operator and release all resources. Close calls close on all inputs recursively—a single top-level close shuts down the entire query tree.

This interface is the same for every operator in the system. A file scan implements open/next/close. A join implements open/next/close—it calls open on its two inputs during its own open, calls next on them during its own next, and calls close on them during its own close. Because operators do not need to know where their input comes from—only that it implements open/next/close—the system supports what the paper calls anonymous inputs or streams.

Query execution is demand-driven (also called lazy or pull evaluation). The top-level operator in a query plan is called repeatedly with next until it returns end-of-stream. Each next call propagates down the operator tree, pulling tuples from below only as needed. No operator produces output until its consumer asks for it. This is efficient in memory because only one tuple (or a small buffer of tuples) needs to be live in memory at any time for each operator.

Example — A Simple Query Tree

Consider the query tree: PRINT → JOIN → (FILE_SCAN_EMP, FILE_SCAN_DEPT). When the user calls open on PRINT, PRINT calls open on JOIN, which calls open on both FILE_SCANs, which open their respective files. When the user calls next on PRINT, PRINT calls next on JOIN. JOIN calls next on FILE_SCAN_EMP to get the first employee tuple, then calls next on FILE_SCAN_DEPT repeatedly to find matching department tuples, and returns one join result to PRINT. PRINT formats it. This continues until JOIN returns end-of-stream to PRINT.

3. Two Models of Parallelization

When Graefe attempted to parallelize Volcano on a multiprocessor machine, he faced a fundamental design choice. There are two paradigms for parallelizing an iterator-based query engine:

The Bracket Model

In the bracket model (used by GAMMA, Bubba, and others), each operator is wrapped in a generic process template that handles all inter-process communication. The template receives data from upstream processes and sends data to downstream processes via network I/O. The operator itself is "bracketed" between receiving and sending code. The operator code handles only the algorithm; the template handles only parallelism.

The Operator Model

In the operator model (Volcano's approach), parallelism is encapsulated in a single, special operator called the exchange iterator. The exchange operator uses and provides the standard open/next/close interface—it looks like any other operator to those above and below it in the query tree. Internally, it manages all inter-process communication, process forking, flow control, and synchronization. All other operators are coded for a single-process system and need no modification.

The bracket model has a fundamental problem: each locus of control is a separate process, requiring a scheduler process for each operator. When the system is extended with a new operator type, two implementations must be written—the algorithm and its parallel wrapper. The operator model requires only the algorithm; the exchange operator handles the rest.

Why the bracket model fails for extensibility

In the bracket model, operators use network I/O (inter-process communication) as their only means of obtaining input and delivering output. This means every operator in a parallel plan crosses process boundaries on every tuple—even when the entire query could run on a single machine without any IPC. In contrast, in Volcano's operator model, only exchange operators cause process switches. Operators that happen to be in the same process communicate by ordinary procedure calls, which are orders of magnitude cheaper than IPC.

4. The Operator Model and the Exchange Iterator

The exchange iterator is a full iterator: it implements open, next, and close. It can be inserted at any point in a query execution plan. Figure 2 in the paper shows a query plan with multiple XCHG (exchange) nodes interspersed among regular operators like JOIN and FS (file scan):

Example — A Parallel Query Tree

PRINT → XCHG → JOIN → (JOIN → (XCHG → FS, XCHG → FS), XCHG → FS). Each XCHG node is a process boundary. Operators above XCHG run in the consumer process; operators below XCHG run in one or more producer processes. The XCHG nodes handle all data transfer between processes via shared-memory ports and semaphores.

When an exchange operator is opened by the consumer process, it creates a shared-memory data structure called a port and forks a new child process using the UNIX fork system call. The child process is an exact duplicate of the parent. The parent (consumer) proceeds to act as a normal iterator consumer—it calls next on the exchange iterator, which retrieves records from the port. The child (producer) runs the subtree below the exchange operator, pushing output records into the port.

Records are transferred in packets: arrays of NEXT_RECORD structures. The packet size is a tunable parameter. Large packets amortize the overhead of inter-process coordination; small packets enable fine-grained pipelining. The paper demonstrates that for packet sizes above about 50 records, the overhead per record becomes negligible.

An optional flow control semaphore prevents the producer from racing too far ahead of the consumer. If flow control is enabled, after inserting a packet into the port, the producer must acquire a semaphore before inserting the next one. The initial value of this semaphore (say, 4) limits how many packets can be in flight at once. This prevents memory exhaustion in the buffer pool when producers are significantly faster than consumers.

5. Vertical Parallelism: Pipelining Between Processes

Vertical parallelism, also called pipelining, means that multiple operators in a pipeline run simultaneously in different processes. In a single-process system, the sequence SCAN → FILTER → JOIN executes strictly sequentially: the scan produces a tuple, then the filter processes it, then the join uses it. Only one stage is active at any instant.

With one exchange operator in the pipeline—say, between FILTER and JOIN—the scan and filter run in a producer process while the join runs in the consumer process. Both processes run simultaneously. While the consumer is processing the current batch of filtered tuples, the producer is already scanning and filtering the next batch. This overlap is vertical parallelism: the pipeline stages run in parallel, each working on a different portion of the data stream.

Note a subtlety: inside a single process, Volcano uses demand-driven (pull) dataflow—the consumer requests tuples from the producer via procedure calls. But the exchange operator switches the paradigm: between processes, Volcano uses data-driven (push) dataflow—the producer pushes packets into the port as fast as it can (subject to flow control), without waiting for requests. The exchange operator mediates the transition between these two paradigms on both sides.

Intuition — Pull inside, push between

Within a process, pull (demand-driven) dataflow is efficient because it avoids unnecessary work: a filter that rejects 99% of tuples does not cause the scan to race ahead producing data that goes unused. Between processes, push (data-driven) dataflow is more efficient because it avoids request messages: the producer doesn't need to wait for a "give me a tuple" message from the consumer before producing. The exchange operator handles the translation so that neither the operators above nor those below need to know about this duality.

6. Horizontal Parallelism: Bushy and Intra-Operator

Volcano's exchange operator also supports two forms of horizontal parallelism: bushy parallelism and intra-operator parallelism.

Bushy parallelism (also called inter-operator horizontal parallelism) means that independent subtrees of a query plan execute simultaneously on different CPUs. In a three-way join $A \bowtie B \bowtie C$, the computation of $A \bowtie B$ can proceed on some CPUs while $C$ is being scanned on others. Inserting an exchange operator between the two inputs to the top-level join achieves this: the first sort is the producer in one process, the second sort is the producer in another process, and they run in parallel.

Intra-operator parallelism means that a single operator runs simultaneously on multiple CPUs, each working on a different partition of the data. This is the form of parallelism exploited by parallel sort (multiple processes sort different partitions), parallel hash join (multiple processes hash different partitions into different hash tables), and parallel aggregation. Intra-operator parallelism requires data partitioning: the input data must be divided among multiple producer processes such that each process gets an independent, complete slice.

In Volcano, intra-operator parallelism is implemented by including multiple input queues in the port (one per producer process). The producer processes each build a partition, and the consumer selects which queue to read from using a support function. For hash partitioning, the support function hashes the current query key and returns the appropriate queue index. For round-robin partitioning, it rotates through queues in sequence. For key-range partitioning, it uses a lookup table of range boundaries.

Definition — Propagation Tree Forking

When a master producer process needs to create $k$ parallel producer processes (slaves), rather than forking all $k$ processes itself (which is expensive and produces a star topology), Volcano uses a propagation tree: the master forks one slave, then both fork another, then all four fork another, etc. This binary fanout takes $\log k$ rounds instead of $k$ rounds, significantly reducing startup latency for large degrees of parallelism.

7. A Worked Example: Three Process Groups

The paper provides a detailed worked example with operators $A, B, C, D$ where $A$ calls $B$'s procedures, $B$ calls $C$'s, and $C$ calls $D$'s. Two exchange operators—X between $A$ and $B$, and Y between $C$ and $D$—partition the query into three process groups: $A_0$ (running operator $A$ alone), the BC group (running operators $B$ and $C$ together, in two parallel processes $BC_0$ through $BC_2$), and the D group (running operator $D$ in four parallel processes $D_0$ through $D_3$).

The startup sequence illustrates the elegance of the operator model: $A$ calls X's open, which creates the port and forks BC processes. The BC group calls Y's open, which creates another port and forks the D group. All processes are now running simultaneously—the D processes scanning and producing, the BC processes joining and filtering, and $A$ consuming and printing. The shutdown sequence is equally clean: when $A$ finishes, it calls X's close, which signals the BC group to shut down, which signals the D group to shut down—the query tree closes orderly from top to bottom.

Throughout this entire startup, execution, and shutdown sequence, operators $A, B, C, D$ are unchanged from their single-process implementations. They call open, next, and close on their inputs without knowing whether those inputs are local procedure calls or port-mediated inter-process transfers. The exchange operator is the only module that knows about processes.

8. Performance Overhead

Graefe measures the overhead of the exchange operator on a Sequent Symmetry with twelve Intel 80386 CPUs at 16 MHz. Three experiments are reported:

  • Baseline (no exchange): Creating and releasing 100,000 records in the buffer takes 20.28 seconds.
  • Exchange in no-fork mode (exchange operator present but no new process created): 28.00 seconds. The overhead per record per exchange operator is $(28.00 - 20.28) / 3 / 100{,}000$ = 25.73 microseconds. Three exchange operators cross three procedure call boundaries.
  • Exchange in fork mode (four-process pipeline): 16.21 seconds with flow control, 16.16 seconds without. This is less than the single-process baseline—pipeline parallelism actually speeds things up.

The exchange overhead as a function of packet size is striking. For 1-record packets, elapsed time is 176.4 seconds (dominated by per-packet synchronization). For 250-record packets, it is 12.73 seconds—better than even the sequential baseline. The paper estimates the per-record-per-process-boundary overhead at approximately 992 microseconds when using small packets, dropping to effectively zero with large packets.

Packet Size vs. Elapsed Time (Table 1)
  • 1 record per packet: 176.4 seconds
  • 5 records per packet: 45.27 seconds
  • 20 records per packet: 20.15 seconds
  • 50 records per packet: 15.71 seconds
  • 100 records per packet: 13.76 seconds
  • 250 records per packet: 12.73 seconds

The lesson is clear: packet size should be set to at least 50 records (ideally 100–250) to keep exchange overhead negligible. This is easily achievable for analytical query workloads where large numbers of tuples flow between operators.

9. Why This Matters

The Volcano paper's influence on database systems architecture has been profound and lasting. Its iterator model—open, next, close—is the foundation of query execution in virtually every major relational database system: PostgreSQL, MySQL, SQL Server, Oracle, DB2, and their descendants all use some variant of it. The model's elegance is that it composes naturally: any operator can be connected to any other operator, enabling modular, extensible query engine design.

The exchange operator specifically influenced the design of parallel database systems. Systems like Tandem's parallel operator (independently designed around the same time), and later commercial parallel databases, adopted the same insight: parallelism should be a separately encapsulated concern that wraps existing serial algorithms rather than pervading every algorithm's implementation. This dramatically reduces the cost of developing and maintaining parallel database systems.

The distinction between demand-driven dataflow (within a process) and data-driven dataflow (between processes) is also an enduring insight. Modern streaming database systems and distributed query engines (Apache Spark's DataFrame execution, Presto/Trino's split-based execution, Apache Flink's dataflow model) all grapple with this same tension and use similar solutions: lazy pull evaluation within a pipeline stage, eager push across network or process boundaries.

The paper also introduced the vocabulary of vertical parallelism (pipelining), bushy parallelism, and intra-operator parallelism—a taxonomy that remains standard in database systems courses and textbooks. Understanding these three forms of parallelism and how they can be combined is essential for designing and reasoning about any modern high-performance query engine.

Intuition — The enduring lesson

Volcano teaches that separation of concerns is not just a software engineering platitude—it is a performance-critical design principle. By isolating all parallelism concerns in a single module (the exchange iterator), the system becomes simultaneously easier to extend (write new operators once, for free parallelism), easier to reason about (the parallel behavior is in one place), and more robust (parallelism bugs are in one module, not scattered across every operator). The exchange operator is a rare case where good software engineering and good systems engineering align perfectly.
