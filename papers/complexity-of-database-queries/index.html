Scientific Paper · PODS 1997

On the Complexity of Database Queries

Christos H. Papadimitriou (UC Berkeley) · Mihalis Yannakakis (Bell Laboratories) Proc. 16th ACM Symposium on Principles of Database Systems (PODS), 1997 · pp. 12–19
Abstract Classical database theory measures the cost of evaluating a query in two ways. Data complexity fixes the query and asks how cost grows with the size of the database; under it, the standard query languages—conjunctive queries, the full relational calculus, Datalog, and fixpoint logic—are all comfortably tractable. Combined complexity feeds both the query and the database as input, and treats them symmetrically; under it those same languages are NP- or PSPACE-complete. This paper argues that neither notion tells the real story, because data complexity quietly hides an algorithm whose running time is $n^{f(q)}$—the query size sits in the exponent. Using the parametric (fixed-parameter) complexity theory of Downey and Fellows, with the query size and the number of query variables as parameters, the authors place conjunctive queries, positive queries, and first-order queries at successively higher levels of the W hierarchy. The conclusion is sharp: the exponential dependence of evaluation cost on query size is essentially unavoidable, and it gets worse as the query language becomes more expressive. The paper closes with a positive result—acyclic conjunctive queries extended with inequalities ($x \neq y$), though not with order comparisons ($<$), remain fixed-parameter tractable.

1. Two Ways to Measure the Cost of a Query

Suppose you have a query $Q$ and a database $d$, and you want to compute the answer $Q(d)$. How long should that take? The answer depends on what you hold fixed and what you let grow. Database theory, following a distinction sharpened by Vardi in 1982, recognizes two standard yardsticks.

Data complexity regards the query as fixed and measures cost as a function of the size $n$ of the database alone. Combined complexity treats both the query and the database as input variables and measures cost as a function of their total size. (A rarely-used third notion, expression complexity, fixes the database and varies only the query.) Combined complexity is typically one exponential higher than data complexity, because a query with $q$ variables can, in the worst case, force the engine to consider all $n^q$ ways of binding those variables to database values.

Definition — the two complexities, precisely

Fix a query language $\Lambda$. The combined complexity of $\Lambda$ is the complexity of the decision problem $\{(Q,d,t) \mid Q \in \Lambda,\ t \in Q(d)\}$—given a query, a database, and a candidate tuple, decide whether the tuple is in the answer. The data complexity is the complexity of the family of problems $\{(d,t) \mid t \in Q(d)\}$, one problem per fixed query $Q$. We say $\Lambda$ has polynomial data complexity if there is a single function $f : \Lambda \to \mathbb{N}$ such that every query $Q \in \Lambda$ can be evaluated in time $n^{f(Q)}$.

For a wide range of important languages—conjunctive queries, first-order queries (equivalently, the full relational algebra and calculus), Datalog, fixpoint logic, and constraint languages with arithmetic or linear/polynomial inequalities—data complexity predicts that evaluation is perfectly tractable. The classes spanned range from $\mathrm{AC}^0$ up to $\mathrm{P}$, well within what complexity theory regards as efficient. This is the result most often quoted in textbooks, and it is the source of a comfortable belief: that the computational problems behind query evaluation are solved and under control.

2. Why Neither Notion Tells the Real Story

The authors argue that the comfortable belief is misleading, and that both classical notions are flawed—in opposite directions.

Combined complexity is too pessimistic. By treating the query and the database as part of the same input, it pretends they are the same kind of object and roughly the same size. In practice the query is tiny and the database is enormous: a join over a handful of tables, evaluated against billions of rows. Lumping them together is "rather restrictive," and it is precisely because queries are so much smaller than databases that the field concentrated on data complexity in the first place.

Data complexity is too optimistic. Saying a query language is in polynomial time "$n^{f(q)}$" hides a crucial fact: the exponent depends on the query. For the standard languages the known algorithms run in time roughly $n^q$ where $q$ is the number of query variables, and this dependence is provably unavoidable for the recursive languages (Vardi, 1982). Even though $q \ll n$, treating $q$ as a constant is not reasonable: even for small $q$, a running time like $n^q$ over a huge $n$ hardly qualifies as tractable.

Intuition — what "polynomial" hides

Consider a join of five tables, each with a million rows. A naïve "consider all variable bindings" evaluation runs in time about $(10^6)^5 = 10^{30}$. That is a polynomial in $n$—degree five—so data complexity files it under "tractable." But the degree of the polynomial is the query size, and $10^{30}$ operations is not tractable by any human standard. What we would really like is an algorithm whose running time is $f(q)\cdot n^c$—where the database exponent $c$ is a constant independent of the query, and all the query's badness is quarantined inside the factor $f(q)$. Whether such an algorithm exists is exactly the question parametric complexity was built to answer.

There is a precedent for this hope. In automated verification, the model-checking problem—does a finite-state program $P$ satisfy a temporal-logic specification $\phi$?—is PSPACE-complete in combined input, yet for LTL it can be solved in time exponential in the small specification $\phi$ and merely linear in the large program $P$. The badness is confined to the small object. The authors ask: can query evaluation enjoy the same kind of algorithm, with the query playing the role of the small specification? Parametric complexity is the framework that decides when the answer is yes.

3. A Crash Course in Parametric Complexity

Parametric (also called parameterized or fixed-parameter) complexity is the theory of Downey and Fellows that refines NP-completeness by isolating a parameter—a quantity expected to be small—and asking whether the hardness of a problem can be pushed entirely into a function of that parameter.

Definition — parametric problem and fixed-parameter tractability

A parametric problem is a set $L$ of pairs $(x,k)$, where $x$ is an input string and $k$ is an integer parameter. The problem is fixed-parameter tractable (f.p. tractable) if some algorithm decides whether $(x,k) \in L$ in time

$$f(k)\cdot |x|^c$$

for some constant $c$ and some (possibly explosive) function $f$. The point is that the exponent $c$ of the input size does not grow with the parameter. Contrast this with running time $|x|^{f(k)}$, where the parameter sits in the exponent—that is the bad regime we are trying to escape.

The canonical contrast is between two NP-complete problems. k-Clique—does a graph have a clique of size $k$?—is solved by checking all $\binom{n}{k}$ vertex subsets, time $\approx n^k$, and no algorithm is known that removes $k$ from the exponent. By contrast, k-Vertex-Cover—is there a set of $k$ vertices touching every edge?—can be solved in time $2^k\cdot n$ by bounded search-tree branching. Both have $k$ as a natural parameter; only the second is fixed-parameter tractable. Clique is the suspected-intractable archetype, and—crucially for this paper—query evaluation looks just like clique, with the query length playing the role of $k$.

Definition — parametric reduction

A parametric reduction from problem $A$ to problem $B$ maps an instance $(x,k)$ of $A$ to an instance $(y,\ell)$ of $B$ such that the new parameter is bounded by a function of the old one, $\ell \le g(k)$ (independent of $x$), and the map runs in time $h(k)\cdot|x|^s$. The condition that $\ell$ stays bounded by the parameter alone is what makes the reduction preserve fixed-parameter tractability—an ordinary polynomial reduction that blew the parameter up to $|x|$ would be useless here.

The W hierarchy

Just as NP-completeness needs a complete problem (satisfiability), parametric intractability is organized around a tower of classes called the W hierarchy, defined through weighted satisfiability. Take a Boolean circuit with AND, OR, and NOT gates and one output. Its depth (more precisely its weft, the number of large-fan-in gates on a path) measures how complicated it is. The problem weighted satisfiability asks: is there a setting of exactly $k$ of the inputs to 1 that makes the circuit output 1? Parameterizing by $k$ and bounding the circuit depth by $t$ gives the class $W[t]$.

The rungs of the ladder

The classes are indexed $W[1], W[2], \ldots$, topped by two limiting classes $W[\mathrm{SAT}]$ (weighted satisfiability for Boolean formulas of unbounded depth) and $W[P]$ (weighted satisfiability for Boolean circuits of unbounded depth). They satisfy

$$\mathrm{FPT} \subseteq W[1] \subseteq W[2] \subseteq \cdots \subseteq W[\mathrm{SAT}] \subseteq W[P].$$

Each class has natural complete problems: k-Clique and Independent Set are $W[1]$-complete; Dominating Set is $W[2]$-complete; Bandwidth is $W[t]$-hard for every $t$. The higher the $t$ for which a problem is shown $W[t]$-hard, the more strongly we believe it is not fixed-parameter tractable—that the parameter is doomed to live in the exponent.

Why this is the right tool

The whole apparatus exists to make one distinction precise: between "$f(k)\cdot n^c$" (the parameter is contained) and "$n^{f(k)}$" (the parameter has leaked into the exponent). Showing a query-evaluation problem is $W[1]$-hard or higher is therefore strong formal evidence that query size must appear in the exponent of any evaluation algorithm—exactly the worry that data complexity papered over.

4. Casting Query Evaluation as a Parametric Problem

A database $d$ is a domain $D$ together with relations $R_1, \ldots, R_m$ over $D$. A query $Q$ maps a database to a new relation $Q(d)$. The paper studies four query languages of increasing power:

  • Conjunctive queries — selection, projection, join, and existential quantification; equivalently, the calculus with conjunction and $\exists$. These are the workhorse SELECT–FROM–WHERE queries.
  • Positive queries — conjunctive queries plus union (disjunction).
  • First-order queries — positive queries plus set difference (negation); equivalently, full relational algebra/calculus.
  • Datalog / fixpoint logic — first-order plus recursion.

To turn evaluation into a parametric problem we must choose the parameter. Two candidates present themselves, and the paper analyzes both:

The two parameters

The query size $q$ — the length of the string needed to express the query. The number of variables $v$ — how many distinct variables appear in the query. The second parameter is motivated by Vardi's 1995 study of queries in which the number of variables may grow with the database while the query's overall size stays bounded; bounding $v$ instead of $q$ brings combined complexity closer to data complexity, with $v$ rather than $q$ in the exponent of $n$.

A third design choice is whether the schema—the set of relations and their arities—is fixed or allowed to vary. Combining {parameter is $q$ or $v$} with {schema fixed or variable} yields four parametric versions of each query problem, related by a diamond-shaped partial order.

Figure 1 — the diamond of four parametric problems 
                 v, variable schema
                 /              \
   v, fixed schema            q, variable schema
                 \              /
                 q, fixed schema

Proposition 1. If any one of the four problems is hard for a class in the W hierarchy, then every problem above it in this order is also hard; and if a problem is in some class, every problem below it is in the same class. (Proof: the identity map is a valid parametric reduction along each arc.) In most cases the schema assumption makes no difference—upper bounds hold for variable schema, lower bounds for fixed schema—so by default the authors take the schema to vary, noting the exceptions.

5. The Classification

The central result places the parametric query-evaluation problems precisely on the W ladder. All three of these languages have data complexity in $\mathrm{AC}^0$ (hence inside LOGSPACE and P), so the classical view sees no difference among them. The parametric view sees a clear, increasing hierarchy.

Theorem 1 — the parametric complexity of query evaluation
Query language Parameter = query size $q$ Parameter = #variables $v$
Conjunctive $W[1]$-complete $W[1]$-hard, in $W[2]$
Positive $W[1]$-complete $W[\mathrm{SAT}]$-hard
First-order $W[t]$-hard, all $t$ $W[P]$-hard

(Under a fixed schema with fixed arities, the conjunctive/parameter-$v$ entry tightens to $W[1]$-complete.)

Reading the table

Two trends jump out. Down each column, as the language gains expressive power (conjunctive → positive → first-order), the parametric hardness climbs the ladder—from $W[1]$ up to the very top, $W[P]$. So the richer the language, the more confidently we can say its query size is stuck in the exponent. Across each row, bounding the number of variables ($v$) is generally at least as hard as bounding the whole query size ($q$), and often strictly harder—consistent with Vardi's finding that the variable count is the more fundamental quantity. The upshot: every one of these languages is parametrically intractable, and the exponential dependence on the query gets worse, not better, as expressiveness grows.

A "likelihood," not yet a proof, for the non-recursive languages

For conjunctive, positive, and first-order queries these are hardness results: $W[1]$-hardness and above. They strongly suggest, but do not unconditionally prove, that query size must appear in the exponent—because proving these languages parametrically tractable would collapse long-standing separations such as $P \neq NP$ or $P \neq PSPACE$. For the recursive languages the story is unconditional: Vardi (1982) showed there are fixpoint queries (and the argument adapts to Datalog) of size polynomial in $k$ computable in $n^k$ but not in $n^{k-1}$. There the query size provably appears in the exponent, no conjecture required. (Restricting all EDB and IDB relations to fixed arity drops Datalog back to $W[1]$-complete.)

6. How the Bounds Are Proved

6.1 Conjunctive queries — a reduction from Clique

The lower bound is a clean, memorable reduction from $k$-Clique, which is $W[1]$-complete. Given a graph $G$ as a single binary relation $G(\cdot,\cdot)$, build the Boolean (0-ary head) conjunctive query

$$P \;\leftarrow\; \bigwedge_{1 \le i < j \le k} G(x_i, x_j).$$

The goal proposition $P$ is true exactly when $G$ contains a clique of size $k$: the variables $x_1, \ldots, x_k$ must map to $k$ vertices that are pairwise adjacent. The query has size $q = O(k^2)$ and uses $v = k$ variables, so the same construction is a parametric reduction to both the $q$- and $v$-parameterized problems. In words: evaluating a conjunctive query is at least as hard as asking whether a join of binary relations is non-empty, and that is already as hard as Clique.

For the matching upper bound with parameter $q$, any conjunctive query is rewritten as a 3-CNF weighted-satisfiability instance whose Boolean variables encode the mapping from query atoms to database tuples; with parameter $v$, the Boolean variables instead encode the mapping from query variables to database constants. Either way the result lands in $W[1]$.

6.2 Positive queries — union pushes the variable case to the top

A positive query is a union of conjunctive queries. For parameter $q$, one transforms it into a union of (exponentially many, but controlled) conjunctive queries and stays in $W[1]$—here the full power of parametric reductions (not merely transformations) is needed. For parameter $v$, disjunction lets the query encode a full Boolean formula on the variable-to-constant mapping, yielding a reduction from weighted formula satisfiability and hence $W[\mathrm{SAT}]$-hardness.

6.3 First-order queries — simulating a Boolean circuit

The strongest lower bound reduces from monotone weighted circuit satisfiability, which is $W[P]$-complete. The given circuit alternates OR and AND gates, with the output an OR gate at level $2t$. The database holds a single binary relation $C$ describing the circuit's wiring diagram—a directed acyclic graph whose nodes are gates—so the query's variables range over gates. First-order queries are then defined level by level up the circuit:

$$\theta_0(x) = \big[\,C(x,x_1)\vee C(x,x_2)\vee\cdots\vee C(x,x_k)\,\big],$$

$$\theta_{2i}(x) = \exists y\,\big[\,C(x,y) \wedge \forall x(\neg C(y,x) \vee \theta_{2i-2}(x))\,\big].$$

Expanding this recurrence fully and quantifying over the $k$ chosen inputs gives the final query

$$Q = \exists x_1 \exists x_2 \cdots \exists x_k\; \theta_{2t}(o),$$

where $o$ is the constant for the output gate. Intuitively $\theta_{2i}(x)$ says "gate $x$ at level $2i$ evaluates to true when inputs $x_1,\ldots,x_k$ are set to 1," so $Q$ holds iff the weighted circuit is satisfiable. The query has size $O(t+k)$ with $v = k+2$ variables, and only a fixed schema (one binary relation) is needed. Because $t$ can be any constant, this proves first-order evaluation is $W[t]$-hard for every $t$ (parameter $q$) and $W[P]$-hard (parameter $v$).

Why the recursive languages are unconditional

For non-recursive languages an unconditional theorem would resolve open conjectures—recall that conjunctive and positive queries have combined complexity NP-complete and first-order queries PSPACE-complete, so unconditional tractability would force $P = NP$ or $P = PSPACE$. But fixpoint logic and Datalog have combined complexity EXPTIME-complete, and the Time Hierarchy Theorem already gives $P \neq EXPTIME$ unconditionally. That is exactly why Vardi's result—query size provably in the exponent for recursive languages—needs no unproven assumption.

7. A Tractable Case: Acyclic Queries with Inequalities

After a wall of hardness, the paper finds an island of tractability. The classic positive result in this area is Yannakakis's theorem that acyclic conjunctive queries can be evaluated efficiently even in combined complexity. The contribution here is to extend that to acyclic queries enriched with inequalities of the form $x \neq y$.

Acyclic conjunctive queries

Given a conjunctive query $G(t_0) \leftarrow R_{i_1}(t_1), \ldots, R_{i_s}(t_s)$, form a hypergraph $H$ whose nodes are the query's variables and which has one hyperedge per atom (the set of variables in that atom). The query is acyclic if $H$ is an acyclic hypergraph—equivalently, it admits a join forest. Yannakakis's algorithm evaluates such a query by a bottom-up semijoin pass that strips dangling tuples, then a pass that materializes the answer, all in time polynomial in both the database and the output.

Why inequalities are dangerous

The naïve way to handle an inequality $x_i \neq x_j$ is to add an edge $(x_i,x_j)$ to the hypergraph. But those extra edges destroy acyclicity even in very simple queries, so the standard machinery no longer applies. Worse, if you allow inequality edges freely the problem becomes NP-complete: Hamiltonian Path reduces to it via the query

$$G \leftarrow E(x_1,x_2), E(x_2,x_3), \ldots, E(x_{n-1},x_n),\ x_1\neq x_2,\, x_1\neq x_3,\, \ldots,\, x_{n-1}\neq x_n,$$

whose answer is non-empty iff the graph has a Hamiltonian path. So inequalities must be handled without putting them in the hypergraph.

Theorem 2 — acyclic queries with inequalities are f.p. tractable

The class of acyclic conjunctive queries with inequalities is fixed-parameter tractable, with respect to both the query size and the number of variables as the parameter. Such a query can be evaluated in f.p. polynomial time in both the input and the output. Concretely, evaluation runs in time $O\!\big(g(k)\,n\,m\,\log^2 n\big)$, where $k$ is the number of variables, $n$ the database size, and $m = |Q(d)|$ the output size.

The trick — color-coding meets acyclic joins

The algorithm marries two ideas. First, Alon–Yuster–Zwick color-coding: hash the database domain $D$ down into a small set of $k$ colors. A random hash makes any fixed set of $k$ values land on distinct colors with probability at least $k!/k^k > e^{-k}$; trying $O(e^k)$ hash functions (or a deterministic perfect hash family) ensures the right separation appears. With distinct colors, an inequality $x_i \neq x_j$ can be checked by comparing colors rather than original values, so it no longer needs an edge in the hypergraph. Second, on the color-reduced instance the query is genuinely acyclic, so Yannakakis's join-forest passes (bottom-up to remove dangling tuples, top-down and bottom-up to build the answer) apply unchanged. The $\log^2 n$ overhead comes from sorting in the joins and from evaluating the perfect hash family.

A familiar special case

Finding a simple path of a specified length $k$ in a graph is exactly an acyclic query with inequalities (the path atoms are acyclic; the "simple" constraint is a set of $x_i \neq x_j$ inequalities). Theorem 2 therefore recovers, as a special case, the fixed-parameter tractability of the long-standing longest simple path problem—first shown f.p. tractable by Monien and famously sped up by Alon–Yuster–Zwick's color-coding. The paper's result is the general database-query statement of that phenomenon.

8. The Boundary: Why "≠" Is Fine but "<" Is Not

The natural next question is whether the positive result survives if we allow order comparisons ($<$ or $\le$) between variables and constants, not just inequalities. The answer is a sharp no—this is the precise boundary the abstract advertises.

Theorem 3 — comparisons reintroduce hardness

The class of acyclic conjunctive queries with comparisons ($<$ or $\le$) is $W[1]$-hard with respect to both parameters $q$ and $v$—and remains so even when restricted to binary relations, path-shaped queries, and only $<$ constraints.

The proof is again a reduction from Clique, but a more intricate one. Number the vertices of $G$ from $0$ to $n-1$ and encode each edge as a pair of integers built from the endpoint labels. A path-shaped query with two binary relations $P$ and $R$, whose comparison atoms $x_{ij} < x_{ji} < x'_{ij}$ chain the encoded edges in increasing order, is satisfiable exactly when $G$ has a clique of size $k$. So order comparisons let an acyclic query secretly enforce the all-pairs-adjacency structure that color-coding had neutralized for plain inequalities.

What separates "≠" from "<"

An inequality $x \neq y$ is a local, symmetric constraint: it only cares whether two values collide, which is exactly what hashing to colors can preserve. An order comparison $x < y$ is global and transitive: it imposes a consistent linear arrangement across all the variables, and that global structure is rich enough to embed Clique. Color-coding cannot help, because hashing scrambles order. (For dense orders one can pre-process by collapsing the strongly-connected components of the comparison graph—two values forced equal by a cycle of $\le$ constraints—but the resulting acyclic query is still $W[1]$-hard.) This dividing line—tractable inequalities, intractable comparisons—is the paper's most quotable practical takeaway.

9. Why It Mattered

This paper reframed a settled-looking question. For fifteen years the textbook line had been that the major query languages are tractable because their data complexity is polynomial. Papadimitriou and Yannakakis showed that this framing "puts the well-known tractability results under a different perspective, one that is perhaps more realistic, and less confusing and misleading." The query size is not an innocent constant hiding in the exponent; under the right lens it is the dominant source of difficulty, and parametric complexity is the lens that makes the difficulty visible and gradable.

The work is one of the earliest and most influential bridges between database theory and parameterized complexity. The identification of conjunctive-query evaluation with $W[1]$-completeness became a cornerstone result, later refined by Grohe, Schwentick, Segoufin, and others, who tied tractability to structural measures such as bounded treewidth of the query. The paper's message—that expressiveness and parametric hardness rise together—reshaped how theorists think about the price of query languages.

The takeaways in one breath

(1) "Polynomial data complexity" is reassuring but deceptive—the query size sits in the exponent. (2) Parametric complexity quantifies exactly how badly: conjunctive queries are $W[1]$-complete, and the hardness climbs to $W[P]$ as the language grows to full first-order logic; for recursive languages the exponent-dependence is unconditional. (3) There is a genuine tractable frontier: acyclic queries with inequalities stay fixed-parameter tractable via color-coding—but adding order comparisons pushes you straight back to $W[1]$-hardness.
