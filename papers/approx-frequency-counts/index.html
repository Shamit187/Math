Approximate Frequency Counts over Data Streams

Gurmeet Singh Manku, Rajeev Motwani Proceedings of the 28th VLDB Conference, Hong Kong, China, 2002
Abstract Data streams — stock tickers, network traffic logs, sensor feeds, web server logs — can be enormous and must be processed in a single pass with limited memory. A fundamental query over any stream is: which elements occur frequently? This paper presents two algorithms for answering this question approximately. Both accept two user-specified parameters: a support threshold $s$ and an error parameter $\epsilon$ (with $\epsilon \ll s$). Both guarantee: (1) all items whose true frequency exceeds $sN$ are reported — no false negatives; (2) no item whose true frequency is below $(s - \epsilon)N$ is reported; (3) all reported frequencies are underestimates by at most $\epsilon N$. The first algorithm, Sticky Sampling, is probabilistic. The second, Lossy Counting, is deterministic and uses at most $\frac{1}{\epsilon}\log(\epsilon N)$ space. The paper also extends Lossy Counting to the problem of finding frequent itemsets over a stream of transactions in a single pass.

1. The Streaming Frequency Problem

Consider a router on an internet backbone that sees millions of packets per second. Each packet belongs to a network flow identified by its source-destination pair. The router's operator wants to know: which flows account for more than 1% of total traffic? This is a heavy hitter or frequent item query.

The naïve approach — maintain an exact count for every flow seen so far — is impossible at internet scale. With millions of distinct flows, the count table would consume gigabytes of memory. Moreover, the router must process each packet in nanoseconds; there is no time to consult secondary storage. The stream cannot be stored and re-scanned.

Intuition — The Core Difficulty

Streams have two properties that make exact counting hard. First, the data volume over the lifetime of the stream may be enormous — far too large to store. Second, there is no second chance: each element must be processed as it arrives, and then it is gone. Any algorithm must make irrevocable decisions about what to remember and what to forget, all while the stream is still flowing.

The same problem structure appears in many domains: finding popular web pages in a web server log, identifying common market-basket items in a retail transaction stream, detecting dominant query types in a database workload, and finding frequent words in a document feed. The paper targets all of these with a single, generic framework.

Existing algorithms for exact frequent-item counting over finite stored datasets require at least two passes. In the streaming setting, only one pass is allowed and results must be available at any time. Prior streaming approaches either had no provable error guarantees or required very large samples to work. Manku and Motwani present the first single-pass algorithms with small, provably bounded memory and provable approximation guarantees.

2. Problem Definition and Error Guarantees

Let $N$ denote the current length of the stream — the number of items seen so far. The user specifies two parameters:

A support threshold $s \in (0,1)$: items whose true frequency exceeds $sN$ are the ones we want to find.

An error parameter $\epsilon \in (0,1)$ with $\epsilon \ll s$: the tolerable approximation error, expressed as a fraction of $N$.

Definition — epsilon-Deficient Synopsis

An algorithm maintains an epsilon-deficient synopsis if its output at any point in the stream satisfies three guarantees simultaneously:

(1) No false negatives: every item whose true frequency $f_e$ exceeds $sN$ is included in the output.

(2) Controlled false positives: no item whose true frequency is less than $(s - \epsilon)N$ appears in the output.

(3) Bounded underestimate: every estimated frequency $f$ reported for an item satisfies $f_e \in [f,\; f + \epsilon N]$ — the true frequency is at most $\epsilon N$ above the reported estimate.

Pause — Understanding the Guarantee

Suppose a user wants all items occurring in at least 0.1% of the stream (support $s = 0.001$), and sets error $\epsilon = 0.0001$ (one-tenth of $s$). Guarantee 1 says: every item appearing at least 0.1% of the time will be in the output — no item is missed. Guarantee 2 says: no item appearing less than 0.09% of the time will be in the output. Items appearing between 0.09% and 0.1% might or might not appear — this is the grey zone. Guarantee 3 says: the reported frequency of any item is at most $\epsilon N$ below its true frequency — reported counts are close to the truth, not wildly underestimated.

3. Sticky Sampling Algorithm

Sticky Sampling is a probabilistic algorithm. It maintains a set $\mathcal{S}$ of entries of the form $(e, f)$, where $e$ is an item and $f$ is its estimated frequency count. The algorithm uses a sampling rate $r$ that starts at 1 (every item is sampled) and increases over time.

How it works. Initially $\mathcal{S}$ is empty and $r = 1$. For each incoming item $e$: if $e$ already has an entry in $\mathcal{S}$, increment $f$ by 1. Otherwise, sample $e$ with probability $\tfrac{1}{r}$ — if selected, add entry $(e, 1)$ to $\mathcal{S}$.

As time progresses, the sampling rate $r$ doubles at intervals. Let $t$ denote $\tfrac{1}{\epsilon}\log(s^{-1}\delta^{-1})$. The first $2t$ elements are sampled at rate $r = 1$, the next $2t$ at rate $r = 2$, the next $4t$ at rate $r = 4$, and so on. When the rate changes, existing entries in $\mathcal{S}$ are thinned: for each entry $(e, f)$, repeatedly toss an unbiased coin and reduce $f$ by 1 for each tail, deleting the entry if $f$ reaches 0. This simulates what the count would have been had we been sampling at the new rate from the very beginning.

Intuition — Why "Sticky"?

The name comes from the algorithm's behavior: once an item enters $\mathcal{S}$, it is sticky — every future occurrence of that item is counted (with probability 1), regardless of the current sampling rate. Only the first encounter is subject to the sampling coin toss. This ensures that items that are truly frequent will almost certainly get into $\mathcal{S}$ early (when the sampling rate is high) and will then have their counts maintained accurately thereafter.

When a user requests a list of frequent items with threshold $s$, Sticky Sampling outputs all entries $(e, f)$ where $f \geq (s - \epsilon)N$.

The paper proves (Theorem 4.1) that Sticky Sampling produces an epsilon-deficient synopsis with probability at least $1 - \delta$ using at most $\tfrac{2}{\epsilon}\log(s^{-1}\delta^{-1})$ expected entries — a modest, logarithmic bound that does not grow with $N$.

4. Lossy Counting Algorithm

Lossy Counting is the paper's deterministic algorithm — it makes no probabilistic choices and is guaranteed to produce an epsilon-deficient synopsis every time, with no failure probability. It uses at most $\tfrac{1}{\epsilon}\log(\epsilon N)$ space.

The key idea: buckets. Conceptually divide the stream into buckets of width $w = \lceil \tfrac{1}{\epsilon} \rceil$ items each. Buckets are numbered starting at 1. The current bucket id is $b_{\text{current}} = \lceil \tfrac{N}{w} \rceil$.

The algorithm maintains a data structure $\mathcal{D}$ of entries of the form $(e, f, \Delta)$, where $e$ is an item, $f$ is an integer representing the estimated frequency, and $\Delta$ is the maximum possible error in $f$.

Definition — Lossy Counting Update Rules

When a new item $e$ arrives, Lossy Counting checks whether an entry for $e$ already exists in $\mathcal{D}$:

If yes: increment $f$ by 1. The entry now reflects one more observed occurrence.

If no: create a new entry $(e, 1, b_{\text{current}} - 1)$. The $\Delta$ value is set to $b_{\text{current}} - 1$, which is the maximum number of times $e$ could have appeared in previous buckets without being tracked.

At bucket boundaries (whenever $N \equiv 0 \pmod{w}$): delete any entry $(e, f, \Delta)$ where $f + \Delta \leq b_{\text{current}}$. These are items whose estimated count is so low that, even accounting for maximum error, they cannot be frequent.

The intuition behind $\Delta$: when a new item first appears in bucket $b_{\text{current}}$, it might have appeared many times in earlier buckets that have already been processed and deleted. The maximum it could have appeared without being in $\mathcal{D}$ is one occurrence per earlier bucket — at most $b_{\text{current}} - 1$ times. So $\Delta$ encodes this maximum accumulated error from the item's first appearance to now.

When a user queries for items with support threshold $s$, Lossy Counting outputs all entries $(e, f, \Delta)$ where $f \geq (s - \epsilon)N$.

Example — Lossy Counting Step by Step

Suppose $\epsilon = 0.01$, so bucket width $w = 100$. We are currently in bucket 3 (items 201–300). Item "HTTP" has been seen 50 times in the current window and was added to $\mathcal{D}$ when it first appeared in bucket 2, so its entry is $(\text{HTTP}, 50, 1)$. At the bucket 3 boundary, the deletion rule checks: $50 + 1 = 51$ which is greater than $b_{\text{current}} = 3$, so "HTTP" is kept. An item "FTP" that appeared only once and has entry $(\text{FTP}, 1, 2)$ satisfies $1 + 2 = 3$, which equals $b_{\text{current}}$, so FTP is deleted — it cannot be frequent.

5. Correctness of Lossy Counting

The paper proves four key lemmas that together establish correctness. Let's trace the argument at a high level.

Lemma 4.1 (Timing of deletions): Deletions only occur at bucket boundaries — so $b_{\text{current}} \leq \epsilon N$ always holds. This follows directly from the definition of bucket width $w = \lceil \tfrac{1}{\epsilon} \rceil$.

Lemma 4.2 (Deletion condition): Whenever an entry $(e, f, \Delta)$ gets deleted, its true frequency $f_e$ satisfies $f_e \leq b_{\text{current}}$. The proof uses induction: at deletion, $f + \Delta \leq b_{\text{current}}$, and $f$ is the exact count of $e$ since its last deletion. So the total true frequency from buckets 1 through current is at most $f + \Delta$.

Lemma 4.3 (No false negatives): If item $e$ does not appear in $\mathcal{D}$, then its true frequency $f_e$ satisfies $f_e \leq \epsilon N$. By Lemma 4.2, whenever $e$ is deleted, $f_e \leq b_{\text{current}}$. Combined with Lemma 4.1, this gives $f_e \leq \epsilon N$. So truly frequent items (with $f_e > sN$, and since $s > \epsilon$) are never deleted — they are always in $\mathcal{D}$.

Lemma 4.4 (Bounded error): For any entry $(e, f, \Delta)$ currently in $\mathcal{D}$, the true frequency satisfies $f \leq f_e \leq f + \epsilon N$. The lower bound holds because $f$ counts only observed occurrences. The upper bound: if $\Delta = 0$, then $f = f_e$ exactly. Otherwise, $e$ was deleted at some point, and from Lemma 4.2, at the last deletion $f_e \leq b_{\text{current}} \leq \epsilon N$. Since $\Delta$ is at most $b_{\text{current}} - 1$, and $b_{\text{current}} \leq \epsilon N$, we get $\Delta \leq \epsilon N$, so $f_e \leq f + \epsilon N$.

Theorem 4.2 — Space Bound for Lossy Counting

Lossy Counting computes an epsilon-deficient synopsis using at most $\tfrac{1}{\epsilon}\log(\epsilon N)$ entries. The proof uses an amortized argument: the sum $\sum_{i=1}^{B} d_i$ (where $d_i$ counts entries whose bucket id equals $B - i + 1$) satisfies $\sum_{i=1}^{j} d_i \leq \sum_{i=1}^{j} \tfrac{w}{i}$, giving the harmonic series bound $|\mathcal{D}| \leq \tfrac{1}{\epsilon}\log(\epsilon N)$.

6. Comparing the Two Algorithms

Sticky Sampling and Lossy Counting offer different tradeoffs. Sticky Sampling is probabilistic: it can fail (with probability at most $\delta$). Its expected space is $\tfrac{2}{\epsilon}\log(s^{-1}\delta^{-1})$ — importantly, this does not depend on $N$, making it good for very long streams. Lossy Counting is deterministic and always correct, but its space $\tfrac{1}{\epsilon}\log(\epsilon N)$ grows logarithmically with the stream length $N$.

Worst Case vs. Practice

The theoretical space bounds are worst cases. In practice, Lossy Counting performs dramatically better. On a Zipfian-distributed stream (where a few items are very common and most are rare — exactly the distribution of real web traffic, market baskets, etc.), the algorithm prunes low-frequency items aggressively at every bucket boundary. For $\epsilon = 0.01$, the worst-case bound suggests roughly 2000 entries, but in Zipfian streams the actual number is hundreds of times smaller. The paper's experiments confirm that Lossy Counting needs only a small fraction of the $\tfrac{1}{\epsilon}$ worst-case space.

The paper also proves an optimality result: the constant $\tfrac{1}{\epsilon}$ in Lossy Counting's space bound is essentially tight. No deterministic algorithm can do better by more than a constant factor.

7. Frequent Itemsets over Streams

Section 5 extends Lossy Counting to the much harder problem of finding frequent itemsets. Instead of a stream of individual items, now each element of the stream is a transaction — a set of items (think: a shopping basket with many products). An itemset $X \subseteq \mathcal{I}$ has support $s$ if it appears as a subset in at least a fraction $s$ of all transactions.

Enumerating all subsets of every transaction is infeasible. The key insight is to apply the Apriori principle: any subset of a frequent itemset must itself be frequent. This means we only need to maintain candidates that have survived a frequency threshold.

The extended algorithm processes transactions in batches (determined by available memory). For each batch, a specialized data structure called TRIE maintains the set $\mathcal{D}$ of entries $(\text{set}, f, \Delta)$ for candidate itemsets. A module called SetGen generates candidate itemsets for the current batch in lexicographic order. At batch boundaries, entries where $f + \Delta \leq b_{\text{current}}$ are deleted using the same Lossy Counting rule.

The design is carefully engineered to use disk-based TRIE storage (so memory size is not the bottleneck) and a SetGen module that exploits the Apriori pruning rule to avoid generating supersets of already-deleted itemsets. This enables single-pass computation of frequent itemsets over transaction streams with limited RAM.

8. Experimental Results

Experiments were run on a 933 MHz Pentium III processor running Linux 2.2.16. Two kinds of data were tested: IBM benchmark transaction streams (1 million transactions each, over 10,000 unique items) and text document sequences (word-pair frequencies in 100K web pages and 800K Reuters documents).

For the IBM benchmark, the paper compares Lossy Counting against Apriori (the classic batch frequent-itemset algorithm) with varying support thresholds $s$ from 0.1% to 1%, and buffer sizes from 4 MB to 44 MB. The key finding: Lossy Counting with a 44 MB buffer outperforms Apriori across all support levels — typically 3x to 8x faster, while using similar or less memory. The accuracy is remarkable: over 99% of itemsets reported in the output have 0% error (exact frequency counts).

Intuition — Why the Error Is So Small in Practice

The theory guarantees error at most $\epsilon N$, but in practice the error is nearly zero for a simple reason. A truly frequent itemset — one appearing in, say, 1% of a million transactions — will be encountered roughly 10,000 times. It will enter the data structure $\mathcal{D}$ very early (in the first batch) and will never be deleted thereafter, since its count rapidly exceeds the deletion threshold. Its estimated frequency will track the true frequency almost exactly. Only genuinely rare itemsets (which we don't care about) suffer significant relative error.

For text streams, the algorithm successfully identifies frequently co-occurring word pairs in very large document corpora — a task that is important for information retrieval, phrase detection, and language modeling — with low memory and in a single pass.

9. Impact and Legacy

The Manku-Motwani paper became a canonical reference for stream mining and approximation algorithms. Its impact was broad and lasting.

The epsilon-deficient synopsis framework gave the community a clean, precise specification for what it means to solve the frequent-item problem approximately. Subsequent papers on streaming algorithms routinely cite this framework and use the same three guarantees as a baseline.

Lossy Counting specifically became a building block for subsequent work. It was extended to handle sliding windows (where old data expires), to track quantiles and histograms, and to handle distributed streams where data arrives at multiple nodes simultaneously.

The space-accuracy tradeoff that Lossy Counting embodies — accept a small, bounded error in exchange for logarithmic memory — is now a standard paradigm in streaming algorithm design. It influenced the design of sketches (like Count-Min Sketch by Cormode and Muthukrishnan, 2005), which generalize the idea to arbitrary frequency queries.

Practical deployment. The Lossy Counting idea (or variants of it) appears in monitoring systems at major internet companies: Apache Flink, Spark Streaming, and other stream processing frameworks include approximate heavy-hitter detection modules that follow this paper's core principles.
