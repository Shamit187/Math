SemBench: A Benchmark for Semantic Query Processing Engines

Jiale Lao, Andreas Zimmerer, Olga Ovcharenko, Tianji Cong, Matthew Russo, Gerardo Vitagliano, Michael Cochez, Fatma Özcan, Gautam Gupta, Thibaud Hottelier, H. V. Jagadish, Kris Kissel, Sebastian Schelter, Andreas Kipf, Immanuel Trummer Proceedings of the VLDB Endowment, Vol. 14, No. 1 · arXiv:2511.01716v2 (Mar 2026)
Abstract Semantic query processing engines (SQPEs) are a new class of database systems that extend SQL with semantic operators — natural-language-configured predicates and transformations evaluated by large language models (LLMs). They enable queries over multimodal data (text, images, audio) that traditional SQL cannot express. SemBench is the first benchmark designed specifically for SQPEs. It covers five real-world scenarios (movie reviews, wildlife detection, e-commerce, car damage, and multimodal QA), 55 queries, three data modalities, and five semantic operator types. The authors evaluate four systems — LOTUS, Palimpzest, ThalamusDB, and Google BigQuery — finding that every system has significant trade-offs in cost, quality, and latency, and that no single system handles all queries well today.

1. What Is a Semantic Query Processing Engine?

Relational databases store numbers, strings, and dates — types that SQL was designed to reason about. But modern tables increasingly contain blobs: a column of product images, a column of audio recordings, a column of unstructured complaint text. You can store these, but traditional SQL cannot reason about their content. You cannot write a WHERE clause that asks "does this image show a red car?" because SQL has no concept of visual understanding.

Definition — Semantic Query Processing Engine (SQPE)

An SQPE extends relational SQL with semantic operators: operators that accept a natural language instruction and are evaluated by a large language model. The LLM reads, looks at, or listens to the data and returns a judgment — in zero-shot mode, with no task-specific training data required. The result is a database system that can answer content-aware questions about multimodal data using ordinary SQL syntax.

The paper's motivating example: a table Cars with a column pic containing one car photograph per row. The following query counts pictures of red cars:

Example 1.1 — AI.IF as a semantic filter 
SELECT COUNT(*)
FROM Cars
WHERE AI.IF(pic, 'the picture shows a red car');

AI.IF is a semantic operator. It receives each row's image and the natural language description; the LLM returns TRUE or FALSE. Standard SQL aggregation does the rest. The same syntax — with slight rewriting — is supported by LOTUS, Palimpzest, ThalamusDB, and BigQuery.

Why SQPEs change query optimization

Semantic operators change the cost structure of query execution in two fundamental ways:

  • Per-byte cost explodes. A single LLM API call costs orders of magnitude more than reading a row from disk or RAM. Traditional cost models optimize for I/O and CPU. In an SQPE, the dominant cost is LLM invocations — a completely different unit. The paper's central optimization goal becomes: minimize the number and size of LLM calls while maximizing result accuracy.
  • Results are stochastic. LLMs are not deterministic oracles. They can miss valid rows (false negatives) or include wrong ones (false positives). Accuracy is not guaranteed. Unlike traditional approximate query processing (AQP), there is no clean statistical model for LLM error — it depends on the prompt, the model, and the data domain.
The right mental model

Think of an SQPE as SQL with a "ask the AI" button on each row. Traditional SQL filters rows by comparing numbers or strings — instant, deterministic, cheap. Semantic operators filter rows by having an AI read, look at, or listen to the data and answer a question about it. The price: each "ask" takes a second and costs a fraction of a cent. Multiply by millions of rows and the costs dominate. The job of an SQPE optimizer is to minimize how many times it has to "ask".

2. Background

2.1 The Crowdsourced Precursor

The idea of SQL with natural-language operators is not new. In the early 2010s, systems like CrowdDB, Deco, and Qurk used human crowdworkers (via Amazon Mechanical Turk) to evaluate semantic predicates. A query could ask a crowdworker "does this image contain a cat?" and route the answer back into the query plan. These systems faced the same optimization challenge: minimizing human calls while maximizing accuracy. A large body of research — on specialized operator implementations, query rewrites, and parallelism — grew from this work. But crowdworkers are expensive, slow, and have limited scalability.

2.2 Large Language Models Change the Game

LLMs — built on the Transformer architecture and trained on enormous corpora via transfer learning — can address new tasks from a natural language description alone (zero-shot learning). They can also be guided by a few examples (few-shot learning). Crucially, modern LLMs handle multimodal inputs: text, images, and audio in the same model. This makes LLMs natural replacements for crowdworkers in semantic query systems.

Why the jump from crowdworkers to LLMs matters

Crowdworkers required task-specific instructions and manual quality control. They took minutes to hours to return results. Their availability was limited. LLMs respond in milliseconds, work around the clock, handle 20 parallel calls easily, and need only a one-line instruction. The volume of data you can process semantically goes from thousands of rows to millions — which is why SQPEs are now appearing in production systems like Google BigQuery and Snowflake.

2.3 Semantic Query Processing Engines Today

In the past two years, several SQPEs have emerged, including academic prototypes (LOTUS, Palimpzest, ThalamusDB) and production systems (Google BigQuery AI Functions, Snowflake Cortex). Each extends a relational algebra with semantic operators and uses LLMs to evaluate them. All support the extended data model where table cells may contain image or audio file paths. The optimization strategies — and their trade-offs — differ significantly across systems, which is exactly what SemBench is designed to measure.

2.4 Why Existing Benchmarks Don't Work

TPC-H and TPC-DS have driven innovation in relational databases for decades. But they contain only standard SQL operators. The optimization techniques they reward — better indexes, smarter join algorithms, compressed storage — do not help with semantic operators. For SQPEs, the dominant costs come from LLM calls, not disk I/O. A benchmark that doesn't include semantic operators cannot measure what matters: how many LLM calls are made, how much they cost, and how accurate the results are.

3. Benchmark Design Principles

3.1 Data Model

SemBench uses a standard relational model with one extension: columns may contain image or audio file paths in addition to SQL data types (integers, text, floats). All four evaluated SQPEs support this format. The underlying data comes from manually annotated Kaggle datasets — the ground truth labels are the original human-assigned labels from the source datasets, not generated by the systems being tested. This prevents contamination of ground truth by LLM outputs.

3.2 Query Design

Each scenario has at least 10 queries. Every query uses at least one semantic operator, possibly mixed with standard SQL. Queries are designed so that LLM call costs dominate total processing time — this keeps the benchmark focused on SQPE-specific optimization challenges rather than relational I/O. Three query types appear across scenarios:

  • Simple queries — one semantic operator in isolation, for individual operator benchmarking.
  • Complex queries — multiple semantic operators, possibly across different data modalities, to test cross-operator optimization.
  • LIMIT queries — queries requesting only the top-k results, which should allow early termination once enough rows are produced.

3.3 Metrics

SemBench evaluates systems across three dimensions. All quality metrics are normalized to $[0, 1]$ where higher means better.

Result Quality

How correct is the system's output compared to ground truth?

  • Aggregation queries (COUNT, SUM): relative error $1/(1+\text{relative error})$, where relative error $= |v_{\text{truth}} - v_{\text{result}}| / |v_{\text{truth}}|$.
  • Retrieval queries: F1 score — harmonic mean of recall (fraction of ground-truth rows returned) and precision (fraction of returned rows that are correct).
  • Ranking queries: Spearman's rank correlation coefficient ($1$ = perfect ranking, $0$ = random).
  • Join / classification queries: Adjusted Rand Index (ARI) — measures how well the system's groupings match the ground-truth groupings. Values above $0$ are better than random.
Processing Cost

Three cost dimensions are tracked per query:

  • Monetary cost: dollars paid for LLM API calls.
  • Execution time: wall-clock seconds. Queries exceeding 1 hour are marked as timed out; the system is not evaluated at larger scales.
  • Memory usage: peak gigabytes of RAM during query execution.

4. The Five Semantic Operators

SemBench covers five semantic operator types. Each is defined as a function from tuple types to output types, evaluated by a language model $M$ applying a natural language instruction $l$.

Table 1 — Semantic Operators in SemBench
Operator Informal definition SQL analogy Example
sem_filter(l: X→Bool) Keep rows where the LLM says l is true. WHERE clause Select patients with sick lungs from X-ray images.
sem_join(l: (X,Y)→Bool) Return pairs from two tables where the LLM says l holds for that pair. JOIN … ON Match two images of the same animal.
sem_map(l: X→Y) Transform each row — the LLM produces a new value per row. SELECT expression Extract brand names from product descriptions.
sem_rank(l: T[X]→Seq[X], k) Order all rows by the LLM's scoring on l; return the top k. ORDER BY … LIMIT k Rank reviews by positivity.
sem_classify(l: X→Y) Assign each row to one of a predefined set of categories. CASE WHEN … END Classify animals by species from images.
The join cost problem

Semantic filters, maps, and classifiers process one row at a time — cost scales as $O(N)$ in the table size. But a naive semantic join must consider every pair of rows from two tables — cost scales as $O(M \times N)$. For tables of a few thousand rows, this means millions of LLM calls. A single semantic join query in the MMQA scenario required 40,000 LLM calls and took over 35 minutes. Semantic join optimization is the central challenge for SQPEs.

5. Benchmark Scenarios

Five scenarios, each grounded in a real-world data domain. Together they cover the full space of data modalities and operator types, ensuring no SQPE can be evaluated on only the subset of queries it supports best.

5.1 Movies — Text Only

Purpose: widest system support; tests all five operator types on plain text.
Data: Rotten Tomatoes movie reviews from Kaggle (1.38 million reviews).
Tables: Movies(id, title, text) and Reviews(id, reviewId, reviewText).
Scale: base 2,000 rows; scalability experiments up to 1,375,738 rows.

All four evaluated systems support all 10 queries in this scenario. It serves as the "level playing field" test — any differences are due to system design choices, not missing modality support.

Example 4.1 — Counting positive reviews 
SELECT COUNT(*) AS positive_review_cnt
FROM Reviews R
WHERE R.id = 'taken_3'
AND AI.IF(R.reviewText, 'this review expresses a positive sentiment');

Standard SQL COUNT and WHERE combined with a semantic filter on the review text. The LLM decides per review whether it expresses positive sentiment.

5.2 Wildlife — Image + Audio

Purpose: tests semantic filters on non-text modalities (image and audio).
Data: camera trap photos (species labels) + animal sound recordings (species labels), both from Kaggle.
Tables: ImageTable(image, city, stationID) and AudioTable(audio, city, stationID).
Scale: base 200 rows; image rows 8,718; audio rows 650.

LOTUS does not support audio data in version 1.1.3, so it can only answer 4 of the 10 queries. This scenario exposes a modality coverage gap in current SQPEs.

Example 4.2 — Finding cities where elephants are detected 
SELECT DISTINCT city
FROM (SELECT city FROM ImageTable I
      WHERE AI.IF(I.image, 'the picture shows an elephant'))
UNION
(SELECT city FROM AudioTable A
 WHERE AI.IF(A.audio, 'this sounds like an elephant'));

A UNION query that sources evidence from two modalities. A city qualifies if an elephant is detected in either a photo OR an audio recording taken at a station in that city. This tests whether the system can evaluate semantic filters across heterogeneous column types in a single query.

5.3 E-Commerce — Text + Image

Purpose: the most operator-diverse scenario; tests all five operator types including joins.
Data: fashion retail dataset from Kaggle (44,446 items: clothes, shoes, accessories).
Table: styles_details(id, productDescription text, productImage img, …).
Scale: base 500 rows; scalability up to 44,446.

14 queries are split into two groups:

  • Queries 1–9: each tests one semantic operator in isolation (filter, map, classify, or join) on text, image, or both.
  • Queries 10–14: complex pipelines combining multiple operators, e.g., a semantic filter followed by a semantic join across text and image modalities.
Example 4.3 — Finding Reebok backpack product IDs 
SELECT id
FROM styles_details
WHERE AI.IF('This is a backpack from Reebok', productDescription);

A single semantic filter on product descriptions. Simple, cheap, high quality. This is what queries 1–9 look like. Queries 10–14 combine this kind of filter with a semantic join, which is where costs diverge dramatically across systems.

5.4 Cars — All Four Modalities

Purpose: the most modality-rich scenario; tests semantic operators across tables, text, image, and audio simultaneously.
Data: four interconnected Kaggle datasets synthesized into a car damage detection database.
Tables:

  • Cars(CarId, Mileage, FuelType, TransmissionType, VIN, RegistrationDate, Country, NumberPlate, PreviousOwners)
  • ComplaintsText(CarId, ComplaintId, Complaint text)
  • CarImage(CarId, ImageId, Image img)
  • DiagnostAudio(CarId, AudioId, Audio audio)

Scale: base 19,672 rows; scalability up to 157,376.

A given car may show damage in zero, one, or multiple modalities. Damage visible in a photograph may or may not match what a diagnostic recording reveals. This scenario tests whether a system can reason about the same real-world concept (car damage) across incompatible evidence sources.

Example 4.4 — Finding all damaged cars across all evidence types 
(SELECT CarId FROM ComplaintsText
 WHERE AI.IF('The car is damaged according to the symptoms.', Complaint))
UNION DISTINCT
(SELECT CarId FROM DiagnostAudio
 WHERE AI.IF('The car is damaged according to the audio.', Audio))
UNION DISTINCT
(SELECT CarId FROM CarImage
 WHERE AI.IF('The car is damaged according to the image.', Image));

Three parallel semantic filters, one per modality, unioned together. Only LOTUS lacks audio support; the rest handle all three branches.

Why audio support matters

In the Cars scenario, three out of ten queries involve audio data (diagnostic recordings). LOTUS cannot evaluate any of these. For a manufacturer trying to identify cars with brake problems from engine-sound recordings, LOTUS simply cannot help. Audio is currently the least-supported modality across SQPEs — a major coverage gap the benchmark makes visible.

5.5 MMQA — Multimodal Question Answering

Purpose: the most complex scenario; tests multi-hop reasoning combining structured tables, text, and images.
Data: MultiModalQA dataset (Wikipedia tables + texts + images).
Tables: 5 tables (athlete records, actor records, airport data, images).
Scale: base 200 rows; scalability up to 1,000.

11 questions require varied combinations of semantic filters, joins, maps, extraction, and summarization. Only Palimpzest technically supports all required operators. LOTUS encounters internal processing errors on one query (unexpected LLM output schema). ThalamusDB handles only a small subset (no SEM_MAP, no cross-modal SEM_JOIN). BigQuery can perform one-to-one SEM_MAP but not many-to-one summarization.

Example 4.5 — Joining airlines with images of their logos 
SELECT t.Airlines, i.uri
FROM mmqa.tampa_international_airport t, mmqa.images i
WHERE AI.IF(
  'You will be provided with an airline name and an image.
   Determine if the image shows the logo of the airline.
   Airline: ', t.Airlines, ', Image: ', i.uri);

A semantic join across two tables: one with airline names (text), one with images. For each candidate pair the LLM decides whether the image shows that airline's logo. At scale 400, this query required 160,000 LLM calls, cost ~$50–60, and took over 35 minutes for LOTUS and Palimpzest. BigQuery completed it in ~92 seconds using dynamic parallelism.

6. Experimental Setup

6.1 Hardware

Main experiments run on an AWS EC2 g4dn.2xlarge instance: 32 GB RAM, 4 vCPUs, NVIDIA T4 GPU (used only for embeddings in LOTUS), 250 GB disk. Scalability experiments run on a separate Ubuntu server with 2× Intel Xeon Gold 5218 CPUs and 384 GB RAM — necessary because some systems require over 200 GB of memory when processing large-scale image join queries.

6.2 LLM Choice: Why gemini-2.5-flash for All Systems

All four systems use gemini-2.5-flash as their backing LLM. This is a deliberate design choice: using the same model eliminates it as a confounding variable. Any difference in cost, quality, or latency between systems can be attributed to the system's query processing strategy, not the underlying AI model.

Why this matters for interpretation

If LOTUS uses GPT-4o and ThalamusDB uses Gemini Flash, a quality difference could be entirely explained by the model, not the system. By fixing the model, the benchmark isolates what actually differs: prompt design, batching strategy, pre-filtering, parallelism, and early termination. These are the engineering decisions that SQPE developers control.

Additional settings: temperature = 0 for all systems (except BigQuery, which manages this internally); reasoning capability disabled (too slow and costly); LLM parallelism fixed at 20 simultaneous calls for all academic systems. Each experiment repeated 5 times; mean and standard deviation reported.

6.3 The Four Systems

LOTUS 1.1.3

Academic system. Strategy: embedding-based pre-filtering for joins. LOTUS embeds all rows using e5-base-v2 (text) or clip-ViT-B-32 (images). For a semantic join, it only sends candidate pairs to the LLM if their embedding vectors are within a distance threshold. This dramatically reduces LLM calls. Tradeoff: embedding-based pre-filtering can miss valid matches whose embeddings happen to be far apart, lowering recall. LOTUS uses relatively concise prompt templates (low token count → lower cost per call) but does not support audio data.

Palimpzest 0.8.2

Academic system. Strategy: MaxQuality objective — optimize for output accuracy above all else. Uses the Abacus optimizer with quality as the primary objective. Very detailed prompt templates with few-shot examples; these raise input token counts and therefore cost more per call, but the LLM has more context and tends to produce better outputs. Palimpzest is consistently among the highest-quality systems but also among the most expensive.

ThalamusDB 0.1.15

Academic system. Strategy: batch processing for joins. Instead of sending one row pair per LLM call, ThalamusDB packs multiple pairs into a single prompt and asks the LLM to decide which pairs satisfy the join condition. Batch size 10 (for the join operator) reduces LLM call count by ~10×. Result: lowest average cost ($0.17 avg across scenarios). Tradeoff: with many pairs in one prompt, the LLM sometimes confuses candidates or misses valid matches — join quality (0.487) is notably lower than Palimpzest (0.703). ThalamusDB also supports a limited subset of operators.

Google BigQuery (AI Functions)

Industrial system. Strategy: dynamic runtime parallelism. BigQuery adjusts the number of parallel LLM invocations based on actual input sizes — the only system to do this. This allows BigQuery to scale where others run out of memory or time out (e.g., E-Commerce and MMQA at large scales). Model parameters are managed internally (not configurable by users), so temperature and prompt templates are set by Google. BigQuery achieves the lowest average latency (31.7 s) and the best image classification quality on some scenarios, but its filter quality on text is below LOTUS.

7. Results — Key Findings per Scenario

Table 4 in the paper contains per-query cost, quality, and latency for all four systems across all five scenarios. The following summarizes the most significant findings.

7.1 Movies — The Clean Baseline

All four systems support all 10 queries. Average results: ThalamusDB achieves cost of $0.02 (by far the cheapest) at quality 0.82; BigQuery achieves quality 0.75 at cost $0.55; LOTUS quality 0.68 at cost $0.62; Palimpzest quality 0.73 at cost $0.82.

The join cost asymmetry

Queries Q1–Q2 are semantic filters with a LIMIT clause: they cost $0.01 or less for most systems. Query Q7 is a semantic join with no LIMIT clause (must compare all review pairs). LOTUS: $1.81, 432 s. Palimpzest: $7.72, 1056 s. The difference between Q1 and Q7 is more than 100×. This single comparison illustrates why semantic joins are the dominant optimization target — they are where SQPE costs go from "negligible" to "prohibitive."

7.2 E-Commerce — Operator Diversity Reveals Coverage Gaps

14 queries covering all five operator types. Only LOTUS and BigQuery support the full set. Palimpzest is missing SEM_RANK + SEM_MAP combined; ThalamusDB supports only 5 of 14. Complex queries Q10–Q14 (multi-operator pipelines crossing text and image) time out or error for ThalamusDB and BigQuery.

Q7 (image-to-image semantic join) is the most expensive query: LOTUS $1.33 / 199 s, Palimpzest $1.79 / 287 s, BigQuery $0.86 / 45 s. At even base scale (500 rows), joining images takes hundreds of seconds and costs over a dollar — before any scaling.

7.3 Wildlife — Image Quality and the Audio Gap

LOTUS is absent from 6 of 10 queries (no audio support). Among systems supporting all queries, BigQuery achieves the highest average quality with a gap of more than 3 standard deviations — the largest quality gap across all scenarios. The authors attribute this to BigQuery's internal prompts being well-tuned for image classification tasks, which dominate the Wildlife scenario.

ThalamusDB achieves the lowest cost (near $0.07 avg) with near-zero variance, because Wildlife uses only semantic filters (no joins). For filters, ThalamusDB also implements early-exit logic: once it finds sufficient evidence to satisfy a query (e.g., at least one city with elephants), it stops evaluating further rows — saving LLM calls that other systems waste.

7.4 Cars — Audio Weakness and Image-Join Expense

This is the scenario where current systems perform worst. Queries involving audio (Q2, Q5, Q9) are either unsupported by LOTUS or produce poor quality across all systems. Queries involving classification (Q10) are unsupported by ThalamusDB and LOTUS.

Image-text joins (Q6–Q8) are dramatically expensive. Q8 in the Cars scenario (semantic join between complaint text and car images) took LOTUS 1350 seconds — 22 minutes — at base scale. This single query required scanning thousands of image-complaint pairs through the LLM.

Specificity improves LLM accuracy

An interesting finding from the Cars scenario: queries about specific damage types (e.g., "engine problems") yield higher LLM quality than queries about generic conditions (e.g., "crash or accident"). LLMs perform better when the problem space is narrow and well-defined. This suggests that SQPEs could improve accuracy by automatically refining broad instructions into more specific sub-queries — a form of prompt engineering that no current system implements.

7.5 MMQA — The Frontier of Current Capability

Only Palimpzest supports all 11 queries. LOTUS encounters schema-mismatch errors on Q4 (the LLM returns output in an unexpected format that the downstream code cannot parse). ThalamusDB handles 3 queries; BigQuery handles 6.

Q7 (semantic join between airline text data and logo images) is the single most expensive query in the entire benchmark: LOTUS $13.61 / 2311 s (38.5 min), Palimpzest $15.65 / 2101 s (35 min), BigQuery $1.18 / 91.7 s. BigQuery's 25× speed advantage for this query comes entirely from dynamic parallelism — it can invoke far more LLM calls in parallel than the 20-call limit on the other systems.

BigQuery quality reversal on MMQA

In most scenarios BigQuery achieves quality at or above the academic systems. In MMQA it averages only 0.32 quality — well below LOTUS (0.88) and Palimpzest (0.88). The reason: BigQuery's internal prompt templates are optimized for common analytical tasks. The complex, multi-hop Wikipedia table-joining queries in MMQA require rich contextual reasoning that BigQuery's default prompts do not support. This is a reminder that LLM quality is domain-dependent and prompt-dependent — raw model capability is not enough.

8. Scalability Experiments

Each scenario has a base scale and several larger scales (Table 3 in the paper). A 1-hour per-query timeout is enforced; systems that time out are not evaluated at larger scales.

Movies and Wildlife: linear and manageable

Both scenarios use mostly semantic filters (no joins). Filter costs grow roughly linearly with data size. All systems scale to the largest Movie scale (1.38M rows) within one hour — except LOTUS, which times out at scale 16K on Q6 (a semantic join with a LIMIT clause). LOTUS evaluates all data before applying the LIMIT as post-processing; other systems terminate early once the required number of rows is found. This single design decision causes LOTUS to exceed the timeout while the others complete comfortably.

E-Commerce and MMQA: quadratic join growth causes failure

For scenarios with semantic joins over images, only BigQuery scales to large sizes. At scale 400 in MMQA, Q7 costs ~$50 for LOTUS and ~$60 for Palimpzest. At scale 4,000 in E-Commerce, Q8 costs ~$140 for BigQuery alone. Memory is the primary failure mode for the academic systems: they buffer all candidate image pairs in RAM before sending them to the LLM, never releasing them. Q8 in E-Commerce requires 250 GB of RAM for ThalamusDB, 150 GB for LOTUS, and 100 GB for Palimpzest at moderate scale — causing server crashes before reaching the timeout.

Cars is the exception: all four systems scale to the full 157,376-row dataset. Because Cars uses semantic filters and classifiers (not joins) as its primary operators, cost grows linearly. BigQuery achieves better execution time due to dynamic parallelism; result quality remains stable across all scales for all systems.

Reading the table, four patterns stand out:

  • LOTUS achieves the best filter quality (0.896) by using detailed prompt templates that give the LLM more context — at the cost of higher token counts and therefore higher per-call expense. BigQuery's simpler internal prompts give it much lower filter quality (0.574) for text-heavy tasks.

Join vs. filter cost ratio

Across all systems, semantic joins cost 3–10× more than semantic filters per query. For LOTUS and Palimpzest the ratio is about 8×. For BigQuery it is about 3× because dynamic parallelism amortizes the per-pair overhead. This gap explains why semantic join optimization — pre-filtering with embeddings, batching, or dynamic parallelism — is the highest-value area for future SQPE research.

10. Lessons Learned

Lesson 1 — LIMIT clauses need real early termination

LOTUS evaluates all data and applies LIMIT as post-processing. The correct approach: terminate semantic operator evaluation as soon as enough rows have been collected. ThalamusDB does this; LOTUS does not. At 16K rows in the Movie scenario, LOTUS times out on Q6 (join with LIMIT) while ThalamusDB completes it in under a minute. The fix is architecturally straightforward but requires integrating the LIMIT constraint into the query execution engine, not just the output layer.

Lesson 2 — Systems should reason about when to stop

For filter queries that ask "does at least one row satisfy this condition in each group?", the system can stop evaluating rows in a group once it has found sufficient evidence. ThalamusDB implements this; other systems continue evaluating every row. This design decision costs nothing in quality and saves substantial LLM calls.

Lesson 3 — LLM parallelism must be runtime-adjustable

BigQuery adjusts the number of parallel LLM invocations dynamically based on query input size. This is the primary reason BigQuery is the only system that scales E-Commerce and MMQA queries to large datasets — others are bottlenecked at 20 parallel calls regardless of how much work they have. Exposing parallelism as a runtime parameter, rather than a fixed configuration, is a key engineering requirement for production SQPEs.

Lesson 4 — LLM failures need explicit handling

LLM API calls fail for many reasons: network outages, rate limiting, unstable APIs. No current academic system handles these failures robustly. BigQuery can stall for over 48 hours at large scale due to network issues or rate limiting. Systems should implement retries with exponential backoff. Without this, long-running benchmark queries become unreliable.

Lesson 5 — Memory management for multimodal joins is critical

Academic systems buffer all candidate image pairs in RAM before sending them to the LLM, never releasing memory as the query proceeds. At moderate scale, this causes memory usage exceeding 100–250 GB for a single query, leading to server crashes. The fix — streaming pairs and releasing memory as results arrive — is known in streaming databases but not yet implemented in any evaluated SQPE.

Optimization Opportunities Not Yet Implemented

The paper identifies three promising directions that no current system pursues:

  • Operator fusion: if a query has both a semantic filter and a semantic join on the same data, combining them into a single LLM call ("does this item satisfy condition A and match item B?") could reduce call count by 2–3×.
  • Result caching: many SemBench queries apply similar predicates to overlapping row sets. Caching LLM results for already-evaluated (row, instruction) pairs would avoid redundant calls across queries in the same session.
  • Automated prompt optimization: currently, prompt design is manual. Different systems make different trade-offs (detailed vs. concise prompts), with quality varying up to 4× for the same underlying model. An SQPE that automatically explores the prompt design space and converges on a cost-quality optimum would outperform all current approaches.

11. Conclusions and Outlook

SemBench fills a gap that has existed since the emergence of LLM-powered database systems: before this paper, no benchmark existed to measure SQPE performance on multimodal queries with semantic operators. The benchmark provides ground truth from real annotated datasets (not generated by the systems being tested), a multi-dimensional evaluation framework (quality, cost, latency, scalability), and public access via sembench.org.

Key empirical conclusions from the evaluation:

  • Every system incurs non-negligible cost or latency overhead for at least some queries.
  • Semantic joins are 3–10× more expensive than filters and are the dominant optimization target.
  • Audio processing is poorly supported — only 3 of 4 systems handle it at all.
  • No single system dominates across all dimensions: LOTUS for filter quality, Palimpzest for join quality, ThalamusDB for cost, BigQuery for latency and scalability.
  • LLM quality is highly domain-dependent; a system that works well for image classification may perform poorly on multi-hop reasoning — and vice versa.
Broader significance

SemBench marks a transition in database benchmarking: from measuring purely relational performance to measuring the joint performance of database engines and the AI models embedded within them. As SQPEs expand their operator coverage (semantic aggregation, grouping) and data modality support (video, multi-image), SemBench plans to add corresponding scenarios. The public leaderboard at sembench.org will continuously update as new systems and results become available.
