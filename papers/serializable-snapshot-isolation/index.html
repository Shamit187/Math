Serializable Isolation for Snapshot Databases

Michael J. Cahill, Uwe Röhm, Alan D. Fekete ACM SIGMOD International Conference on Management of Data · SIGMOD 2008
Abstract Many popular database management systems offer snapshot isolation (SI) rather than full serializability. SI is attractive because readers never block writers and vice versa, and it eliminates many common anomalies. But SI is not fully serializable: carefully-crafted interleaving of transactions that individually maintain consistency can violate integrity constraints globally. Until now, preventing such anomalies required application developers to introduce artificial locking or update conflicts through careful static analysis. This paper presents a new concurrency control algorithm — Serializable Snapshot Isolation (SSI) — that automatically detects and aborts transactions involved in dangerous SI-specific conflict patterns at runtime, for arbitrary applications, without requiring any application modification. SSI preserves SI's attractive property that reads never block writes. A prototype in Oracle Berkeley DB shows throughput approaching that of plain SI in most cases, and significantly better than strict two-phase locking (S2PL).

1. The Problem with Snapshot Isolation

Snapshot isolation has become one of the most widely deployed concurrency control mechanisms in production databases. Oracle RDBMS, PostgreSQL, SQL Server 2005, and Oracle Berkeley DB all offer it. Its appeal is obvious: reads are served from a snapshot of the database taken at transaction start time, so concurrent writes by other transactions never delay a read, and reads never delay writes. This gives much higher throughput than strict two-phase locking (S2PL), especially on read-heavy workloads.

The trouble is that snapshot isolation is not serializable. It is possible, under SI, for a set of transactions — each of which maintains all declared integrity constraints when run alone — to collectively corrupt the database when run concurrently. The classic example is write skew, first identified in Berenson et al. 1995.

Example 1 — Write Skew (The Doctor On-Call Problem)

A hospital database has a table Duties(DoctorId, Shift, Status) representing which doctors are on duty. An invariant requires that at least one doctor be on duty in every shift. A transaction that changes a doctor's status from "on duty" to "reserve" checks that at least one other doctor is still on duty before committing. Under SI, two such transactions — one for Doctor D1 and one for Doctor D2 — can both start at the same snapshot showing both doctors on duty, each see the other as on duty and proceed, and both commit — leaving no doctor on duty. The invariant is violated even though each transaction was individually correct.

The traditional remedy is to force the application to introduce artificial locking: for example, issuing a SELECT FOR UPDATE on the entire Duties table before checking the constraint, so that only one transaction can proceed at a time. This works, but it requires developers to be aware of every possible SI anomaly in their application — a daunting requirement for large, evolving codebases.

2. Snapshot Isolation Refresher

Under snapshot isolation, when a transaction $T$ begins, it is conceptually assigned a start timestamp $\text{start-time}(T)$. When $T$ reads a data item $x$, it sees the version of $x$ written by the most recent transaction that committed strictly before $\text{start-time}(T)$ and that also modified $x$. It never sees writes from transactions that are concurrent with $T$ (i.e., transactions that were still running when $T$ started).

SI enforces one additional rule: the First-Committer-Wins rule. If transaction $T_1$ and $T_2$ are concurrent and both wish to write the same data item, the one that commits first succeeds; the other is aborted with an update conflict. This prevents Lost Update anomalies.

Definition — rw-Dependency (Anti-Dependency)

A transaction $T_1$ has an rw-dependency (also called an anti-dependency) to $T_2$ if $T_1$ reads some version of item $x$, and $T_2$ later writes a newer version of $x$ — a version that is later in the version order than the version that $T_1$ read. Intuitively: $T_2$ "overwrites" what $T_1$ saw, so $T_1$ was working with stale data relative to $T_2$'s write.

3. Write Skew and the Multiversion Serialization Graph

Transaction histories can be analyzed using a multiversion serialization graph (MVSG). Each committed transaction is a node. Edges represent dependencies: a wr-dependency from $T_1$ to $T_2$ means $T_1$ wrote a version of $x$ that $T_2$ read. A ww-dependency means $T_1$ wrote a version of $x$ that was immediately superseded by $T_2$'s write. A rw-dependency (dashed edge in the paper's diagrams) means $T_1$ read a version of $x$ that was later overwritten by $T_2$.

A history is serializable if and only if its MVSG is acyclic. Adya (1999) showed that any cycle produced by SI must contain at least two rw-dependency edges. Fekete et al. (2005) extended this to show that any cycle under SI must contain two consecutive rw-dependency edges — that is, there must exist a "pivot" transaction $T_0$ with rw-dependencies both incoming (from some $T_N$) and outgoing (to some $T_1$), and both $T_N$ and $T_1$ are concurrent with $T_0$.

Definition — Dangerous Structure

A dangerous structure in the MVSG is a configuration of three transactions $T_N, T_0, T_1$ such that: (1) there is an rw-dependency from $T_N$ to $T_0$, (2) there is an rw-dependency from $T_0$ to $T_1$, (3) $T_N$ and $T_0$ are concurrent, and (4) $T_0$ and $T_1$ are concurrent. Fekete et al. proved that every non-serializable execution under SI contains at least one dangerous structure. Therefore, aborting one transaction from every dangerous structure is sufficient to ensure serializability.

Intuition — Why Two Consecutive rw-Edges?

Think of an rw-dependency from $T_1$ to $T_2$ as saying: "$T_2$ wrote something after $T_1$ read it." SI's snapshot mechanism means that $T_1$ could not have seen $T_2$'s write. A single such edge is safe: it just means $T_1$ operated on slightly stale data, which is exactly what SI allows. But two consecutive rw-edges create a situation where the stale reads of two transactions mutually enable each other's writes to violate a global constraint — the essence of write skew. Detecting and breaking this pattern is precisely what SSI does.

4. The Write Skew Pattern: Two Consecutive rw-Edges at Runtime

The write skew example with doctors D1 and D2 corresponds exactly to the dangerous structure in the MVSG. Let $T_0$ be the initial state (conceptually a committed transaction that wrote the initial data). Let $T_1$ be D1's transaction and $T_2$ be D2's transaction.

$T_1$ reads D2's status (rw-dep: $T_1$ reads, $T_2$ later writes — so there is an rw-edge from $T_1$ to $T_2$). $T_2$ reads D1's status (rw-dep from $T_2$ to $T_1$). These two edges form the consecutive rw-pair with $T_1$ as pivot: incoming rw from $T_2$, outgoing rw to $T_2$ — and both $T_1$ and $T_2$ are concurrent. Similarly $T_2$ is also a pivot. SSI detects this pattern and aborts one of the transactions.

5. The SSI Algorithm

The core algorithm is simple to state: maintain two boolean flags per transaction, and abort when both are set. Each transaction record carries:

Definition — SSI Conflict Flags

T.inConflict is set to true if there is an rw-dependency from some concurrent transaction $U$ to $T$ — meaning $U$ read something that $T$ later wrote.

T.outConflict is set to true if there is an rw-dependency from $T$ to some concurrent transaction $U$ — meaning $T$ read something that $U$ later wrote.

A potential non-serializable execution is detected whenever both T.inConflict and T.outConflict are true simultaneously for some transaction $T$ — meaning $T$ is a pivot in a dangerous structure.

When a dangerous structure is detected, one of the transactions involved is aborted. The prototype aborts the pivot (the transaction with both flags set) unless the pivot has already committed, in which case one of the transactions that set its flags is aborted instead. This is a conservative policy: it may abort some transactions that would not have caused a non-serializable execution (false positives), but it never allows a truly non-serializable execution to commit.

The check at commit time is simple:

Algorithm — Modified commit(T)

At the start of a transaction, set T.inConflict = T.outConflict = false. At commit time: if T.inConflict and T.outConflict are both true, abort T and return UNSAFE_ERROR. Otherwise, proceed with the normal SI commit path and release WRITE locks (but not SIREAD locks).

6. The SIREAD Lock and Detecting rw-Dependencies

The crucial challenge in implementing SSI is detecting rw-dependencies at runtime. An rw-dependency from $T_1$ to $T_2$ arises when $T_1$ reads version $v$ of item $x$, and $T_2$ creates a later version $v'$ of $x$ while $T_1$ is still active.

The algorithm uses a new type of lock called SIREAD. Unlike a standard read lock, a SIREAD lock does not conflict with WRITE locks — so acquiring a SIREAD lock never blocks a writer, and an existing WRITE lock never blocks a SIREAD acquirer. SIREAD locks are purely informational: their presence on item $x$ tells any future writer "a transaction has read this item."

When transaction $T$ reads item $x$, the modified read procedure: (1) acquires a SIREAD lock on $x$ for $T$, (2) checks whether any WRITE lock exists on $x$ held by a concurrent committed transaction $U$ with U.inConflict set — if so, abort $T$ (it would be part of a dangerous structure), (3) for each version of $x$ newer than what $T$ read, if the creating transaction $U$ is committed and has U.outConflict set, abort $T$; otherwise set U.inConflict = T.outConflict = true.

When transaction $T$ writes item $x$, the modified write procedure checks for existing SIREAD locks on $x$. If a SIREAD lock exists for a concurrent transaction $U$ (meaning $U$ read the version of $x$ that $T$ is about to overwrite), this is an rw-dependency: set U.outConflict = T.inConflict = true. If both flags on either transaction are now true, abort it.

Caution — SIREAD Locks Must Outlive Their Transaction

A critical subtlety: SIREAD locks must be retained even after their owning transaction $T$ has committed, until all transactions that were concurrent with $T$ have also completed. This is because a write by a later transaction $U$ may create a rw-dependency from $T$ to $U$ even after $T$ commits — and we still need to detect it to protect $U$'s concurrent partners.

7. Implementation in Oracle Berkeley DB

The authors implemented SSI in Oracle Berkeley DB version 4.6.21, an open-source embedded database used as a reference platform. Berkeley DB performs locking and multi-version concurrency control at the granularity of database pages, not individual rows. This is coarser than ideal for SSI (it introduces false positive rw-dependencies between transactions that access different rows on the same page), but it simplified implementation significantly.

The total implementation required modifying only 692 lines of code out of approximately 200,000 lines in Berkeley DB — about 0.3% of the codebase. The changes comprised: (1) new error return codes DB_SNAPSHOT_CONFLICT and DB_SNAPSHOT_UNSAFE, (2) the new SIREAD lock mode (which does not conflict with any other lock mode), (3) modified read/write/commit procedures as described above, and (4) a cleanup procedure to remove SIREAD locks whose owning transactions can no longer participate in dangerous structures (i.e., all concurrent transactions have committed).

The lock cleanup procedure runs periodically and whenever the lock table is full. It finds the earliest read timestamp among all active transactions and removes any SIREAD lock whose owning transaction committed before that timestamp — at that point, no active transaction could be concurrent with the lock's owner.

8. Correctness and False Positives

The correctness argument for SSI rests on three facts: (1) Every non-serializable execution under SI contains a cycle with two consecutive rw-dependencies (Fekete et al., Theorem 2.1). (2) The SSI algorithm detects every rw-dependency between concurrent transactions (by SIREAD lock tracking). (3) When two consecutive rw-dependencies are detected, at least one of the transactions involved is aborted, breaking the cycle.

The algorithm is conservative: the two boolean flags per transaction cannot distinguish whether the two rw-dependencies to and from a pivot transaction form an actual cycle in the MVSG. They may have no path between them — in which case no non-serializable execution is possible, but SSI aborts anyway. This is a false positive.

Example — False Positive

Consider transactions T0, T1, TN. TN reads $x$ and $z$; T0 writes $x$ and reads $y$; T1 writes $y$ and $z$. There is an rw-edge from TN to T0 (TN read $x$, T0 wrote $x$) and an rw-edge from T0 to T1 (T0 read $y$, T1 wrote $y$). Both flags on T0 are set, so SSI aborts T0. But if there is no path in the MVSG from T1 back to TN (i.e., T1 and TN are unrelated), then this execution was actually serializable. SSI aborted T0 unnecessarily.

In practice, false positives are rare on real workloads. They are more common at high contention with page-level locking, because different-row accesses on the same page create spurious rw-dependencies. The authors argue that the false-positive rate is acceptable in exchange for the simplicity and low overhead of the two-flag approach.

9. Experimental Evaluation

The evaluation uses the SmallBank benchmark, a model of a simple banking application with five transaction types: Balance (Bal), Deposit-Checking (DC), Transfer-to-Savings (TS), Write-Check (WC), and Amalgamate (Amg). The static dependency graph of SmallBank contains the dangerous structure: Balance → WriteCheck → TransactSavings → Balance, with WriteCheck as the pivot. Without SSI, SmallBank transactions can exhibit write skew under ordinary SI.

Short transactions (without log flushes): At multi-programming level (MPL) 20 with no disk I/O on commit, SI achieves roughly 15,000 transactions per second (TPS), S2PL achieves only about 2,500 TPS, and SSI achieves approximately 13,000 TPS — about 85% of SI's throughput and more than 5x better than S2PL. The performance gap between SSI and SI is due to the overhead of SIREAD lock management and false-positive aborts.

Long transactions (with log flushes): When commit requires a disk write, transaction duration increases by an order of magnitude. In this regime, SSI's throughput tracks SI closely at low MPL, and both significantly outperform S2PL at high MPL because S2PL deadlocks consume substantial CPU time for detection. SSI's error rate is slightly higher than SI's (due to false positives) but much lower than S2PL's deadlock rate.

Low contention (large dataset): With a dataset ten times larger (fewer conflicts), the overhead of SSI over SI is 10–15%. This overhead comes primarily from managing the larger lock and transaction tables and from false-positive aborts. The authors note this is an artifact of Berkeley DB's page-level granularity; a row-level implementation would have far fewer false positives and thus lower overhead.

10. Impact and Legacy

The Cahill-Röhm-Fekete SSI paper had immediate and lasting impact. Its most prominent adoption was in PostgreSQL 9.1, released in 2011, which implemented SSI as its "Serializable" isolation level. The PostgreSQL implementation extended the algorithm to handle predicate reads (phantoms) using predicate locking, and reduced false positives through more careful tracking of conflict edges. Today, PostgreSQL's default serializable isolation is SSI, not S2PL.

The paper elegantly resolved a long-standing puzzle in database research: everyone knew SI was not serializable, but making it serializable had seemed to require either expensive static analysis or full two-phase locking. SSI showed that a small amount of runtime bookkeeping — two bits per transaction and a non-blocking lock type — suffices. The insight that dangerous structures, not arbitrary cycles, are both necessary and sufficient for SI anomalies is the key theoretical contribution.

SSI also influenced the design of distributed transaction systems. Google Spanner uses a variant of SSI for its externally-consistent transactions, and CockroachDB, TiDB, and YugabyteDB all implement serializable isolation via SSI-based algorithms. The paper's influence on production systems is thus substantial and ongoing.
