Database Architecture Optimized for the new Bottleneck: Memory Access

Peter Boncz, Stefan Manegold, Martin L. Kersten Proceedings of the 25th VLDB Conference, Edinburgh, Scotland, 1999
Abstract Through the 1990s, database performance tuning was synonymous with minimizing disk I/O. But by 1999, something had changed: main memory had become large enough to hold entire databases, and disks had become fast enough that a well-buffered system rarely hit them. The new bottleneck was the CPU's access to main memory. Processor speeds were growing at roughly 70% per year, while DRAM speeds improved by barely 50% over the entire decade. A simple scan experiment on the MonetDB system reveals the consequence: a database server running a trivial in-memory table scan spends 95% of its time waiting for memory, not doing computation. This paper diagnoses the bottleneck through hardware event counters (TLB misses, L1 misses, L2 misses), translates the diagnosis into architectural guidelines (columnar vertical decomposition), and introduces a family of cache-conscious radix algorithms for equi-join that exploit the memory hierarchy from TLB all the way to L1 cache.

1. Introduction

The traditional database performance model pictures a slow disk and a fast CPU separated by a memory buffer pool. The optimizer minimizes the number of page reads; everything else is considered free. This model was accurate when disk access took millions of CPU cycles and memory access took just a handful. By the late 1990s, it had become dangerously wrong.

Processor speeds had been roughly doubling every 18 months (Moore's law, as popularly applied to clock speed). DRAM speeds had not kept pace. The physics of DRAM chips forces a trade-off between capacity and speed, and the market had chosen capacity. The result was a widening "memory gap": by 1999, accessing a single word from main memory took over 100 CPU cycles on high-end workstations. A 250 MHz CPU can execute 250 million instructions per second; waiting 100 cycles for one memory access is 400 nanoseconds of dead time.

The memory system's response to this gap — a hierarchy of progressively faster, progressively smaller caches — helps only if the access pattern is local. If a program accesses memory randomly, no cache can help: every access misses every level of cache and goes all the way to main memory. Database query processing, with its joins over large relations and its record-at-a-time tuple layout, is one of the worst-case access patterns imaginable for a cache hierarchy.

2. The Memory Bottleneck

The paper identifies three distinct components of memory performance, each with its own characteristics:

Definition — The Memory Hierarchy Components

L1 cache (on-die, ~32 KB, 1–4 ns): Contains the most recently accessed cache lines. A cache line is 16–32 bytes on 1990s hardware. If successive memory accesses fall within the same cache line (stride smaller than line size), L1 gives essentially free performance.

L2 cache (on-die or close, ~4 MB, 10–25 ns): Holds recently used L1 lines that were evicted. Accesses that miss L1 but hit L2 cost about 6–10× more than L1 hits.

TLB (Translation Lookaside Buffer, ~64 entries): Holds the virtual-to-physical page address translations for recently accessed pages. A TLB miss requires a hardware page-table walk — on some architectures more expensive than a main memory access. If a query accesses more than 64 distinct pages simultaneously, TLB misses begin to dominate.

Main memory (DRAM, ~400 ns): The penalty for a full cache miss from L2 to main memory is measured in hundreds of CPU cycles.

The paper models the execution cost per iteration of a simple scan as:

$$T(s) = T_{CPU} + T_{L2}(s) + T_{Mem}(s)$$

with

$$T_{L2}(s) = M_{L1}(s) \cdot l_{L2}, \quad M_{L1}(s) = \min\!\left(\frac{s}{LS_{L1}},\; 1\right)$$

$$T_{Mem}(s) = M_{L2}(s) \cdot l_{Mem}, \quad M_{L2}(s) = \min\!\left(\frac{s}{LS_{L2}},\; 1\right)$$

where $s$ is the stride in bytes (the gap between consecutive memory accesses), $LS_{L1}$ and $LS_{L2}$ are the L1 and L2 cache line sizes, and $l_{L2}$ and $l_{Mem}$ are the latencies for L2 and main memory accesses in CPU cycles. When $s$ exceeds the L2 cache line size (typically 64–128 bytes), every iteration is a guaranteed cache miss.

3. The Reality Check Experiment

To demonstrate the severity of the bottleneck concretely, the authors perform a "reality check" scan: sequentially read 200,000 bytes from an in-memory buffer, with varying stride $s$. The Y-axis measures elapsed time; the X-axis is the stride in bytes.

The results are striking. On all tested machines (Sun LX, Sun Ultra, Sun Ultra-2, SGI Origin 2000), elapsed time is nearly flat and minimal for small strides (data fits within a cache line, so successive accesses hit L1). Time jumps sharply at the L1 cache line boundary (typically 16–32 bytes), then jumps again at the L2 line boundary (64–128 bytes), then plateaus as every access becomes a full main-memory fetch.

Intuition — What this means for row-store databases

A conventional row-store tuple for the TPC-D "Item" table is about 80 bytes wide. A query that scans a single integer column (4 bytes) of that table accesses one integer every 80 bytes — a stride of 80 bytes, which is right in the danger zone where L2 misses begin. The CPU fetches a 64-byte cache line, uses 4 of those bytes, and discards the rest. It is 94% wasted memory bandwidth. With 200,000 tuples, the scan spends nearly all its time waiting for memory, not computing.

4. Vertical Data Layout

The architectural response is vertical fragmentation: store each column of a relational table in a separate array, rather than storing all columns of each row together. MonetDB implements this through Binary Association Tables (BATs).

Definition — Binary Association Table (BAT)

A BAT stores one column of a relation as an array of fixed-size two-field records: (OID, value). The OID (Object Identifier) acts as the row key; the value is the column value for that row. Because all entries have the same fixed width, the array is dense and contiguous in memory. A BAT for an integer column has a stride of exactly 8 bytes (4 for OID, 4 for value), rather than the 80-byte stride of the full row tuple. The entire column fits in far fewer cache lines, and sequential scans become maximally cache-friendly.

MonetDB further reduces memory footprint using two techniques. First, virtual OIDs: when OID values are dense and ascending (1000, 1001, 1002, …), there is no need to store them explicitly. MonetDB computes OIDs on the fly from array position, saving 4 bytes per entry — a 50% reduction in BAT width for many columns. Second, byte encodings: columns with low domain cardinality (e.g., a shipmode column with 7 possible values) are stored as 1- or 2-byte integers rather than variable-length strings, without requiring a decoding step during selection since equality predicates can be translated to integer comparisons at query compile time.

The result for the TPC-D "shipmode" column: storage per value shrinks from 8 bytes (in a standard BAT) to 1 byte (after byte-encoding and virtual-OID). That is an 8× improvement in data density, meaning 8× more shipmode values fit in a given amount of cache.

5. Query Processing Algorithms

For sequential scans and selections with low selectivity (most of the relation must be visited), vertical layout combined with a simple scan is optimal: the memory access pattern is stride-1 on a narrow array. The paper focuses most of its algorithmic contribution on the harder operator: the equi-join.

Hash-join has long been the default for main-memory databases. The standard algorithm builds a hash table on the inner relation, then probes it for each tuple of the outer relation. The problem: if the inner relation's hash table does not fit in L2 cache (which it usually does not for large relations), every probe generates a random memory access — there are no locality guarantees from hashing. With the inner relation spanning thousands of cache lines, each probe is a cache miss.

Why standard hash-join thrashes cache

A hash function maps each probe key to a bucket in the hash table. If the hash table has $H$ buckets spread over main memory, then on average each probe touches a different page. If $H$ exceeds the number of TLB entries (64), then each probe also causes a TLB miss — the virtual-to-physical address lookup must be performed for each bucket. The combination of cache miss and TLB miss makes each probe cost hundreds of CPU cycles. For a join of tens of millions of tuples, this dominates completely.

6. Radix Clustering

The solution is to cluster both relations before joining, so that matching tuples are physically adjacent in memory and the join can be computed with purely sequential access. MonetDB introduces radix-cluster: a multi-pass algorithm that groups tuples by the low-order bits of their join key.

Radix-cluster on $B$ bits is done in $P$ passes, each processing $B_p$ bits (with $\sum_{p=1}^{P} B_p = B$). After clustering, tuples are grouped into $H = 2^B$ clusters of approximately $C/H$ tuples each. Tuples with the same low-order $B$ bits in their join key are physically co-located.

The key insight behind using multiple passes: each pass writes tuples into $H_p = 2^{B_p}$ output buckets simultaneously. If $H_p$ exceeds the number of TLB entries, writing into that many simultaneous buckets causes TLB trashing. By using multiple passes with fewer bits per pass, the number of simultaneously active output buckets stays below the TLB capacity, avoiding TLB misses. The extra I/O of an additional pass is cheaper than the TLB thrashing it prevents.

The total execution cost for radix-cluster on $P$ passes, $B$ bits, and relation cardinality $C$ is modeled as:

$$T_c(P,B,C) = P \cdot \!\left(C w_c + M_{L1,c}\!\!\left(\tfrac{B}{P}, C\right) l_{L2} + M_{L2,c}\!\!\left(\tfrac{B}{P}, C\right) l_{Mem} + M_{TLB,c}\!\!\left(\tfrac{B}{P}, C\right) l_{TLB}\right)$$

where $w_c$ is the per-tuple computation cost, $l_{L2}, l_{Mem}, l_{TLB}$ are latencies in CPU cycles for L2, main memory, and TLB misses, and the $M$ functions count the expected number of misses per relation pass.

7. The Join Algorithms

Two join algorithms build on radix-cluster:

Definition — Partitioned Hash-Join and Radix-Join

Partitioned hash-join: Radix-cluster both relations on $B$ bits to create $H = 2^B$ cluster pairs. For each pair, build a hash table on the inner cluster and probe with the outer cluster. Because each cluster is small (approximately $C/H$ tuples), the hash table fits in cache, and probing is cache-friendly.

Radix-join: Radix-cluster both relations on $B$ bits. For each pair of matching clusters, use a simple nested-loop join — no hash table. This works because after radix-clustering, matching tuples are already sorted by their low-order bits, so a sequential scan of each cluster pair finds all matches. Cluster size must be small enough to fit in L1 cache (about 8 tuples per cluster for optimal performance).

The choice between them depends on relation cardinality. Radix-join needs more clustering bits (to get cluster sizes small enough for nested-loop), making the clustering phase more expensive. Partitioned hash-join needs fewer clustering bits (clusters just need to fit in L2 or TLB size), but the hash table overhead becomes expensive when clusters get very small. The paper identifies four regimes based on optimal cluster size: "phash L2" (clusters fit in L2), "phash TLB" (clusters fit within TLB pages), "phash L1" (clusters fit in L1), and "radix" (optimal for the radix-join).

8. Cost Models

A distinctive feature of this paper is its commitment to quantitative} analytical models. Rather than just reporting benchmark numbers, the authors develop cost models that predict performance from hardware parameters: cache line sizes, cache capacities, TLB size, memory latency, and CPU speed. These models are validated against actual hardware event counter measurements using the MIPS R10000 performance counters available on the SGI Origin2000.

The radix-join cost model is:

$$T_r(B, C) = C\!\left\lceil\frac{C}{H}\right\rceil w_r + C w_r' + M_{L1,r}(B,C) l_{L2} + M_{L2,r}(B,C) l_{Mem} + M_{TLB,r}(B,C) l_{TLB}$$

The paper calibrated the model on the Origin2000 with $l_{TLB} = 228\,\text{ns}$, $l_{L2} = 24\,\text{ns}$, $l_{Mem} = 412\,\text{ns}$, and $w_c = 50\,\text{ns}$. The predictions match measured performance closely across all tested cardinalities and bit widths — the model lines in the paper's plots trace through the data points with remarkable accuracy.

This kind of hardware-grounded modeling was unusual for database systems papers in 1999, which more typically reported relative speedup ratios without explaining the mechanism. The MonetDB approach — measure the actual hardware events, build a model from those events, validate the model — became increasingly standard in systems research over the following decade.

9. Overall Results

The comparison of all join strategies is summarized in the paper's Figure 13, plotting elapsed time versus relation cardinality. Key findings:

  • Simple hash-join and sort-merge join, which perform random memory accesses, are slowest across all cardinalities.
  • All four radix-cluster-based strategies significantly outperform the random-access alternatives.
  • The phash-L2 strategy is optimal for small cardinalities (below about 250,000 tuples), where the hash table fits comfortably in L2.
  • Radix-join wins for large cardinalities (above about 1 million tuples), where the extra clustering cost is amortized and the nested-loop over tiny clusters becomes extremely cache-efficient.
  • The vertical (columnar) BAT storage format, combined with virtual OIDs and byte encoding, achieves roughly 8× reduction in memory footprint for typical OLAP columns compared to row-store layout.

The paper also cites an external validation: the Drill Down Benchmark, where a commercial row-store database running with a large buffer pool (nearly memory-resident) was measured to be 40× slower than MonetDB on the same workload. After incorporating the cache-optimization techniques described in the paper, MonetDB further improved its own result by almost another order of magnitude on that benchmark.

10. Legacy and Impact

This paper provided the theoretical and empirical foundation for a transformation that reshaped database systems over the following 20 years: the shift from row-oriented to column-oriented storage for analytical workloads.

The columnar storage idea did not originate here — it appeared in earlier work on vertical partitioning and the Decomposed Storage Model (DSM). What this paper added was the detailed, hardware-grounded justification: cache line analysis, TLB miss counting, and validated cost models that explained precisely why columnar storage wins for analytical queries and by how much. That quantitative grounding made the case impossible to dismiss.

The radix-join algorithm introduced here became a staple of main-memory database implementation. It is used in MonetDB, DuckDB, and many analytical engines. The broader principle — that join algorithms must be designed with the memory hierarchy in mind, not just I/O cost — is now considered foundational. Cache-conscious join algorithms appear in textbooks that would have laughed at the idea in 1990.

The paper also established a methodological precedent: using hardware performance counters to validate analytical cost models. This approach — instrument the hardware, not just the software — became standard in systems papers through the 2000s and 2010s and is now expected in top-tier systems research. The Boncz, Manegold, Kersten paper is one of the earliest examples of doing it rigorously for a database problem.
