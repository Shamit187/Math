Querying Heterogeneous Information Sources Using Source Descriptions

Alon Y. Levy, Anand Rajaraman, Joann J. Ordille Proceedings of the 22nd VLDB Conference, Mumbai, India, 1996
Abstract By 1996, hundreds of structured information sources had appeared on the World Wide Web — databases of used cars, stock prices, bibliographies, phone directories — yet querying them was painful and manual. Each source had its own interface, its own schema, and no source could see any other. This paper introduces the Information Manifold (IM), a system that provides a single, uniform query interface over more than 100 such sources simultaneously. The key idea is twofold: first, each source is described declaratively — both its contents (what data it holds) and its capabilities (what queries it can accept) — using a concise formal language. Second, a planning algorithm reads these descriptions to automatically construct executable query plans, pruning irrelevant sources and combining results from multiple sources in a provably correct way. Experiments with queries over 100 sources show that plan generation takes under one second per plan, and the algorithm scales sub-exponentially thanks to an effective source-pruning step called bucket creation.

1. Introduction

Imagine you want to find sportscars for sale that were manufactured no earlier than 1992, together with reviews for each model you find. The data you need is scattered. One website covers used cars generally; another is limited to luxury cars priced above $20,000; a third tracks vintage cars from before 1950; a fourth has product reviews for cars made after 1990. To answer your question manually you must figure out which sites are even relevant, separately query each relevant site according to its own interface, and then join the results yourself. The Information Manifold is an attempt to automate every step of that process.

The challenge is not just that the sources are numerous. It is that they are heterogeneous in two orthogonal senses. Their contents differ: no two databases cover exactly the same slice of reality. And their capabilities differ: some sources accept a category filter but not a year filter; others require a model as input; still others return results only in a particular format. A query planner that ignores either dimension will either miss relevant sources or try to use sources in ways they cannot support.

2. The Core Problem

Most earlier work on federated databases assumed that every source is a full relational database — one that can accept arbitrary SQL queries and return arbitrary results. That assumption is almost never true on the open Web. A web form for used cars might accept a model name and a price range, but refuse to answer queries that ask only for a year range. The IM paper is one of the first to take source capabilities seriously as a first-class constraint.

Intuition — Why capability matters

Think of each source as a black box with a specific set of input slots and output slots. You can only pull data out of the box by filling in the required input slots first. Before you can use a source in a query plan, you must ensure that earlier steps in the plan have already produced values to fill those slots. Ignoring this constraint produces plans that look correct on paper but cannot actually be executed.

A second challenge is incompleteness. No source claims to contain all cars for sale. The IM system therefore adopts an open-world assumption: the answer to a query is the union of all tuples that any executable, semantically correct plan can produce. This is a deliberate choice — it means answers can be partial, but they are never wrong.

3. Describing Sources

The heart of the Information Manifold is its source description language. Each source is described by two complementary components: a content description and a capability record.

Definition — Content Description

The content of a source is described as a conjunctive query over the world-view relations. For example, Source 1 (used cars) is described as:

V₁(c) ⊆ CarForSale(c), UsedCar(c)

This says: every car c that Source 1 knows about is a car for sale and is a used car. The source need not contain all such cars — it contains a subset. This is captured by the subset symbol rather than the equality sign.

Definition — Capability Record

A capability record for a source relation R is a 5-tuple $(S_{in}, S_{out}, S_{sel}, \text{min}, \text{max})$ where $S_{in}$ is the set of parameters that must be given as inputs, $S_{out}$ is the set of attributes returned as outputs, $S_{sel}$ is the set of attributes on which the source can apply selections, and min and max are the minimum and maximum number of input bindings the source will accept. A query plan step must respect all of these constraints.

To illustrate: Source 1's capability record indicates that it requires at least one of {Model, Category} as an input, can return {Model, Year, Price, SellerContact}, and can apply a selection on Year or Price. Source 2 (luxury cars, all priced above $20,000) has its price constraint baked into the content description — its content query includes the built-in atom $p \geq 20000$, so the planner can immediately prune it from any query that asks for cheap cars.

Example — Source pruning in action

Our running query asks for sportscars manufactured no earlier than 1992. Source 3 covers only cars manufactured before 1950. Its content description includes the built-in predicate $\text{Year}(c, y),\; y \leq 1950$. Since this contradicts the query's requirement $y \geq 1992$, Source 3 can be eliminated without even contacting it. Similarly, Source 4 covers only motorcycles — the class Motorcycle is declared disjoint from CarForSale, so it is also pruned immediately.

4. The World View

Users pose queries against a world view: a virtual schema of relations and classes that acts like a global database schema, even though no data is actually stored there. The world view for the car example includes a class hierarchy — CarForSale is a subclass of Car, which is a subclass of Automobile, and so on — plus relations like ProductReview(Model, Year, Review). Users write queries against these virtual relations. The system's job is to decompose such queries into concrete accesses to real sources.

Formally, a query in the Information Manifold is a conjunctive query of the form:

$$Q(\bar{X}) \leftarrow R_1(\bar{Z}_1),\; \ldots,\; R_n(\bar{Z}_n),\; C_Q$$

where $R_1, \ldots, R_n$ are world-view relations and $C_Q$ is a conjunction of comparison constraints (order subgoals) of the form $u\,\theta\,v$ with $\theta \in \{<, >, \leq, \neq, =\}$. Queries must be range-restricted, meaning every answer variable appears in at least one relational subgoal.

Pause and reflect

Notice the elegant separation of concerns. The world view is a logical schema that has nothing to do with any specific source. The source descriptions relate each source's contents to world-view relations. The query is expressed purely against the world view. This three-layer architecture means you can add or remove sources without touching either the user queries or the world-view schema. It is the same idea that underlies modern data virtualization platforms thirty years later.

5. Query Plans

A query plan is a sequence of accesses to information sources, interleaved with local processing (selection, join, projection). A plan must be both semantically correct and executable.

Semantic correctness is defined through expansion. If you unfold every source access in a plan by substituting the source's content description, the resulting query must be contained in (not necessarily equivalent to) the original user query. Containment rather than equivalence is the right notion because sources are incomplete — they may hold only a subset of the tuples matching a given condition.

Executability is about respecting capability records. The steps of the plan must be ordered so that whenever a source requires certain inputs, those inputs have already been produced by earlier steps. More precisely, at each step there must be a set of bound variables that satisfies the minimum input cardinality requirement of the source being accessed.

Example — A complete executable plan

For the sportscar query, one semantically correct and executable plan is:

  1. Access Source 1 with input {Category = sportscar}, receiving back {Model, Year, Price}. Apply the local filter $\text{Year} \geq 1992$.
  2. For each (Model, Year) pair returned, access Source 5 (car reviews) with inputs {Model, Year}, receiving a review text.
Note that Source 1 is placed first because it can accept a category as input and return year — satisfying Source 5's input requirement. The ordering is enforced, not guessed.

6. Planning Algorithms

The algorithm for generating query plans has two stages: (1) finding all semantically correct conjunctive plans, and (2) ordering each plan's subgoals to make it executable.

The first stage works by computing a bucket for each subgoal in the query. A bucket for subgoal $R_i$ is the set of sources whose content descriptions are consistent with — and can contribute tuples to — that subgoal. The algorithm CreateBuckets tests each source against each subgoal by checking whether adding the source's content description to the query creates an unsatisfiable set of constraints (e.g., a class membership and its disjointness partner both appear). Sources that pass the test are added to the bucket; those that fail are pruned.

Once all buckets are computed, the second stage generates semantically correct plans by taking one source from each bucket (the Cartesian product of the buckets), and checking whether a valid executable ordering exists. This check is done by the polynomial-time procedure create-executable-plan, which greedily orders subgoals by availability of bound variables and pushes as many selections as possible to the sources.

Theorem 4.1 — Completeness of the ordering algorithm

Let $Q'$ be a semantically correct conjunctive plan. If there exists any ordering of the subgoals of $Q'$ that yields an executable plan, then create-executable-plan will find it. Furthermore, the running time of the procedure is polynomial in the size of $Q'$.

A key complexity result complements this theorem: if sources were allowed to have multiple capability records (different sets of acceptable inputs for the same relation), then determining whether any executable ordering exists becomes NP-complete. The IM design choice of one canonical capability record per source is therefore not just a simplification — it is what keeps planning tractable.

Complexity warning

Without the bucket-pruning step, the number of candidate plans to check would be $O(n^{|Q|})$ where $n$ is the number of sources and $|Q|$ is the number of subgoals. With 100 sources and a 3-subgoal query, that is one million candidates. Bucket creation reduces this to the product of the bucket sizes, which in practice is tiny — often in the single digits.

7. Implementation and Experiments

The Information Manifold was deployed against over 100 structured information sources on the WWW, including entertainment databases, stock market feeds, bibliographic services, airline information, and product catalogs. Source descriptions were written by hand — one of the acknowledged open problems at the time.

The system architecture separates the planner from the execution engine via interface programs — one per source. Each interface program accepts the bound parameters dictated by the plan, queries the real source (often via form submission and HTML scraping), and returns structured tuples to the execution engine. The execution engine then applies local joins, projections, and selections.

Experiments measured three representative queries as the number of available sources was scaled from 20 to 100. Key findings:

  • Total query planning time grows sub-exponentially with the number of sources, even though the theoretical worst case is exponential. This is because bucket pruning keeps the bucket sizes small regardless of the total number of sources.
  • The average time per plan stays below one second for all tested queries, even with 100 sources. Network round-trip time to execute a plan typically dwarfs planning time.
  • For Query 1 (titles and years of movies featuring Tom Hanks), only 2 of 100 sources are ever placed in any bucket — the rest are pruned immediately by content mismatch. The number of plans enumerated is therefore 7 rather than the naive estimate of over a million.

8. Legacy and Impact

The Information Manifold paper arrived at the beginning of a decade-long wave of research on information integration. Its central contribution — the formal separation of what a source contains from what queries a source can answer, combined with automatic query planning over source descriptions — became the template for nearly all subsequent mediator-based integration systems.

The paper's "local-as-view" (LAV) framing — describing each source's content as a view over a global schema — proved especially influential. It was contrasted with the "global-as-view" (GAV) approach, and the comparison drove a large body of follow-on theoretical work. The problem of query rewriting using views was shown to be NP-complete in general and spurred decades of research on tractable special cases.

In the commercial world, the direct descendants of this work include data virtualization layers, federated query engines, and the concept of a data catalog. Modern systems like Apache Arrow Flight, Trino (PrestoSQL), and numerous enterprise data fabric products implement variants of the same basic idea: a virtual global schema, declarative source registrations, and automatic query decomposition and routing. The language has changed, but the architecture first sketched in the Information Manifold remains recognizable.
