Scientific Paper · VLDB 1997

An Efficient, Cost-Driven Index Selection Tool for Microsoft SQL Server

Surajit Chaudhuri, Vivek Narasayya Proceedings of the 23rd VLDB Conference, Athens, Greece, 1997
Abstract Choosing which indexes to build on a database is one of the most consequential decisions a database administrator can make — and one of the most tedious. Get it wrong, and queries that should take milliseconds take minutes. This paper describes AutoAdmin's index selection tool, built for Microsoft SQL Server 7.0, which automates that decision by using the query optimizer's own cost estimates as its guide. The key insight is that you can ask the optimizer to estimate the cost of running a workload with a hypothetical, not-yet-built index — a "what-if" index. By comparing costs across many configurations using what-if indexes, the tool can find a near-optimal set of indexes for a given SQL workload without ever building a single real index. Three novel techniques — a candidate index selection algorithm, an atomic-configuration cost evaluation scheme, and an iterative method for handling multi-column indexes — reduce the tool's running time by a factor of 4 to 10 compared to a naïve approach, with negligible loss in quality.

1. Introduction

Enterprise databases face a cruel trade-off. Indexes dramatically speed up reads by allowing the database to jump directly to relevant rows instead of scanning entire tables. But every index has a cost: it occupies storage space, and every INSERT, UPDATE, or DELETE must update all relevant indexes. A table with twenty indexes might serve SELECT queries twice as fast but suffer five times the write overhead. The question "which indexes should I build?" has no universal answer — it depends on the specific mix of queries and updates that the system actually receives.

Before AutoAdmin, the standard approach was either to follow textbook rules (index foreign keys, index highly selective columns, avoid more than five indexes per table) or to run an expert system that encoded those rules. Both approaches have the same weakness: they are disconnected from the query optimizer. A recommended index is only useful if the optimizer actually chooses to use it. An index the optimizer ignores wastes space and inflicts write overhead for no benefit. AutoAdmin's core philosophical shift is to let the optimizer drive the decision from start to finish.

2. The Index Selection Problem

The problem is formally stated as follows. Given a workload $W = \{Q_1, \ldots, Q_n\}$ and an upper bound $k$ on the number of indexes to select, find a configuration (a set of indexes) $C$ with $|C| \leq k$ that minimizes the total cost:

$$\text{Cost}(C, W) = \sum_{Q \in W} \text{Cost}(Q, C)$$

where $\text{Cost}(Q, C)$ is the optimizer's estimated cost for executing query $Q$ when configuration $C$ is present in the database. The configuration with the minimum total cost is the optimal configuration.

Intuition — Why is this hard?

If there are $n$ admissible indexes (columns that appear in WHERE, GROUP BY, or ORDER BY clauses), the number of subsets of size at most $k$ is $\binom{n}{k}$. For a realistic TPC-D workload with 100 admissible indexes and a limit of 10, that is over $10^{13}$ configurations. Even if each optimizer call took one microsecond, exhaustive search would take years. The tool must be clever about which configurations to even consider.

3. What-If Indexes

The foundational enabler of the entire approach is the what-if index — a hypothetical index that the tool registers with SQL Server without actually building it. SQL Server was modified to support this: when a what-if index is created, the server makes the distribution statistics for the indexed column(s) available to the optimizer as if the index existed. The optimizer then produces a cost estimate for any query that mentions those columns, as if the index were there.

This is a crucial architectural choice. By keeping the optimizer "in the loop" — rather than building a separate cost model — AutoAdmin inherits the optimizer's knowledge of join algorithms, selectivity estimation, and plan shape. If the optimizer later changes its strategies, the index selection tool automatically adapts, with no maintenance required.

Synchrony, not asynchrony

Earlier index selection tools maintained their own internal cost model, separate from the actual optimizer. This creates a synchronization problem: if the optimizer changes its behavior (e.g., adds a new join algorithm, updates its cost formulas), the tool's model becomes stale. AutoAdmin avoids this entirely by delegating all cost estimation to the live optimizer. The tool's only job is to intelligently choose which configurations to ask the optimizer to evaluate.

4. Cost Evaluation and Atomic Configurations

Calling the optimizer is expensive — each call requires inter-process communication and loading of distribution information. The paper introduces atomic configurations to minimize optimizer invocations.

Definition — Atomic Configuration

A configuration $C$ is atomic for a workload if for some query $Q$ in the workload, there exists an execution of $Q$ by the query engine that uses all indexes in $C$. Informally: an atomic configuration is one where all the indexes could plausibly be used together in a single plan.

The key insight is: if $C$ is not atomic, then the optimizer will always prefer some atomic subset of $C$ when optimizing any query. Therefore, we can derive the cost for non-atomic configurations from atomic ones without additional optimizer calls. Specifically, for a Select/Update query:

$$\text{Cost}(Q, C) = \min_{C_i \subseteq C,\; C_i \text{ atomic}} \text{Cost}(Q, C_i)$$

This means we only need to evaluate optimizer costs for atomic configurations. The total cost for any configuration $C$ can be assembled from these without extra optimizer calls.

The paper further constrains atomic configurations using two observations about real query processors. First, no query uses more than $j$ indexes per table (the paper finds $j = 2$ works well). Second, for multi-table queries, only indexes on the first $t$ joined tables matter most (the paper finds $t = 2$). These "single-join atomic configurations" dramatically cut the number of configurations that need optimizer evaluation — by 50% to 61% for workloads with complex joins.

A further trick is the relevant index set optimization. If two configurations $C$ and $C'$ have the same indexes on the columns that actually appear in a query, then $\text{Cost}(Q, C) = \text{Cost}(Q, C')$. So previously computed costs can be reused — yet another way to save optimizer invocations.

5. Candidate Index Selection

Rather than considering every admissible index for the whole workload at once, the algorithm first computes a smaller candidate index set. The idea: determine the best configuration for each individual query in the workload, and take the union of those best configurations as candidates. An index that is not part of the best configuration for any single query is unlikely to appear in the best configuration for the entire workload.

The best configuration for a single query is found by running the index selection tool itself on that one-query workload — a beautiful recursive self-application. This is called the query-specific-best-configuration (BEST-CONF) algorithm.

Example — Candidate selection in practice

For the TPC-D benchmark workload TPCD_2 (which involves 3, 4, and 5-join queries), BEST-CONF selects 33% fewer candidate indexes than the total number of admissible indexes, yet the final configuration chosen using only those candidates is identical in quality to the configuration chosen using all admissible indexes. The savings in optimizer calls and enumeration cost are substantial.

6. Configuration Enumeration

Once a candidate index set is established, the tool must search over subsets of candidates to find one of size at most $k$ with minimum total cost. Exhaustive enumeration is infeasible for realistic values of $n$ (number of candidates) and $k$. The paper uses the Greedy(m, k) algorithm.

Greedy($m, k$) works as follows:

  1. Start with the best $m$-index configuration found by exhaustive search (the "seed").
  2. Expand this seed greedily: at each step, add the one index that gives the largest cost reduction, until $k$ indexes have been chosen or no further reduction is possible.

The parameter $m$ controls the trade-off between quality and computation. When $m = 0$, the algorithm is a pure greedy. When $m = k$, it is the naïve exhaustive search. The paper finds that $m = 2$ yields near-optimal results with dramatically lower cost.

The experiments show that Greedy(2, k) finds the same configuration as exhaustive optimal search in all but one of the tested workloads (TPCD_4, an update-heavy workload), and even there the cost difference is less than 1%.

7. Multi-Column Indexes

Multi-column (composite) indexes — such as an index on (OrderDate, ShipMode) — can be more powerful than single-column indexes for queries with multiple predicates. But they explode the search space: for $k$ columns on a table, $k!$ orderings of a multi-column index are possible. The paper handles this with an iterative approach called MC-LEAD.

The strategy: in the first iteration, find the best single-column indexes. Then, for each single-column index on column $a$ that was selected, consider all two-column indexes of the form $M(a, b)$ for any column $b$. The key constraint is that $a$ must be the leading column, but $b$ need not itself have a winning single-column index. This is based on the intuition that a two-column index is only useful if its leading column is independently valuable.

Experiments show MC-LEAD loses 0–6% quality compared to the brute-force MC-BASIC approach across five TPC-D workloads, while dramatically reducing the number of multi-column index candidates considered.

8. Experimental Results

The tool was tested on five representative TPC-D workloads (TPCD_1 through TPCD_4 and TPCD_O) covering a range of join complexities and update percentages (from 0% to 50% updates). Key results:

  • Candidate index reduction: BEST-CONF selected 30–43% fewer candidate indexes than the total admissible indexes across all workloads, with 0–15% drop in final quality — and zero drop for three of the five workloads.
  • Optimizer call reduction: The combination of atomic configuration restrictions and relevant-index-set optimization reduced the total number of optimizer invocations by 79–92% compared to naïve evaluation.
  • Speed vs. baseline: The complete algorithm ran 4 to 10 times faster than a baseline that used no candidate selection and no atomic configuration tricks, with at most 7% quality drop (and usually 0–1%).
Pause and reflect

Notice that the paper never claims to find the mathematically optimal configuration. It claims to find a configuration that is close to optimal in terms of the optimizer's cost metric. This is the right goal for a practical tool: the optimizer's cost estimates are themselves approximations, so sub-percent quality differences are well within the noise. Burning exponential time chasing the last fraction of a percent is a poor use of resources.

9. Legacy and Impact

This paper essentially defined the architecture of modern automated physical database design tools. The what-if index concept became a standard feature: Oracle's SQL Tuning Advisor, IBM's Design Advisor, and PostgreSQL's HypoPG extension all implement variants of what-if indexing. The three-stage pipeline — candidate selection, configuration enumeration, multi-column handling — is recognizable in every commercial database advisor available today.

The principle of keeping the optimizer "in the loop" turned out to be deeply right. As optimizers became more sophisticated (incorporating partition pruning, index-only scans, materialized views, adaptive query plans), the AutoAdmin architecture absorbed those improvements automatically — because it was never simulating the optimizer, only consulting it.

The paper also seeded the broader field of self-tuning databases. AutoAdmin grew into a full research agenda at Microsoft that eventually produced automatic statistics maintenance, adaptive query processing, and, decades later, learned index structures and AI-driven tuning advisors. The 1997 paper is the root of that tree.
